## 🎯 슬라이드 3 — 프로젝트 개요 `[0:40 ~ 2:00]` ⏱ **1분 20초**

먼저 문제 정의입니다.

현재 대부분의 카드 앱은 **내역 조회에만 머무르고 있습니다.** 소비를 분석해 주지 않고, 이상 거래가 발생해도 사후 알림 수준이라 금전적 피해를 막기 어렵습니다. 개인화된 예산 조언도 없고, **소비 패턴과 사기 탐지가 연동된 서비스는 사실상 전무한 상황**입니다.

저희는 이 네 가지 문제를 AI로 풀고자 했습니다.

중앙 솔루션 박스를 보시면,
- **K-Means**로 사용자의 소비 유형을 절약형·균형형·소비형·투자형 네 그룹으로 분류하고,
- **Isolation Forest**로 이상 거래를 실시간 탐지하며,
- **LSTM과 XGBoost**로 지출을 예측·분류합니다.
- 여기에 **규칙 엔진과 ML 모델을 결합한 거래 리스크 하이브리드 평가** 시스템을 구축했습니다.

하단의 네 가지 핵심 목표 — AI 분석, 실시간 탐지, 개인화 전략, 유형 군집화 — 이것이 PayWise가 해결하려는 문제입니다.

## 🎯 슬라이드 5 — AI 소비 패턴 분석 `[3:20 ~ 4:50]` ⏱ **1분 30초**

핵심 AI 모델 네 가지입니다.

**첫째, K-Means 군집화**입니다. 식비·쇼핑·교통 등 **11개 카테고리별 지출 비율**을 표준화해 **4개 클러스터**로 분류합니다. 이를 통해 사용자를 절약형·균형형·소비형·투자형으로 자동 분류하고, 유형별로 예산 전략을 차별화합니다.

**둘째, Isolation Forest**입니다. 비지도 학습 모델로 **예상 이상치 비율(contamination)** 을 조정하면서 이상 스코어를 실시간 산출합니다. 지도 학습과 달리 사기 라벨이 부족한 실제 환경에서도 동작한다는 점이 강점입니다.

**셋째, LSTM**입니다. 시계열 소비 데이터를 학습해 다음 달 카테고리별 지출액을 예측합니다. 단순 평균이 아니라 **월별 시점 간 패턴**을 학습하는 구조입니다. 데이터가 부족한 사용자는 가중이동평균으로 자동 폴백돼서 항상 답을 줍니다.

**넷째, XGBoost**입니다. 과소비 레이블 기반 지도 학습 분류기로, **feature importance와 SHAP**을 활용해 "왜 과소비로 판정되었는지"를 사용자에게 설명할 수 있습니다. 이것이 뒤에 나올 XAI 기능의 기반이 됩니다.

하단 파이프라인처럼 **데이터 수집 → 특성 추출 → ML 추론 → API 응답** 네 단계가 순차 실행되며, 분석 결과는 프론트엔드의 레이더·바·게이지 차트로 시각화됩니다.

## 🎯 슬라이드 6 — 거래 리스크 평가 서비스 `[4:50 ~ 6:20]` ⏱ **1분 30초**

거래 리스크 평가 서비스, fraud-service입니다. 학습 데이터는 Kaggle 카드결제 공개 데이터셋이라 현재 스코프는 **카드 결제 이상 거래 스크리닝**이며, 송금 사기 도메인 확장은 후속 계획입니다.

왼쪽의 **판단 로직**부터 보시면, ML 스코어를 기준으로 네 단계로 분기합니다.
- **0.95 이상**이면 **BLOCK — 즉시 차단**,
- **0.35 이상**이면 **REVIEW — 추가 검토**,
- **0.005 이상**은 **SOFT_REVIEW — 경고 플래그**,
- 그 미만은 **PASS**입니다.

이 임계값은 **불균형 데이터 평가지표인 PR-AUC**를 최대화하는 지점으로 튜닝했습니다.

여기에 **규칙 엔진**을 병행합니다. 금액·시간·빈도·기기 변경 같은 10가지 규칙을 평가해서, **ML 판단과 규칙 판단 중 더 강한 쪽을 최종 액션으로 채택**합니다. REVIEW 이상이면 **Step-up Auth**가 자동 트리거되어 FIDO2 패스키 또는 TOTP 재인증을 요구합니다.

오른쪽 모델 구성을 보시면 세 모델을 비교 구현했습니다.
- **Isolation Forest 비지도 모델** — 본 적 없는 이상치 탐지,
- **부스팅 트리 지도 모델(XGBoost)** — 학습된 사기 패턴 분류,
- 그리고 **IF + 부스팅 하이브리드** — 두 점수를 0.7/0.3 가중평균으로 결합합니다.

세 모델은 **5-fold 교차검증**으로 비교했고, 가중치는 휴리스틱이라 향후 자동 튜닝이 후속 작업입니다.

## 🎯 슬라이드 7 — 부가 기능 `[6:20 ~ 7:40]` ⏱ **1분 20초**

부가 기능 여섯 가지입니다.

**XAI**는 SHAP으로 **피처별 기여도를 분해**해 상위 3개 피처를 Reason Code로 변환합니다. 결과는 "심야 지출 비중이 평소 대비 3배 증가" 같은 한국어 문장으로 사용자에게 전달됩니다.

**FIDO 인증**은 단순 패스워드 방식의 한계를 보완하기 위해 도입했습니다. **TOTP(OTP 앱)와 FIDO2 패스키** 두 방식을 병행 지원하며, REVIEW 판정 시 Step-up Auth로 자동 트리거됩니다.

**감정 기반 분석**은 소비 직후 사용자가 입력한 감정 태그와 지출 내역을 상관분석해 **충동 소비 패턴을 탐지**합니다.

**예산 전략 추천**은 소비 유형별 맞춤 예산을 설계하고 카테고리 한도와 절약 팁을 제안합니다. 예산 80% 도달 시 **WebSocket 실시간 알림**이 발송되며, 모바일 푸시(FCM)는 후속 연동 예정입니다.

**금융 교육 콘텐츠**는 분석 결과를 기반으로 맞춤형 투자·저축 가이드를 제공합니다.

마지막으로 **보안 대시보드**입니다. **SHA-256 해시 체인 기반 감사 로그**로 모든 거래 판정을 기록하고 — 단일 노드 구조라 분산 합의는 없지만 변조 탐지는 가능합니다 — MyData 동의 이력과 PID 가명처리 상태를 시각화합니다. 이 부분은 지도교수님의 요구사항을 반영한 결과물입니다.

## 💡 예상 질문 대비 답변

**Q1. 이게 진짜 사기 탐지인가요? 그냥 이상 거래 탐지 아닌가요?**
> 정직하게 답변하면, 현재 학습 데이터(Kaggle 카드결제 공개셋)와 룰 엔진은 **카드 결제 이상 거래 스크리닝** 단계입니다. 보이스피싱·머니뮬·계정탈취 같은 송금 사기 도메인 확장은 후속 계획에 PaySim 데이터셋 교체와 도메인 특화 룰 추가로 정리되어 있습니다. 현재 시연 가능한 건 **위험 점수 → Step-up 인증 → 해시 체인 감사** 엔드투엔드 보안 파이프라인입니다.

**Q2. 왜 Isolation Forest를 선택했나요?**
> 사기 라벨은 극단적으로 불균형(전체의 0.17% 수준)이라 지도 학습 단독으론 한계가 있습니다. **라벨 없이 "평소와 다른 패턴"을 탐지하는 비지도 학습**이 1차 스크리닝에 적합하고, 부스팅 트리(XGBoost)와 0.7/0.3 가중평균으로 결합해 학습된 패턴까지 같이 잡습니다.

**Q3. fraud-service를 왜 분리했나요?**
> 거래 리스크 모델은 **업데이트 주기와 트래픽 특성이 메인 서비스와 다릅니다.** 독립 배포해야 모델 교체·스케일아웃·장애 격리가 가능합니다. HTTP REST로 통신하며 환경변수로 URL을 주입해 배포 유연성을 확보했습니다.

**Q4. 블록체인이라고 하셨는데 분산 노드가 있나요?**
> 엄밀히는 비트코인의 **데이터 구조(SHA-256 해시 체인 + 머클 리프)** 만 차용한 단일 노드 구조입니다. 분산 합의·P2P가 없어 변조 *방지*는 못 하지만 **변조 *탐지*는 보장**합니다. 슬라이드와 멘트에서도 "해시 체인 기반 감사 로그"로 표현해 과장을 피했고, 운영급 분산 노드는 후속 작업입니다.

**Q5. 실제 사용자 데이터는 어떻게 확보하나요?**
> 현재는 Kaggle·IEEE-CIS 공개 데이터셋과 데모 시드 데이터로 학습하고 있습니다. 후속 연구 방향의 **MyData 테스트베드 연동**이 이 부분을 해결합니다.

**Q6. 개인정보 보호는 어떻게 하나요?**
> PID 가명처리로 원본 user_id를 해시화하고, 속성 기반 접근 제어(ABAC/ABE)로 열람 권한을 제한합니다. ABE는 charm-crypto 대신 HMAC + AES-GCM 경량 구현이며 운영 도입 시 교체 가능하게 인터페이스가 분리돼 있습니다.

**Q7. 6월 캡스톤 종료 시점에 무엇을 보여줄 수 있나요?**
> 세 가지로 정리했습니다 — ① 4가지 사기 시나리오 검출률 표, ② Docker Compose 단일 명령으로 전체 스택 시연, ③ Vercel/Railway 데모 배포 URL. 실 사용자 운영이 아니라 **시연으로 확인 가능한 범위**로 한정했습니다.
