# #4 PayWise 보안 대시보드 — 블록체인 감사 로그부터 ABAC·MyData·PID까지

## ① 개요

PayWise의 보안 대시보드는 단순한 "설정 페이지"가 아니다. 거래 한 건이 처리될 때마다 감사 로그가 SHA-256 해시 체인으로 묶이고, 접근 권한은 속성 기반(ABAC) 정책으로 세밀하게 제어되며, 사용자의 실제 ID는 주기적으로 교체되는 가명(PID)으로 대체된다. 이 모든 레이어를 단일 `/v1/security` 라우터 아래에 묶어 SRS 1·2·3·5·6·7·8·10 준수를 한곳에서 시연할 수 있도록 설계한 것이 이 기능의 핵심이다.

> **구현 실태**: 이 라우터의 `/audit/*`, `/abac/evaluate`, `/protocols/*`, `/mydata/*`, `/privacy/pid/*` 는 **fraud-service의 실제 구현(blockchain_audit, abac_engine, abe_engine)과 분리된 backend 측 자체 인메모리 시뮬레이션**이다. 예: `_AUDIT_CHAIN: list[dict]` ([routes_security_dashboard.py:26](backend/app/api/routes_security_dashboard.py:26)) 는 fraud-service의 `audit_chain.json` 과 별개의 로컬 미러이고, `/abac/evaluate` 는 fraud-service의 8개 룰 엔진(#15) 대신 5개 룰을 독립 구현한다. `/protocols/benchmark` 는 6개 보안 프로토콜의 실제 구현이 아니라 **SHA-256 1000회 latency 측정**으로 그래프를 채운다 ([routes_security_dashboard.py:182-186](backend/app/api/routes_security_dashboard.py:182)). 즉, "통합 대시보드"라기보다 **시연용 독립 데모**에 가까우며, 실제 fraud-service의 SRS 준수 증거를 그대로 노출하지는 않는다.

## ② 시스템 구성

```
┌─────────────────── Frontend (Next.js) ──────────────────────┐
│  /security            메인 탭 (보안 점수·TOTP·FIDO2·이벤트)   │
│  /security/blockchain 블록체인 감사 뷰어                      │
│  /security/protocols  프로토콜 카드 + ABAC 테스트 폼          │
│  /security/mydata     동의 목록 + PID 관리                    │
└─────────────────────────┬───────────────────────────────────┘
                          │ REST (Bearer JWT)
┌─────────────────── Backend (FastAPI) ───────────────────────┐
│  routes_security_dashboard.py  ← 이번 글의 대상              │
│  ├── /audit/*          인메모리 SHA-256 감사 체인             │
│  ├── /abac/evaluate    속성 기반 접근 제어 시뮬레이터          │
│  ├── /protocols/*      6개 SRS 프로토콜 벤치마크              │
│  ├── /mydata/*         금융 데이터 동의 레지스트리             │
│  └── /privacy/pid/*    가명 ID 생성·조회                     │
└─────────────────────────────────────────────────────────────┘
```

- **`_AUDIT_CHAIN`**: 프로세스 수명 동안 유지되는 인메모리 리스트. 각 블록이 이전 블록의 `block_hash`를 `prev_hash`로 포함한다.
- **`_MYDATA_CONSENTS` / `_PID_REGISTRY`**: 동의·PID도 인메모리 딕셔너리. 재시작 시 초기화되는 프로토타입 한계가 있다.
- **외부 의존 없음**: fraud-service나 별도 블록체인 노드 없이 백엔드 단독으로 동작한다.

## ③ 동작 흐름

거래 처리 후 감사 로그가 쌓이고, 대시보드에서 무결성을 검증하는 주요 흐름을 따라간다.

```
1. fraud-service(또는 테스트 클라이언트)
   POST /v1/security/audit/log  { transaction_id, user_id, action, score, amount }
        │
2. routes_security_dashboard.py: log_audit_entry()
   ├── 체인이 비어 있으면 prev_hash = "0"*64 (제네시스 블록)
   ├── 그렇지 않으면 prev_hash = _AUDIT_CHAIN[-1]["block_hash"]
   └── SHA-256(ts + entry + prev_hash) → block_hash 계산, 리스트에 append
        │
3. 응답: { status: "logged", index, hash }

4. 사용자가 /security/blockchain 페이지 진입
   GET /v1/security/audit/chain?limit=50
   → reversed(_AUDIT_CHAIN[-50:])  # 최신 블록이 상단에 표시
        │
5. FE: 블록 카드 렌더링
   action("PASS"/"REVIEW"/"BLOCK") → 색상 코드 → 좌측 border

6. "Verify Chain Integrity" 클릭
   GET /v1/security/audit/verify
   ├── 각 블록의 prev_hash == 이전 블록의 block_hash 비교
   └── 어긋나면 { valid: false, error: "Block N: prev_hash broken" }

7. ABAC 평가 (프로토콜 페이지)
   POST /v1/security/abac/evaluate  { user_role, clearance, location, ... }
   → 5가지 규칙 순차 평가 → { allowed, masked_fields, rules_applied }

8. PID 생성 (MyData 페이지)
   POST /v1/security/privacy/pid/generate  { user_id }
   → SHA-256(PID:<user_id>:<ts>:<nonce>) → 16자 가명
```

### 4-1. SHA-256 해시 체인 블록 생성

```python
# routes_security_dashboard.py:42-54
prev_hash = _AUDIT_CHAIN[-1]["block_hash"] if _AUDIT_CHAIN else "0" * 64
block = {
    "index": len(_AUDIT_CHAIN),
    "timestamp": ts,
    **entry.model_dump(),
    "prev_hash": prev_hash,
    "block_hash": hashlib.sha256(
        json.dumps({"ts": ts, "data": entry.model_dump(), "prev": prev_hash},
                   sort_keys=True).encode()

}
_AUDIT_CHAIN.append(block)
```

### 4-3. ABAC 5-rule 평가 엔진

```python
# routes_security_dashboard.py:113-162
clearance_map = {"LOW": 1, "MEDIUM": 2, "HIGH": 3, "TOP_SECRET": 4}
user_cl = clearance_map.get(req.clearance, 1)
res_cl  = clearance_map.get(req.resource_sensitivity, 1)

# Rule 1: 보안 등급
if user_cl < res_cl:
    allowed = False; rules_applied.append("CLEARANCE_LEVEL")

# Rule 2: HIGH 이상 리소스 → MFA 필수
if allowed and not req.mfa_verified and res_cl >= 3:
    allowed = False; rules_applied.append("MFA_REQUIRED")

# Rule 3: 외부에서 TOP_SECRET 접근 차단
if allowed and req.location == "external" and res_cl >= 4:
    allowed = False; rules_applied.append("LOCATION_RESTRICTION")
elif allowed and req.location == "external" and res_cl >= 3:
    masked_fields.extend(["user_id", "account_number", "phone"])
    rules_applied.append("LOCATION_MASK")

# Rule 4: viewer 역할 → PII 마스킹
if allowed and req.user_role == "viewer":
    masked_fields.extend(["user_id", "email", "phone", "ip"])
    rules_applied.append("VIEWER_PII_MASK")

# Rule 5: 모바일/태블릿 + HIGH → 금액·점수 마스킹
if allowed and req.device_type in ("mobile", "tablet") and res_cl >= 3:
    masked_fields.extend(["amount", "score"])
    rules_applied.append("DEVICE_MASK")

return {
    "allowed": allowed,
    "masked_fields": list(set(masked_fields)),   # 중복 제거
    "fgac_granularity": len(rules_applied),       # 적용된 규칙 수
}
```

[`routes_security_dashboard.py:113`](../../backend/app/api/routes_security_dashboard.py:113) — 등급을 숫자로 매핑해 `<` 비교 한 줄로 clearance 검증을 끝낸다.  
[`routes_security_dashboard.py:159`](../../backend/app/api/routes_security_dashboard.py:159) — `list(set(masked_fields))` 로 Rule 3·4가 모두 `user_id` 를 추가할 때 중복을 제거한다.  
[`routes_security_dashboard.py:161`](../../backend/app/api/routes_security_dashboard.py:161) — `fgac_granularity` 는 적용된 규칙 수로, FE에서 세밀도 지표로 표시한다.

### 4-4. 프로토콜 벤치마크 — SHA-256으로 지연시간 측정

```python
# routes_security_dashboard.py:173-193
for name, ops in [
    ("AACE (SRS 2)", 3),
    ("CP-ABE+BLE (SRS 5)", 4),
    ("ZeroTrust (SRS 6)", 2),
    ("OEEP-ABE (SRS 7)", 3),
    ("EABEHP (SRS 8)", 3),
    ("Encra AES+IBE (SRS 10)", 2),
]:
    n_iters = 1000
    t0 = time.perf_counter()
    for i in range(n_iters):
        _h.sha256(f"{name}:{i}".encode()).hexdigest()
    elapsed_ms = (time.perf_counter() - t0) * 1000
    avg_ms = elapsed_ms / n_iters
    protocols[name] = {
        "avg_latency_ms": round(avg_ms, 4),
        "ops_per_sec": round(n_iters / (elapsed_ms / 1000), 0),
        "phases": ops,
    }
```

[`routes_security_dashboard.py:184`](../../backend/app/api/routes_security_dashboard.py:184) — 실제 ABE·IBE 라이브러리 대신 `sha256`으로 CPU 부하를 흉내낸다. 진짜 암호 연산 비용과는 다르지만, 파이프라인 단계 수(`phases`)가 SRS별 복잡도를 간접적으로 표현한다. 미구현 항목임을 명시.

## ⑤ 설계 포인트 / 트러블슈팅 거리

- **인메모리 저장의 트레이드오프**: `_AUDIT_CHAIN`, `_MYDATA_CONSENTS`, `_PID_REGISTRY` 모두 프로세스 메모리에만 산다. 서버 재시작 한 번에 전체 감사 이력이 사라진다. 프로토타입으로는 충분하지만, 프로덕션에서는 PostgreSQL(감사 체인)·Redis(PID 캐시)로 외부화해야 한다. (✅ ROADMAP W3-#1 — `AuditChainEntry` 테이블 + `routes_security_dashboard` log/chain/verify/search 엔드포인트가 PG로 전환. block_index DESC 인덱스로 조회 O(log N))

- **벤치마크가 SHA-256 속도를 측정한다**: `/protocols/benchmark` 는 실제 CP-ABE·IBE 연산 대신 `sha256` 루프를 돌린다. 따라서 모든 프로토콜이 비슷한 지연시간으로 나타난다. "프로토콜 단계 수(`phases`)로 복잡도 차이를 간접 표현한다"는 주석 수준의 시뮬레이션이다.

- **ABAC 규칙의 단락 평가(short-circuit)**: `allowed = False` 가 된 뒤에도 마스킹 규칙(Rule 4·5)은 `if allowed and ...` 조건으로 건너뛴다. 접근이 거부된 상황에서 마스킹 필드를 계산할 필요가 없어 규칙이 누적되지 않는다. 다만 Rule 3에서 `elif`로 마스킹을 추가하는 경로는 `allowed`가 `True`일 때만 진입하므로 논리적으로는 일관되다.

- **MyData 철회 시 소유권 미검증**: [`routes_security_dashboard.py:293`](../../backend/app/api/routes_security_dashboard.py:293) 주석에 명시되어 있듯, `/mydata/revoke/{consent_id}` 는 JWT에서 `user_id`를 추출해 소유권을 확인하지 않는다. `consent_id`만 알면 누구든 철회가 가능하므로, 프로덕션에서는 `get_current_user` 의존성 주입과 소유권 검증이 필수다.

- **PID 로테이션 알림 없음**: FE의 MyData 페이지는 `needs_rotation` 플래그를 받아 "Rotate PID Now" 버튼을 표시하지만, 백엔드가 자동 로테이션을 트리거하거나 이메일·푸시 알림을 보내지는 않는다. 90일 뒤 사용자가 페이지를 열지 않으면 PID가 만료된 채로 방치된다.

### 예상 질문 & 답변 (발표 Q&A 대비)

**Q1. backend의 보안 대시보드가 fraud-service의 실제 구현과 분리된 이유는?**
> 정직하게 말하면 **시연 편의 + 시뮬레이션**. fraud-service의 `audit_chain.json`·`abac_engine`·`abe_engine`은 운영급이고, backend의 `/v1/security`는 그걸 거울처럼 보여주는 통합 데모 라우터. 두 레이어 통합은 후속 작업이며, 발표에선 이 차이를 명시적으로 설명할 예정.

**Q2. ABAC 룰이 fraud-service는 8개, backend는 5개로 다른 이유?**
> backend는 시연용으로 핵심 룰만 골라 자체 구현, fraud-service가 운영 정본. 정책 일관성을 위해 fraud-service 룰을 단일 소스로 두고 backend가 호출만 하는 구조로 통합 예정.

**Q3. `/protocols/benchmark`가 SHA-256 1000회 측정으로 끝난다는 게 무슨 뜻?**
> 6개 SRS 보안 프로토콜의 실제 구현이 아니라 "비슷한 비용의 연산"을 1000회 반복한 latency 측정. 시연 그래프를 채우기 위한 placeholder. 운영 측정은 fraud-service의 실제 호출 경로 instrumentation으로 후속.

**Q4. PID(가명 ID) 로테이션은 자동화돼 있나요?**
> 현재는 사용자가 페이지에서 "Rotate PID Now" 버튼을 누르는 수동 방식. 90일 자동 로테이션 + 알림은 ⑤절에서 후속 작업으로 정리.

**Q5. MyData 동의가 실제 금융결제원 테스트베드와 연동되나요?**
> 아직 안 됨. 현재는 PayWise 자체 동의 레지스트리. 발표 슬라이드 8의 "향후 계획"에 MyData 테스트베드 실 연동을 명시했고, Rate Limiting·Circuit Breaker와 함께 후속 진행.

## ⑥ 한 줄 정리

보안 대시보드는 SHA-256 해시 체인 감사 로그·5-rule ABAC·PID 가명화·MyData 동의를 단일 라우터(`/v1/security`)로 묶어 SRS 1·2·3·5·6·7·8·10 요구사항을 한 화면에서 시연할 수 있게 구성한 계층적 보안 쇼케이스다.
