# #20 모델 학습 파이프라인 — 두 개의 분리된 학습 경로와 그 사이 단절

## ① 개요

PayWise에는 **두 개의 ML 학습 파이프라인이 서로 단절된 채 공존**한다. 하나는 backend의 `/v1/ml/train` 엔드포인트가 트리거하는 **인-프로세스 학습**으로, PostgreSQL의 거래 데이터를 읽어 K-Means/IsolationForest/XGBoost/LSTM 4개 모델을 모듈 레벨 싱글턴 객체에 메모리로 적합시킨다. 다른 하나는 `fds-research` 폴더의 오프라인 학습 스크립트 (`train_export_rf.py`)가 만들어낸 **joblib 번들**을 fraud-service가 디스크에서 읽어 사용하는 **번들 배포** 경로다. 두 경로는 동일한 fraud 도메인을 다루지만 코드·데이터·모델이 모두 분리되어 있고, 서로의 결과를 공유하지 않는다.

> **구현 실태**: backend 측 `train_all()` 은 학습 결과를 **디스크에 영속화하지 않는다**. clustering.py / classifier.py / forecasting.py / anomaly.py 어디에도 `joblib.dump` 호출이 없다 ([anomaly.py 주석](backend/app/ml/anomaly.py:7)에는 "model_bundle_open_full.joblib에 포함된" 이라는 표현이 있어 외부 번들 사용을 가정하지만 실제 학습-저장 경로는 없음). 즉 서버를 재시작하면 학습된 가중치가 모두 휘발되어 다음 예측 호출은 fallback/콜드 스타트로 떨어진다. 또한 fds-research → fraud-service 배포 경로는 **수동**이다 — 개발자가 `train_export_rf.py` 를 돌려 `outputs/fds/model_bundle_open_full.joblib` 을 만들고, docker-compose가 그 디렉터리를 read-only 볼륨으로 마운트해야 fraud-service가 읽는다. CI/CD 파이프라인은 없다.

## ② 시스템 구성

```
[경로 ① — backend 인-프로세스 학습]

  POST /v1/ml/train
      │
      ▼
  trainer.train_all(session)
      ├─ _train_clustering()  → cluster_model.fit(profiles)        (KMeans, sklearn)
      ├─ _train_anomaly()     → anomaly_detector.fit(transactions) (IsolationForest)
      ├─ _train_classifier()  → overspend_classifier.fit(X, y)     (XGBoost)
      └─ _train_forecaster()  → forecaster.train(monthly_totals)   (LSTM, PyTorch)
            │
            └─ 모두 모듈 레벨 싱글턴에 in-memory 저장
                  ↓
            서버 재시작 시 휘발

[경로 ② — fds-research → fraud-service 배포]

  개발자 머신:
    $ python fds-research/scripts/fds/train_export_rf.py
        --schema schemas/fds/schema_v1_*.yaml
        --train-csv data/...csv
        --out outputs/fds/model_bundle_open_full.joblib
            │
            ▼
    joblib(dict) = {pipeline, schema_raw, feature_names, clf_step_name}
            │
            │  rsync / git commit + redeploy
            ▼
    docker-compose.yml:
      volumes:
        - ./fds-research/outputs/fds:/capstone:ro

  fraud-service 컨테이너:
    MODEL_PATH=/capstone/model_bundle_open_full.joblib
            │
            ▼
    매 호출마다:
      load_model_bundle() → joblib.load(path) → 캐시 없음
```

| 파일 | 역할 |
|---|---|
| `backend/app/api/routes_train.py` | `/v1/ml/train` 트리거, `/v1/ml/status` 적합 여부 조회 |
| `backend/app/ml/trainer.py` | 4개 trainer 함수, PostgreSQL → in-memory 모델 |
| `fds-research/scripts/fds/train_export_rf.py` | RF 학습 + joblib 번들 export |
| `fraud-service/app/scoring/model_loader.py` | joblib 로드 (캐시 없음) |
| `docker-compose.yml:44-45` | `outputs/fds` → `/capstone` 볼륨 마운트 |

## ③ 동작 흐름

```
[경로 ① 흐름]
1. 운영자가 POST /v1/ml/train 호출
2. trigger_training(session) → train_all(session)
3. 4개 trainer 가 순차 실행
   3a. _train_clustering: GROUP BY user/category → 비율 벡터 → cluster_model.fit()
   3b. _train_anomaly: ORDER BY random() LIMIT 10000 → IF.fit()
   3c. _train_classifier: 5000건 샘플링 + 7차원 피처 → XGBoost.fit()
       레이블 = (amount > 사용자 평균 * 2) ? 1 : 0
   3d. _train_forecaster: GROUP BY 월 → LSTM.train()
4. 각 단계 결과를 dict로 합쳐 응답 반환
5. 모델 객체는 모듈 import 시점부터 살아있던 싱글턴에 in-place 적합
6. 다음 예측 호출은 곧바로 새 가중치 사용
7. ⚠️ 서버 재시작 → 가중치 휘발 → 누군가 다시 /v1/ml/train 호출해야 함

[경로 ② 흐름]
1. 개발자가 로컬에서 train_export_rf.py 실행 (수동, 비정기적)
2. SMOTE 오버샘플링 + RF 200 estimators 학습
3. joblib.dump 로 model_bundle_open_full.joblib 저장
4. git commit & push (또는 별도 산출물 저장소)
5. CI/CD 없음 → 운영 서버 재배포 시점이 모델 갱신 시점
6. 컨테이너 부팅 → MODEL_PATH 환경변수 확인
7. fraud-service /v1/score 요청마다 load_model_bundle() → joblib.load()
   ⚠️ 모듈 레벨 캐싱이 없음. 요청마다 재역직렬화
```

## ④ 핵심 코드 분석

### 4-1. train_all — 4개 모델 순차 학습

```python
# trainer.py:31-41
async def train_all(session: AsyncSession) -> dict:
    results = {}
    results["clustering"] = await _train_clustering(session)
    results["anomaly"]    = await _train_anomaly(session)
    results["classifier"] = await _train_classifier(session)
    results["forecaster"] = await _train_forecaster(session)
    logger.info("ML training complete: %s", results)
    return results
```

[trainer.py:31](backend/app/ml/trainer.py:31)

**HTTP 타임아웃 위험**: `train_all`은 한 HTTP 요청 안에서 4개 모델 학습을 모두 끝낸다. K-Means는 비교적 빠르지만, XGBoost 5000샘플 학습 + LSTM 시계열 학습은 수십 초~수 분 걸릴 수 있다. FastAPI 기본 ASGI 타임아웃 또는 nginx/ALB의 60초 타임아웃에 걸리면 클라이언트는 504를 받지만 학습은 백그라운드에서 계속 진행된다 (또는 끊긴다). 표준 대응은 ① Celery/Arq로 큐잉, ② BackgroundTasks로 즉시 응답 후 비동기 실행, ③ 학습 진행 상태를 별도 DB 테이블에 기록하고 폴링 API 제공. 현재는 셋 다 없다.

**부분 실패 처리 없음**: `_train_classifier`가 예외를 던지면 `_train_forecaster`는 실행되지 않고 클라이언트는 500을 받는다. 이미 적합된 clustering/anomaly는 살아있지만 응답에는 실패만 보고된다. 부분 진행 상태를 상태 테이블에 기록하거나 try/except로 각 단계를 감싸 partial success를 반환해야 한다. (✅ ROADMAP W6-#7 — `TrainingRun` 테이블 + `app/services/training_progress.py` (begin_run/complete_run/fail_run/recent_runs), per-model 결과 JSON 직렬화, status = success/partial/failed 자동 분류)

### 4-2. 분류기 레이블링 — 통계적 정의 self-fulfilling prophecy

```python
# trainer.py:197-198
X_list.append(features)
# 레이블: 평균의 2배 이상이면 과소비
y_list.append(1 if tx.amount > avg_amt * 2 else 0)
```

[trainer.py:197](backend/app/ml/trainer.py:197)

레이블이 "사용자 평균의 2배 초과"라는 단순 통계적 정의다. 진짜 과소비/사기 라벨이 아니다. 모델이 학습하는 함수는 결국 "amount / avg_amt > 2 인지 예측" 인데, 7차원 피처 중 두 번째 피처가 정확히 `amount / avg_amt` 다. **모델은 자기 레이블 룰을 그대로 학습**할 뿐이며, 추가 정보를 거의 추출하지 못한다. ROC-AUC가 0.99 가까이 나와도 그건 누수(label leakage)에 가까운 자명한 결과다. 실제 chargeback 라벨, 사용자 신고 라벨, 또는 도메인 전문가 라벨링이 없다면 이 분류기는 통계적 outlier 탐지의 우회 구현일 뿐이다.

### 4-3. 피처 placeholder

```python
# trainer.py:187-195
features = [
    tx.amount,
    tx.amount / avg_amt if avg_amt > 0 else 0,
    cat_pct,
    hour,
    1 if tx.is_domestic else 0,
    1.0,  # monthly_total_ratio (simplified)
    10,   # tx_frequency placeholder
]
```

[trainer.py:187](backend/app/ml/trainer.py:187)

7차원 중 마지막 두 차원이 **모든 샘플에 동일한 상수(1.0, 10)** 다. 그 두 차원은 학습 데이터에서 분산이 0이라 정보 이득(information gain)이 0이다. XGBoost는 자동으로 그 피처를 사용하지 않게 되지만, **추론 시점에도 그 두 자리에 같은 상수를 채워야 형상이 맞는다**. 즉 "추후 이 자리에 진짜 피처를 넣겠다"는 의도가 보이지만 현재는 더미 슬롯이다. 차원 수 자체를 줄여 5차원으로 학습하면 모델 크기·추론 속도가 모두 개선된다.

### 4-4. ORDER BY random() — 풀 테이블 스캔

```python
# trainer.py:91-100, 163-173
.order_by(func.random())
.limit(10000)
```

[trainer.py:98](backend/app/ml/trainer.py:98)

PostgreSQL의 `ORDER BY random()`은 **모든 행에 random 값을 계산하고 정렬**하므로 O(N log N) 시간 + 풀 테이블 스캔이다. 거래 테이블이 1M 행을 넘으면 트레이닝 한 번에 분 단위가 걸린다. 더 효율적인 대안:
- `TABLESAMPLE BERNOULLI (1)` 로 1% 무작위 추출 → O(N)
- 사기 라벨이 있다면 stratified sampling 으로 양/음성 균형 보장

(✅ ROADMAP W6-#8 — `trainer._random_sample_clause(table, target_n, total_estimate)` 가 PostgreSQL 환경에서 BERNOULLI 절 생성, target/total*100*2.5 (0.1~50% 클립) 안전 마진, ML_TABLESAMPLE_DISABLE env 폴백, 비-PG/SQLite 자동 미적용)

### 4-5. fraud-service 측 — 매 요청마다 joblib 재역직렬화

```python
# model_loader.py:26-33
def load_model_bundle() -> dict[str, Any] | None:
    path = resolve_model_path()
    if path is None:
        return None
    try:
        return joblib.load(path)
    except Exception:
        return None
```

[model_loader.py:26](fraud-service/app/scoring/model_loader.py:26)

**모듈 레벨 캐싱이 없다.** `routes_score.py:46`과 `:85`에서 두 번 호출되며, 각 요청마다 디스크에서 joblib 파일을 읽고 압축 해제하고 객체 그래프를 복원한다. RF 200 estimators 번들이면 보통 10-50MB → 디스크 IO + 역직렬화로 요청당 50-200ms가 추가될 수 있다. `@functools.lru_cache(maxsize=1)` 또는 모듈 import 시점에 한 번만 로드하면 즉시 해결된다. 현재 구조에서 fraud-service의 P50 latency가 의외로 높은 진짜 원인일 가능성이 크다.

# trainer.py:78-79

## ⑤ 설계 포인트 / 트러블슈팅 거리

- **두 ML 시스템의 책임 경계가 모호하다**: backend 측은 사용자 분석(소비 유형·과소비 분류·예측), fraud-service 측은 거래 사기 점수로 분리되어 있지만, 둘 다 IsolationForest/XGBoost를 쓴다. 동일한 모델 클래스를 두 곳에서 다른 데이터로 학습한다 — 코드 재사용 효율이 떨어지고, 한쪽 모델 개선이 다른 쪽에 자동 반영되지 않는다. 공통 학습 라이브러리(`paywise-ml`)를 추출하고 양쪽이 import하는 구조가 더 건전하다.

- **on-demand 학습 + 비영속 = 운영 사고 위험**: backend는 `/v1/ml/train`을 누군가 명시적으로 호출해야만 모델이 학습된다. 컨테이너 재시작이 발생하면 (롤링 업데이트, OOM kill, 노드 교체) 모든 학습 결과가 사라지고, 다음 예측은 fallback 경로로 떨어진다. 운영자가 알아채지 못한 채 "모델 기반 예측"이 사실은 fallback인 상태가 며칠씩 지속될 수 있다. 학습 후 `joblib.dump` 로 디스크에 저장하고, 부팅 시 자동 로드하는 패턴이 표준이다. (✅ ROADMAP W6-#1 — `app/ml/persistence.py` cluster/anomaly/classifier (joblib) + forecaster (torch state_dict) dump_all/load_all, train_all(persist=True) 자동 dump, ML_BUNDLE_DIR env)

- **fds-research → fraud-service 배포가 git push 의존적**: joblib 파일을 git으로 관리한다는 가정이 위험하다. 모델 번들이 수십 MB면 git LFS가 없는 한 저장소가 비대해진다. 또한 학습 데이터·하이퍼파라미터·검증 메트릭이 함께 추적되지 않으면 어느 commit의 번들이 어떤 데이터에서 어떤 성능으로 학습되었는지 사후 추적이 불가능하다. MLflow 또는 DVC로 모델 버전 관리, S3/MinIO에 번들 저장, 부팅 시 다운로드하는 흐름이 필요하다.

- **A/B 테스트(#18)와의 연결도 미완**: `MODEL_B_PATH` 환경변수가 정의되어 있지만, 그것이 가리키는 신모델 번들을 만들기 위한 별도 학습 흐름은 명시되어 있지 않다. fds-research에서 `train_export_rf.py` 변형을 만들거나 하이퍼파라미터를 다르게 한 두 번째 번들을 별도 경로로 export 해야 한다. 현재는 #18 자체가 wiring되지 않은 상태라 이 갭이 드러나지 않을 뿐이다.

- **재학습 트리거 정책이 없다**: 모델 드리프트(distribution shift)를 감지해 자동 재학습을 트리거하는 로직이 없다. fds-research에 `ops_drift.py` 스크립트가 있긴 하지만, 그 결과가 backend의 `/v1/ml/train` 또는 fds-research의 export 흐름과 자동 연결되지 않는다. 시간 기반(매주 일요일 새벽), 데이터 기반(거래 N건 누적), 성능 기반(precision drop %p) 중 어느 하나라도 자동화 정책으로 명시되어야 한다.

(✅ ROADMAP W6-#2 — `model_loader.load_model_bundle` 에 `@functools.lru_cache(maxsize=1)` 적용 + `clear_model_cache()`/`model_cache_info()` 노출, 동일 경로 반복 로드 시 디스크 IO·역직렬화 제거)

### 예상 질문 & 답변 (발표 Q&A 대비)

**Q1. 학습 결과가 디스크에 저장 안 된다는 게 무슨 뜻?**
> backend `train_all()`은 모듈 싱글턴 메모리에만 가중치 적합. 재시작 시 휘발 → fallback. 발표에선 "현재 2-track 구조(요청 학습 + joblib 번들)"로 표현하고, persistence 추가가 후속 작업.

**Q2. fds-research → fraud-service 배포는 자동화돼 있나요?**
> 수동. 개발자가 `train_export_rf.py` 실행해 `model_bundle_open_full.joblib` 생성하고 docker-compose 볼륨 마운트로 fraud-service가 읽는 구조. CI/CD는 후속.
