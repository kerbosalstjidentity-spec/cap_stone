# #9 감정 기반 소비 분석 — 거래에 감정을 붙이면 무엇이 보이는가

---

## ① 개요

사람은 항상 이성적으로 소비하지 않는다. 스트레스를 받은 날 충동적으로 쇼핑하거나, 무료함에 배달 앱을 켜는 패턴은 지출 금액 데이터만으로는 포착할 수 없다. PayWise의 감정 기반 소비 분석은 사용자가 거래에 **감정 태그(happy / stressed / bored / reward / impulse / neutral)** 를 직접 기록하게 하고, 이 데이터를 집계해 "어떤 감정 상태일 때 어느 카테고리 지출이 평소 대비 얼마나 늘어나는지"를 정량화한다. 여기서 한 발 더 나아가, 현재 시간대와 최근 24시간 감정 이력을 조합해 **충동 소비 위험도**를 실시간으로 계산하고 임계값을 넘으면 즉시 알림을 발송한다.

> **알림 채널 실태**: "즉시 알림 발송"은 실제로 wiring되어 있다 — `routes_emotion.py:40` 의 `tag_emotion()` 가 `check_and_notify()`([emotion_engine.py:331](backend/app/services/emotion_engine.py:331))를 호출하고, 임계값 초과 시 `notification_service.create_and_push()` 로 이어진다. 다만 전송 채널은 **DB 저장 + Redis pub/sub + WebSocket** 까지이며 ([notification_service.py:138-139](backend/app/services/notification_service.py:138)), FCM/APNs 같은 모바일 푸시 백엔드는 연결되어 있지 않다. 즉 앱이 켜져 있고 WebSocket 세션이 살아있는 사용자만 즉시 받고, 백그라운드 사용자는 다음 접속 시 "안 읽은 알림" 으로 확인하는 구조다.

## ② 시스템 구성

```
[Client]
    │  POST /v1/emotion/tag  (감정 태깅)
    │  GET  /v1/emotion/impulse-risk/{user_id}
    │  GET  /v1/emotion/heatmap/{user_id}
    │  GET  /v1/emotion/insights/{user_id}
    ▼
[routes_emotion.py]  ← FastAPI 라우터
    │
    ▼
[emotion_engine.py]  ← 핵심 분석 로직
    ├─ upsert_emotion_tag()      : 태그 저장/갱신
    ├─ compute_correlation()     : 감정×카테고리 상관 집계
    ├─ compute_heatmap()         : 6×11 히트맵 정규화
    ├─ predict_impulse_risk()    : 시간대·감정 이력 기반 위험 점수
    ├─ get_insights()            : 배수 상위 조합 추출
    └─ check_and_notify()        : 임계값 초과 시 알림 연동
    │
    ├── [PostgreSQL]
    │     ├─ emotion_tags  (user_id, transaction_id, emotion, intensity, note)
    │     └─ transactions  (JOIN 대상 — amount, category, timestamp)
    │
    └── [notification_service.py]  ← 실시간 알림 (WebSocket + Redis Pub/Sub)
```

**핵심 테이블**: `emotion_tags`는 `(user_id, transaction_id)` 복합 유니크 인덱스를 가진다. 거래 하나에 감정은 하나만 기록되며, 재태깅 시 upsert로 덮어쓴다.

## ③ 동작 흐름

### A. 감정 태깅 → 즉시 위험 체크

```
1. 사용자가 거래 목록(GET /recent-transactions)에서 특정 거래를 선택
2. POST /v1/emotion/tag  {user_id, transaction_id, emotion, intensity(1-5), note}
3. upsert_emotion_tag() : emotion_tags 테이블에 INSERT 또는 UPDATE
4. session.commit() 후 check_and_notify() 비동기 호출
5. predict_impulse_risk() 가 위험 점수를 계산
6. risk_score >= EMOTION_RISK_THRESHOLD 이면 notification_service.create_and_push() 호출
7. WebSocket을 통해 클라이언트에 "충동 소비 주의" 알림 실시간 전달
```

### B. 히트맵·인사이트 조회

```
1. GET /v1/emotion/heatmap/{user_id}
2. compute_heatmap() → compute_correlation() 호출
3. DB에서 (emotion, category) 그룹별 AVG(amount), COUNT, SUM 집계
4. 전체 평균 대비 배수(multiplier) = emotion별 avg / overall_avg 계산
5. 6(감정)×11(카테고리) 행렬에 max_value 로 정규화(0~1)
6. 클라이언트에 rows 배열 반환 → 프론트에서 색상 강도로 시각화
```

## ④ 핵심 코드 분석

### 4-1. 감정 태그 Upsert

```python
# [emotion_engine.py](backend/app/services/emotion_engine.py:46-77)
async def upsert_emotion_tag(
    session: AsyncSession,
    user_id: str,
    transaction_id: str,
    emotion: str,
    intensity: int = 3,
    note: str = "",
) -> EmotionTag:
    stmt = select(EmotionTag).where(
        EmotionTag.user_id == user_id,
        EmotionTag.transaction_id == transaction_id,
    )
    result = await session.execute(stmt)
    tag = result.scalar_one_or_none()

    if tag:
        tag.emotion = emotion
        tag.intensity = intensity
        tag.note = note
    else:
        tag = EmotionTag(...)
        session.add(tag)

    await session.flush()
    return tag
```

- `scalar_one_or_none()` 로 기존 태그를 먼저 조회한 뒤 있으면 필드를 덮어쓴다.  
- DB 레벨의 `UNIQUE(user_id, transaction_id)` 제약과 맞물려 거래당 정확히 하나의 감정 기록이 보장된다.  
- `flush()`는 commit 없이 세션 내 변경을 DB에 반영해, 이후 `check_and_notify()`가 동일 트랜잭션 안에서 최신 상태를 읽을 수 있게 한다.

### 4-2. 감정×카테고리 상관 집계

```python
# [emotion_engine.py](backend/app/services/emotion_engine.py:118-153)
async def compute_correlation(session: AsyncSession, user_id: str) -> dict:
    stmt = (
        select(
            EmotionTag.emotion,
            Transaction.category,
            func.avg(Transaction.amount).label("avg_amount"),
            func.count().label("count"),
            func.sum(Transaction.amount).label("total"),
        )
        .join(Transaction, EmotionTag.transaction_id == Transaction.transaction_id)
        .where(EmotionTag.user_id == user_id)
        .group_by(EmotionTag.emotion, Transaction.category)
    )
    ...
    overall_avg = (await session.execute(overall_stmt)).scalar() or 1.0

    correlations = [
        {
            ...
            "multiplier": round(float(row.avg_amount) / float(overall_avg), 2),
        }
        for row in rows
    ]
```

- 집계 쿼리 하나로 `(emotion, category)` 조합별 평균·건수·합계를 한 번에 뽑는다.  
- `multiplier` = `(감정 상태에서 해당 카테고리 평균 지출)` ÷ `(전체 평균 지출)`. 1.0이 기준이며 2.0이면 "평소의 2배"를 의미한다.  
- `overall_avg or 1.0` 으로 0-division을 방어한다.

### 4-3. 히트맵 정규화

```python
# [emotion_engine.py](backend/app/services/emotion_engine.py:160-196)
async def compute_heatmap(session: AsyncSession, user_id: str) -> dict:
    corr = await compute_correlation(session, user_id)
    ...
    max_val = max(
        (item["avg_amount"] for item in corr["correlations"]),
        default=1.0,
    )

    rows = []
    for emotion in EMOTIONS:
        cells = []
        for cat in CATEGORIES:
            item = data.get(emotion, {}).get(cat, {})
            raw = item.get("avg_amount", 0.0)
            cells.append({
                "value": round(raw / max_val, 4) if max_val > 0 else 0.0,
                "raw_avg": raw,
                "count": item.get("count", 0),
            })
```

- `max_val`로 나눠 전체 셀을 `[0, 1]`로 정규화한다. 프론트는 이 값을 색상 강도에 직접 매핑할 수 있어 스케일 변환 로직이 클라이언트 측에 불필요하다.  
- 데이터가 없는 `(emotion, category)` 조합은 `raw_avg=0, count=0`으로 채워져 항상 `6×11` 완전 행렬이 반환된다.

### 4-4. 충동 소비 위험도 계산

```python
# [emotion_engine.py](backend/app/services/emotion_engine.py:203-284)
HOUR_RISK = {
    **{h: 0.2 for h in range(6, 11)},    # 아침 출근
    **{h: 0.1 for h in range(11, 17)},   # 낮
    **{h: 0.3 for h in range(17, 21)},   # 저녁 퇴근
    **{h: 0.4 for h in range(21, 24)},   # 밤
    **{h: 0.3 for h in range(0, 6)},     # 새벽
}

async def predict_impulse_risk(session: AsyncSession, user_id: str) -> dict:
    now = datetime.utcnow()
    hour = now.hour
    is_weekend = now.weekday() >= 5

    # 최근 24시간 감정 이력
    since = now - timedelta(hours=24)
    ...

    score = 0.0

    # 1. 시간대 위험
    hour_weight = HOUR_RISK.get(hour, 0.1)
    score += hour_weight

    # 2. 주말 보너스
    if is_weekend:
        score += WEEKEND_BONUS  # 0.1

    # 3. 최근 스트레스/충동 태그
    stress_tags = [t for t in recent_tags if t.emotion in ("stressed", "impulse")]
    if stress_tags:
        intensity_avg = sum(t.intensity for t in stress_tags) / len(stress_tags)
        stress_weight = min(0.3, len(stress_tags) * 0.08) * (intensity_avg / 5)
        score += stress_weight

    # 4. 저녁+스트레스 복합
    if hour >= 18 and stress_tags:
        score += 0.15

    score = min(score, 1.0)
```

요인별 가중치 요약:

| 요인 | 최대 기여 | 비고 |
|---|---|---|
| 시간대 (HOUR_RISK) | 0.4 | 밤(21~24시) 최고 |
| 주말 | 0.1 | 평일 대비 고정 추가 |
| 스트레스/충동 태그 | 0.3 | 건수×0.08×강도 비율, 상한 0.3 |
| 저녁+스트레스 복합 | 0.15 | 시간대와 태그 동시 충족 시 |
| **합계 상한** | **1.0** | `min(score, 1.0)` |

- `stress_weight = min(0.3, count × 0.08) × (intensity_avg / 5)` : 건수와 강도를 곱해 단순 카운팅보다 세밀한 위험 측정이 가능하다.  
- 저녁+스트레스 복합 가중치(`0.15`)는 두 요인이 동시에 성립할 때만 더해지는 독립 항으로, "퇴근 후 스트레스 폭식" 시나리오를 의도적으로 가중한다.

### 4-5. 위험도 임계값 초과 시 알림 발송

```python
# [emotion_engine.py](backend/app/services/emotion_engine.py:331-346)
async def check_and_notify(session: AsyncSession, user_id: str) -> None:
    try:
        risk = await predict_impulse_risk(session, user_id)
        if risk["risk_score"] >= settings.EMOTION_RISK_THRESHOLD:
            from app.services.notification_service import create_and_push
            await create_and_push(
                session=session,
                user_id=user_id,
                event_type="emotion_risk",
                title="충동 소비 주의",
                body=risk["warning_message"],
                metadata={"risk_score": risk["risk_score"], "risk_level": risk["risk_level"]},
            )
    except Exception as e:
        logger.warning("[Emotion] check_and_notify error: %s", e)
```

- `EMOTION_RISK_THRESHOLD`는 `settings`에서 가져와 배포 환경별로 조정 가능하다.  
- `import`를 함수 내부에 위치시켜 `notification_service`와의 순환 참조를 회피한다.  
- `try/except`로 알림 실패가 태깅 API 자체의 응답을 깨뜨리지 않도록 격리한다.

### 4-6. 감정 기반 인사이트 추출

```python
# [emotion_engine.py](backend/app/services/emotion_engine.py:291-324)
async def get_insights(session: AsyncSession, user_id: str) -> dict:
    corr = await compute_correlation(session, user_id)
    insights = []

    for item in sorted(corr["correlations"], key=lambda x: x["multiplier"], reverse=True):
        mult = item["multiplier"]
        if mult < 1.5:
            continue
        if mult >= 2.5:
            severity = "danger"
        elif mult >= 2.0:
            severity = "warning"
        else:
            severity = "info"

        text = (
            f"{item['emotion_kr']} 상태일 때 {item['category_kr']} 지출이 "
            f"평소 대비 {mult:.1f}배 증가하는 경향이 있습니다."
        )
        insights.append({...})

        if len(insights) >= 6:
            break
```

- `multiplier < 1.5` 는 필터링 — 의미 있는 이탈이라 보기 어려운 조합은 인사이트에 포함하지 않는다.  
- 상위 6개만 반환해 "너무 많은 경고"로 인한 피로도를 방지한다.  
- `severity` 3단계(`info / warning / danger`)는 UI 색상 코딩 기준으로 직접 사용된다.

## ⑤ 설계 포인트

- **감정 입력은 사용자가 직접**: 트랜잭션에서 감정을 자동 추론(NLP 등)하지 않는다. 정확성보다 "기록하는 행위 자체가 소비 반성을 유도한다"는 행동경제학적 설계 의도다. 단, 입력 빈도가 낮으면 상관 분석의 샘플 수가 부족해 multiplier 신뢰도가 낮아지는 문제가 있다.

- **충동 위험 점수는 룰 기반**: 시간대·주말·스트레스 태그 3개 요인의 선형 합산이다. 개인별 소비 패턴(예: 특정 사용자는 아침에 충동 지출이 많음)을 반영하지 못하는 것이 한계다. 향후 사용자별 `HOUR_RISK` 테이블로 개인화가 가능한 구조다.

- **히트맵 정규화 기준**: max 정규화는 한 셀이 극단적으로 큰 값을 가질 경우 나머지 셀이 0에 수렴해 색상 변별력이 사라지는 문제가 생길 수 있다. 분위수 정규화 또는 로그 스케일 적용이 UX 개선 여지로 남아 있다.

- **알림 실패 격리**: `check_and_notify()`의 예외를 `logger.warning`으로만 처리해 알림 장애가 태깅 API 응답에 영향을 주지 않는다. 다만 알림 누락이 무음으로 처리되므로, 중요한 위험 알림이 실제로 발송됐는지 확인하려면 별도 감사 로그가 필요하다.

- **순환 참조 방어**: `emotion_engine`이 `notification_service`를 지연 임포트(`import` inside function)로 참조한다. 두 모듈이 서로를 직접 참조하는 구조가 아님에도 방어적으로 적용돼 있는데, 의존성 방향을 단방향으로 유지하려면 `notification_service`를 인자로 주입받는 방식이 더 명확하다.

## ⑥ 한 줄 정리

거래에 감정 레이블을 붙이는 단순한 아이디어를, 상관 집계·히트맵·룰 기반 위험 점수·실시간 알림으로 이어지는 파이프라인으로 구체화한 기능이다.
