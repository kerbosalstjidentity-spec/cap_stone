# #10 소비 전략 추천 — 군집·분류·규칙을 묶어 사람에게 말 걸기

---

## ① 개요

소비 패턴 분석이 "지금 어떻게 쓰고 있는가"를 보여준다면, 소비 전략 추천은 "앞으로 어떻게 써야 하는가"를 제안한다. PayWise는 앞서 구현된 K-Means 군집화(소비 유형 분류)와 XGBoost 분류기(과소비 위험도)의 결과를 소비 프로필과 연결해, 카테고리 편중·임계값 초과·예산 초과를 감지하는 **규칙 기반 추천**으로 마무리한다. 세 레이어가 순차 실행되어 하나의 `StrategyRecommendation` 응답으로 합쳐지며, 프론트엔드는 군집 라벨·위험도 게이지·절약 가능 금액을 카드 UI로 시각화한다.

---

## ② 시스템 구성

```
[Client — strategy/page.tsx]
    │  GET /api/v1/strategy/recommend/{userId}
    │  GET /api/v1/analysis/compare/{userId}   (전월 비교)
    ▼
[routes_strategy.py]  ← FastAPI 라우터
    │
    ├─ profile_store.get_profile()         ← InMemorySpendProfileStore
    │       └─ _UserStore (카테고리 집계, 시간대 집계)
    │
    ├─ cluster_model.predict(cat_pcts)     ← K-Means 군집화 (ml/clustering.py)
    │       └─ 군집 라벨: 절약형/균형형/소비형/투자형
    │
    ├─ overspend_classifier.predict()      ← XGBoost 분류기 (ml/classifier.py)
    │       └─ 과소비 확률 0~1
    │
    └─ 규칙 기반 추천 생성 (5가지 조건)
            └─ StrategyRecommendation 응답

[_budgets: dict]  ← 인메모리 예산 저장소
    │  POST /v1/strategy/budget/{user_id}
    │  GET  /v1/strategy/budget/{user_id}
    └─ GET  /v1/strategy/savings/{user_id}
```

**소비 프로필 저장소**는 거래를 수신할 때마다 카테고리별 집계(`category_totals`, `category_counts`)와 시간대별 카운트(`hour_counts`)를 실시간으로 갱신하는 싱글턴 인메모리 객체다. DB 조회 없이 `O(1)`로 프로필을 반환할 수 있어 추천 API 응답 속도를 빠르게 유지한다.

---

## ③ 동작 흐름

```
1. GET /v1/strategy/recommend/{user_id} 요청 수신
2. profile_store.get_profile(user_id) → SpendProfile 조회
   - 없으면 404 반환
3. 카테고리별 지출 비율 벡터(cat_pcts) 구성
4. cluster_model.predict(cat_pcts) → cluster_label ("절약형" 등)
5. overspend_classifier.build_features(...) → 7개 특성 벡터 생성
6. overspend_classifier.predict(features) → risk_score (0~1)
7. 규칙 5종 순차 적용 → recommendations[], saving_opportunities[] 누적
8. StrategyRecommendation 응답 직렬화 → 클라이언트 반환
9. 프론트엔드: cluster_label 배지 + risk_score 게이지 + 절약 카드 렌더링
```

## ④ 핵심 코드 분석

### 4-1. 소비 프로필 실시간 집계

```python
# [spend_profile.py](backend/app/services/spend_profile.py:28-34)
def add(self, tx: TransactionIngest) -> None:
    self.transactions.append(tx)
    self.category_totals[tx.category] += tx.amount
    self.category_counts[tx.category] += 1
    self.hour_counts[tx.timestamp.hour] += 1
    if tx.amount > self.max_amount:
        self.max_amount = tx.amount
```

거래가 들어올 때마다 카테고리 합계·건수, 시간대 빈도, 최대 금액을 즉시 갱신한다. 덕분에 `get_profile()` 호출 시 추가적인 집계 쿼리가 필요 없고, `defaultdict(float)` 덕분에 첫 등장 카테고리도 초기화 없이 처리된다.

### 4-2. 프로필 스냅샷 생성

```python
# [spend_profile.py](backend/app/services/spend_profile.py:48-87)
def get_profile(self, user_id: str) -> SpendProfile | None:
    store = self._users.get(user_id)
    if not store or not store.transactions:
        return None

    total_amount = sum(store.category_totals.values())
    peak_hour = max(store.hour_counts, key=store.hour_counts.get) if store.hour_counts else 0
    top_cat = max(store.category_totals, key=store.category_totals.get) if store.category_totals else SpendCategory.OTHER

    breakdown = []
    for cat in SpendCategory:
        cat_total = store.category_totals.get(cat, 0.0)
        cat_count = store.category_counts.get(cat, 0)
        if cat_count == 0:
            continue
        breakdown.append(
            CategorySummary(
                category=cat,
                total_amount=cat_total,
                tx_count=cat_count,
                avg_amount=cat_total / cat_count,
                pct_of_total=cat_total / total_amount if total_amount > 0 else 0,
            )
        )

    return SpendProfile(
        ...
        category_breakdown=sorted(breakdown, key=lambda x: x.total_amount, reverse=True),
        ...
    )
```

- `category_breakdown`은 지출액 내림차순으로 정렬되어 반환된다. 추천 로직이 `breakdown[0]`을 top category로 참조하기 때문에 정렬 순서가 중요하다.
- 거래가 하나도 없는 카테고리는 `cat_count == 0` 조건으로 걸러내 불필요한 항목이 응답에 포함되지 않는다.

### 4-3. 규칙 기반 추천 5종

```python

# 3) 쇼핑 충동 소비 (건당 평균이 전체 평균의 1.2배 초과)
shopping = breakdown.get(SpendCategory.SHOPPING)
if shopping and shopping.avg_amount > avg * 1.2:

# 4) 여가/엔터테인먼트 (5% 초과)
ent = breakdown.get(SpendCategory.ENTERTAINMENT)
if ent and ent.pct_of_total > 0.05:
    # 30% 절감 가정

# 5) 예산 초과
budget = _budgets.get(user_id)

    over = profile.total_amount - budget.monthly_total
```

규칙별 절감 가정 비율 요약:

| 규칙 | 트리거 조건 | 절감 가정 |
|---|---|---|
| 카테고리 편중 | pct > 30% | 해당 카테고리의 10% |
| 식비 과다 | pct > 15% | 식비의 15% |
| 쇼핑 충동 | 건당 평균 > 전체 평균 × 1.2 | 쇼핑의 20% |
| 여가 과다 | pct > 5% | 여가의 30% |
| 예산 초과 | 실지출 > 월예산 | 초과액 명시 |

- 주거(`housing`)·공과금(`utilities`)은 편중 경고에서 제외한다. 이 두 카테고리는 통제 가능성이 낮은 고정 지출이기 때문이다.
- 조건이 하나도 해당하지 않으면 "현재 소비 패턴이 안정적입니다."를 기본 메시지로 삽입해 빈 응답을 방지한다.

### 4-4. ML 레이어 연결 — K-Means + XGBoost

```python
# [routes_strategy.py](backend/app/api/routes_strategy.py:99-113)

# K-Means 군집 라벨
cat_pcts = {cs.category.value: cs.pct_of_total for cs in profile.category_breakdown}
cluster_result = cluster_model.predict(cat_pcts)
label = cluster_result["cluster_label"]

# XGBoost 과소비 위험도
top_cat_pct = profile.category_breakdown[0].pct_of_total if profile.category_breakdown else 0
features = overspend_classifier.build_features(
    amount=avg, avg_amount=avg, category_pct=top_cat_pct,
    hour=profile.peak_hour, is_domestic=True,
    monthly_total=profile.total_amount, monthly_avg=profile.total_amount,
    recent_tx_count=profile.total_tx_count,
)
risk_result = overspend_classifier.predict(features)
risk = risk_result["probability"]
```

- K-Means 입력은 카테고리별 **비율 벡터**다. 절대 금액이 아닌 비율을 사용하므로 소득 수준이 다른 사용자 간에도 군집 비교가 가능하다.  
- XGBoost 특성 중 `monthly_avg=profile.total_amount`로 당월 총액을 평균으로 넘기는 부분이 있다. 이력이 한 달치밖에 없을 때의 fallback 처리인데, 다수 월 이력이 쌓일수록 별도 `monthly_avg` 계산이 필요한 개선 여지다.
- 두 모델 모두 미학습 상태이면 각자의 규칙 기반 fallback을 실행해 추천 API가 모델 의존 없이도 동작한다.

### 4-5. 예산 대비 초과 분석

```python
# [routes_strategy.py](backend/app/api/routes_strategy.py:163-186)
async def get_savings(user_id: str) -> dict:
    profile = profile_store.get_profile(user_id)
    budget = _budgets.get(user_id)
    savings = []

    for cs in profile.category_breakdown:
        if budget:
            budget_for_cat = next(
                (b.budget_amount for b in budget.items if b.category == cs.category), None
            )
            if budget_for_cat and cs.total_amount > budget_for_cat:
                savings.append({
                    "category": cs.category.value,
                    "spent": cs.total_amount,
                    "budget": budget_for_cat,
                    "over": round(cs.total_amount - budget_for_cat, 2),
                    "suggestion": f"{cs.category.value} 예산 초과 — {cs.total_amount - budget_for_cat:,.0f}원 절감 필요",
                })

    return {"user_id": user_id, "savings": savings}
```

- `next(... for b in budget.items if b.category == cs.category, None)` 패턴으로 카테고리별 예산을 O(n) 선형 탐색한다. 카테고리 수가 11개로 고정이므로 성능 문제가 없다.  
- 예산이 미설정된 카테고리(`budget_for_cat is None`)는 초과 판정 대상에서 제외하므로, 부분 예산 설정도 자연스럽게 지원된다.

```tsx
const riskColor = (score: number) =>
  score > 0.7 ? "var(--danger)" : score > 0.4 ? "var(--warning)" : "var(--success)";

// [strategy/page.tsx](frontend/src/app/strategy/page.tsx:88-96)
<div style={{
  flex: 1, height: 8, background: "#e2e8f0", borderRadius: 4, overflow: "hidden"

</div>
```

- `risk_score` (0~1)를 그대로 `width` 퍼센트에 매핑한다. CSS 트랜지션(`0.5s ease`)으로 새로고침 시 게이지가 부드럽게 채워지는 UX를 제공한다.  
- 0.4 / 0.7 두 임계값으로 초록(safe) → 노랑(warning) → 빨강(danger) 3단계 색상을 결정한다.

## ⑤ 설계 포인트

- **인메모리 저장소의 트레이드오프**: `profile_store`와 `_budgets`는 모두 프로세스 메모리에 산다. 응답 속도가 빠르고 외부 의존 없이 동작하지만, 서버 재시작 시 모든 데이터가 사라진다. Phase 1 구현으로 명시되어 있어 이후 DB 영속화가 예정된 구조다.

- **규칙과 ML의 역할 분담**: K-Means/XGBoost는 "이 사람이 어떤 유형인가"와 "위험도가 얼마인가"를 수치로 답하고, 실제 행동 제안(절약 방법·금액)은 규칙이 담당한다. ML 모델이 자연어 제안을 직접 생성하지 않기 때문에 제안 문구를 수정하거나 임계값을 조정하기 쉽다.

- **XGBoost 특성 구성의 한계**: `monthly_avg`에 당월 총액 자체를 넣는 fallback 처리는 이력이 충분히 쌓이지 않은 신규 사용자에서 `monthly_total_ratio`가 항상 1.0이 되는 문제를 만든다. 결과적으로 위험도가 실제보다 낮게 나올 수 있다.

- **절약 금액 계산은 추정치**: "식비의 15%", "쇼핑의 20%" 등의 절감 비율은 코드에 하드코딩된 가정값이다. 사용자별 과거 절약 성공률이나 업계 벤치마크 데이터를 반영하면 신뢰도가 높아지지만, 현재는 "이 정도면 절약 가능하다"는 가이드라인 수준이다.

- **전월 비교는 별도 API**: `strategy/page.tsx`는 `recommend`와 `analysis/compare` 두 API를 `Promise.allSettled`로 병렬 호출한다. 전월 비교 실패가 전략 추천 표시를 막지 않도록 독립적으로 처리하는 설계다.

### 예상 질문 & 답변 (발표 Q&A 대비)

**Q1. 추천이 너무 일반적이지 않나요? 협업 필터링 같은 건 안 쓰나요?**
> 현재는 K-Means 군집(소비 유형) + XGBoost 점수(과소비 위험) + 규칙 5종을 합치는 콘텐츠 기반 + 룰 추천. CF는 사용자 수가 충분히 쌓여야 효과 있어 후순위. 우선 도메인 룰의 설명력으로 사용자에게 "왜"를 분명히 전달.

**Q2. 추천 결과를 사용자가 무시하면 어떻게 학습하나요?**
> 현재는 무시 시그널을 학습에 반영하지 않음(피드백 루프 없음). 향후 "추천 노출 → 채택률" 로깅 + 추천 알고리즘 A/B 테스트(#18)로 학습 루프 구성 예정.

**Q3. K-Means 라벨이 바뀌면 추천도 바뀌나요?**
> 네, 사용자 라벨이 절약형↔균형형으로 이동하면 추천 카드 텍스트와 우선순위가 즉시 갱신. 다만 라벨 매핑이 결정적(군집 중심 비율 합 정렬)이라 학습마다 흔들리지는 않음 (#5 참조).

**Q4. 카테고리별 절감액은 어떻게 계산하나요?**
> 사용자 카테고리 비율 vs 동일 군집 평균 비율의 차이 × 월 평균 지출. "당신은 외식 비중이 절약형 평균보다 X% 높음 → 월 Y만원 절감 가능" 식의 도메인 휴리스틱.

**Q5. 전월 비교는 왜 별도 API인가요?**
> `Promise.allSettled`로 병렬 호출되며, 전월 비교 실패가 추천 표시를 막지 않게 분리. 응답 지연 격리와 부분 실패 허용이 목적.

## ⑥ 한 줄 정리

K-Means 군집·XGBoost 위험도·규칙 5종을 하나의 엔드포인트에서 순차 합산해, 각 ML 결과가 "왜 이 사람에게 이 제안인가"를 설명하는 텍스트로 이어지도록 구성한 기능이다.
