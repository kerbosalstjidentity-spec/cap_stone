# #21 알림 시스템 — DB + Redis Pub/Sub + WebSocket 3-계층과 FCM의 분리

## ① 개요

PayWise의 알림 시스템은 두 개의 독립된 채널로 구성된다. 하나는 **backend의 WebSocket + Redis Pub/Sub** 경로로, 앱이 열려있는 사용자에게 감정 소비 경보·거래 알림을 실시간으로 전달한다. 다른 하나는 **fraud-service의 FCM(Firebase Cloud Messaging)** 경로로, 거래 차단(BLOCK) 또는 Step-up 인증 요청 시 사용자의 모바일 기기에 직접 푸시를 보낸다. 두 채널은 코드베이스도, 동작 방식도 완전히 분리되어 있다.

> **구현 실태**: FCM 경로(fraud-service)는 `FIREBASE_ENABLED=false` 가 기본값이라 별도 Firebase 설정 없이는 항상 비활성화된다 ([push_service.py:21](fraud-service/app/services/push_service.py:21)). WebSocket 경로(backend)는 Redis subscriber가 `start_redis_subscriber()` 로 부팅 시 실제 시작되어 정상 동작한다 ([main.py:157](backend/app/main.py:157)). 단, WebSocket 세션이 없는 사용자(앱 닫힘)는 DB에 저장된 알림을 다음 접속 시 폴링으로 받을 뿐이다. `fcm_token` 을 요청 바디로 받는 구조이므로 클라이언트가 토큰을 넘겨주지 않으면 FCM이 활성화되어 있어도 푸시 대상이 없다.

## ② 시스템 구성

```
[채널 A — backend WebSocket + Redis]

  감정 위험 탐지 / 거래 이벤트
      │
      ▼
  create_and_push(session, user_id, ...)
      ├─ DB 저장: Notification 테이블 (PostgreSQL)
      ├─ Redis publish("notify:{user_id}", payload)
      │       │
      │       └─ ConnectionManager._subscribe_loop()
      │           psubscribe("notify:*")
      │               │
      │               ▼
      └─ notification_manager.send_to_user(user_id, payload)
              │
              └─ WebSocket.send_json() → 연결된 클라이언트

  GET  /v1/notifications/ws?token={jwt}  ← WebSocket 연결
  GET  /v1/notifications/               ← REST 목록 조회
  PUT  /v1/notifications/{id}/read      ← 읽음 처리

[채널 B — fraud-service FCM]

  FraudServiceManager.get_final_action()
      │  BLOCK or REVIEW 판정 시
      ▼
  build_step_up_payload(tx_id, amount, action_type)
      │
      └─ send_sync(fcm_token, title, body, data)
              │
              └─ FIREBASE_ENABLED=true + firebase-admin 설치 시
                  → messaging.send(Message) → FCM → 모바일 기기

  ⚠️ FIREBASE_ENABLED 기본값 = false
  ⚠️ fcm_token 이 요청 바디에 없으면 send_sync 자체를 건너뜀
```

| 파일 | 역할 |
|---|---|
| `backend/app/services/notification_service.py` | ConnectionManager(WebSocket 관리) + create_and_push + 조회 헬퍼 |
| `backend/app/api/routes_notifications.py` | WebSocket 엔드포인트 + REST CRUD |
| `fraud-service/app/services/push_service.py` | Firebase Admin SDK 래퍼, FCM 발송 |
| `fraud-service/app/services/fraud_service.py:93-108` | BLOCK/STEP_UP 시 push_service 호출 |

## ③ 동작 흐름

```
[WebSocket 알림 흐름]
1. 앱 시작 → ws://host/v1/notifications/ws?token={jwt} 연결
2. routes_notifications.websocket_endpoint()
   - JWT decode → user_id 추출
   - notification_manager.connect(user_id, websocket)
3. backend main.py lifespan:
   - notification_manager.start_redis_subscriber()
   - _subscribe_loop(): Redis psubscribe("notify:*") 패턴 구독 시작
4. 어딘가에서 create_and_push(session, user_id, ...) 호출
   - Notification DB 행 삽입 (session.flush)
   - Redis publish("notify:{user_id}", payload)
   - notification_manager.send_to_user(user_id, payload)
5. _subscribe_loop 가 Redis 메시지 수신 → send_to_user 중복 전송
   ⚠️ Redis publish + 직접 send_to_user 두 경로가 동시에 실행 → 중복 전송 위험
6. 클라이언트 WebSocket.recv() → 알림 처리
7. ping/pong 루프로 연결 유지

[FCM 알림 흐름]
1. /v1/evaluate 요청 바디에 fcm_token 포함 여부 확인
2. FraudServiceManager.get_final_action() → BLOCK or REVIEW 판정
3. build_step_up_payload(tx_id, amount, action_type) → title/body/data 생성
4. _init_firebase() 호출
   - FIREBASE_ENABLED=false → return False → send_sync skip
   - FIREBASE_ENABLED=true + firebase-admin 설치 → SDK 초기화
5. fcm_token 있으면 messaging.send(Message) 실행
6. { push_sent: true/false, type: "BLOCK_ALERT"|"STEP_UP_AUTH" } 반환
```

## ④ 핵심 코드 분석

### 4-1. ConnectionManager — 사용자별 다중 WebSocket 지원

```python
# notification_service.py:29-54
async def connect(self, user_id: str, websocket: WebSocket) -> None:
    await websocket.accept()
    if user_id not in self._connections:
        self._connections[user_id] = []
    self._connections[user_id].append(websocket)

async def send_to_user(self, user_id: str, data: dict) -> None:
    dead = []
    for ws in self._connections[user_id]:
        try:
            await ws.send_json(data)
        except Exception:
            dead.append(ws)
    for ws in dead:
        self.disconnect(user_id, ws)
```

[notification_service.py:29](backend/app/services/notification_service.py:29)

한 user_id에 여러 WebSocket이 붙을 수 있다 — 같은 계정으로 PC + 모바일이 동시 접속하는 경우를 지원한다. `send_to_user`는 전송 실패한 연결을 `dead` 목록에 수집해 루프 중에는 건드리지 않고, 루프 종료 후 일괄 disconnect한다 — 이터레이션 중 컬렉션 변경을 피하는 안전한 패턴이다.

### 4-2. Redis Pub/Sub + 직접 send — 중복 전송 구조

```python
# notification_service.py:138-139
await publish(f"notify:{user_id}", payload)         # ① Redis 발행
await notification_manager.send_to_user(user_id, payload)  # ② 직접 전송
```

[notification_service.py:138](backend/app/services/notification_service.py:138)

두 줄이 항상 모두 실행된다. `publish`로 Redis에 발행하면 `_subscribe_loop`가 받아서 `send_to_user`를 호출한다. 그리고 바로 다음 줄에서 또 `send_to_user`를 직접 호출한다. **같은 인스턴스에 WebSocket이 연결된 사용자는 알림을 두 번 받는다**. Redis Pub/Sub는 멀티 인스턴스 배포 시 다른 인스턴스의 연결에 알림을 전달하기 위한 용도다. 같은 인스턴스라면 Redis 경유 없이 직접 전송만으로 충분하고, 다른 인스턴스라면 직접 전송은 의미가 없다. 두 경로 중 하나만 남겨야 한다.

### 4-3. Redis subscriber 루프 — 재연결 내성

```python
# notification_service.py:68-96
async def _subscribe_loop(self) -> None:
    while True:
        try:
            pubsub = await get_pubsub()
            if not pubsub:
                await asyncio.sleep(5)
                continue
            await pubsub.psubscribe("notify:*")
            async for message in pubsub.listen():
                ...
        except asyncio.CancelledError:
            break
        except Exception as e:
            logger.warning("[WS] Redis subscriber error: %s, retrying in 3s", e)
            await asyncio.sleep(3)
```

[notification_service.py:68](backend/app/services/notification_service.py:68)

Redis 연결 실패 시 5초 대기 후 재시도, 기타 예외는 3초 대기 후 재시도한다. `CancelledError`만 `break`으로 정상 종료한다. Redis가 일시적으로 내려갔다 복구되면 자동으로 재구독된다. `while True` 무한 루프가 `asyncio.sleep`으로 비동기 이벤트루프를 양보하므로 다른 코루틴을 차단하지 않는다.

### 4-4. FCM — FIREBASE_ENABLED 환경변수 게이트

```python
# push_service.py:21-47
_FIREBASE_ENABLED = os.getenv("FIREBASE_ENABLED", "false").lower() == "true"

def _init_firebase() -> bool:
    if not _FIREBASE_ENABLED:
        return False
    try:
        import firebase_admin
        from firebase_admin import credentials
        if not firebase_admin._apps:
            cred = credentials.Certificate(_CREDENTIALS_PATH)
            firebase_admin.initialize_app(cred)
        _initialized = True
        return True
    except ImportError:
        logger.warning("firebase-admin 미설치 — FCM 비활성화")
        return False
```

[push_service.py:21](fraud-service/app/services/push_service.py:21)

`FIREBASE_ENABLED=false`(기본값)면 첫 줄에서 `return False`로 빠져나간다. Kafka의 `_HAS_AIOKAFKA`(`#19`)와 동일한 selective degradation 패턴이다. `firebase-admin`이 설치되어 있지 않아도 `ImportError`를 잡아 WARNING만 남긴다. 결론: 개발 환경에서 Firebase 없이 전체 서비스를 실행하면서도 BLOCK/STEP_UP 판정 코드가 에러 없이 통과한다.

### 4-5. FCM은 fraud-service에, WebSocket은 backend에 — 채널 분리 의도

```python
# fraud_service.py:93-108
from app.services.push_service import build_step_up_payload, send_sync
payload = build_step_up_payload(tx_id, amount, action_type)
if fcm_token:
    send_sync(fcm_token, payload["title"], payload["body"], payload["data"])
return {"push_sent": bool(fcm_token), "type": "BLOCK_ALERT", **payload}
```

[fraud_service.py:93](fraud-service/app/services/fraud_service.py:93)

fraud-service는 FCM 경로만 쓴다 — Redis나 WebSocket을 직접 건드리지 않는다. backend는 FCM을 전혀 호출하지 않는다. 의도적 분리: **긴급 차단 알림**은 앱 오픈 여부와 무관하게 모바일 기기에 전달해야 하므로 FCM이 적합하다. **일반 소비 통계·감정 경보**는 앱 열려있는 상태에서 WebSocket으로 충분하다.

## ⑤ 설계 포인트 / 트러블슈팅 거리

- **알림 중복 전송**: `create_and_push`에서 Redis publish와 직접 `send_to_user`가 동시에 호출된다. 단일 인스턴스에서 WebSocket 연결이 있는 사용자는 알림을 **두 번** 받는다. Redis Pub/Sub 경로는 멀티 인스턴스에서만 필요하므로, 단일 인스턴스라면 `await publish(...)` 줄을 제거하거나, 반대로 `send_to_user` 직접 호출을 제거하고 Redis subscriber에 위임해야 한다. (✅ ROADMAP W4-#6 + W9-#6 — Redis pub/sub 단일 경로화, publish 성공 시 직접 송신 안 함. publish 실패(Redis 미가용) 시에만 fallback)

- **`user_id`가 query string으로 전달됨**: REST 알림 조회 엔드포인트의 `user_id`가 쿼리 파라미터다 — `GET /v1/notifications/?user_id=other_user_id`. JWT 검증 없이 다른 사용자 알림을 열람할 수 있다. `Depends(get_current_user)` 로 JWT에서 user_id를 추출해야 IDOR(Insecure Direct Object Reference) 취약점이 해소된다. (✅ ROADMAP W1-#1)

- **`mark_all_read`가 `await session.commit()`을 직접 호출**: 다른 함수들은 세션 commit을 라우터에 위임하지만, `mark_all_read`와 `mark_as_read`만 직접 commit한다. 한 HTTP 요청에서 `mark_all_read` 후 다른 DB 작업이 있다면 "이미 커밋된 세션"에서 추가 변경을 시도해 `InvalidRequestError`가 날 수 있다. 라우터에서 commit을 담당하는 통일된 패턴으로 수정이 필요하다.

- **WebSocket 연결이 스레드/인스턴스를 못 넘는다**: `_connections` dict는 프로세스 내 메모리다. 로드밸런서 뒤에 인스턴스가 2대 이상이면, 사용자 A가 인스턴스 1에 WebSocket을 맺었는데 알림 발행은 인스턴스 2에서 일어나면 `send_to_user`가 빈 connections를 찾아 전달이 실패한다. Redis pub/sub가 이를 보완하는 설계이지만, 앞서 설명한 중복 전송 문제와 충돌한다. 일관된 구조는 ① Redis pub/sub만 유일한 브로드캐스트 경로로 쓰고, ② 직접 `send_to_user` 호출은 구독 루프 내부에서만 하는 것이다.

- **FCM 비동기 래퍼가 실제로는 동기 호출**: `send()` 함수가 `async def`이지만 내부에서 `asyncio.to_thread` 없이 동기 `send_sync()`를 직접 호출한다. FCM SDK의 `messaging.send()`는 HTTP 요청을 동기로 블로킹한다. BLOCK 판정이 내려질 때마다 FCM 응답 대기 시간(보통 100-300ms) 동안 이벤트루프가 멈춘다. `await asyncio.to_thread(send_sync, ...)` 로 감싸야 비동기 성능이 보장된다. (✅ ROADMAP W4-#6 — `await asyncio.to_thread(send_sync, ...)` 적용)

### 예상 질문 & 답변 (발표 Q&A 대비)

**Q1. 발표대본의 "실시간 Push 알림"이 진짜 모바일 푸시인가요?**
> 정직하게: **WebSocket 실시간**입니다. FCM은 `FIREBASE_ENABLED=false` 기본값이라 미연결. 모바일 백그라운드 푸시는 후속 작업이며 발표 멘트도 "WebSocket 실시간"으로 정정 예정.

**Q2. WebSocket 연결이 끊긴 사용자는 어떻게 받나요?**
> DB에 `Notification` 테이블로 저장 → 다음 접속 시 폴링으로 미읽음 알림 표시. 즉 채널은 push 보장이 아닌 best-effort + DB persistent.

## ⑥ 한 줄 정리

backend의 DB + Redis Pub/Sub + WebSocket 3-계층 일반 알림과 fraud-service의 FCM 긴급 차단 푸시가 의도적으로 분리된 구조 — 단, Redis 발행과 WebSocket 직접 전송이 동시에 일어나 중복 전송이 발생하고, REST API의 user_id 쿼리 파라미터 IDOR와 FCM async 래퍼의 이벤트루프 블로킹이 운영 전 보완이 필요하다.
