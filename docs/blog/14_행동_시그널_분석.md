# #14 행동 시그널 분석 — 사람인지 봇인지, 결제 전에 먼저 판단한다

## ① 개요

ML 사기 점수와 규칙 엔진은 **거래 데이터**를 본다. 행동 시그널 분석은 그보다 한 단계 앞, 즉 **사용자가 폼을 어떻게 채웠는지, 마우스를 어떻게 움직였는지, 어떤 네트워크를 타고 접속했는지**를 보고 리스크를 선별한다. 주석에는 "Layer 1 — Client/Edge 행동 시그널 사전 스크리닝"이라 명시되어 있으며, `_evaluate_one` 에서 ML 모델보다 먼저 호출된다. 브라우저/앱 SDK가 수집한 시그널을 8가지 휴리스틱으로 가중합산해 0~1 점수와 이상 플래그를 반환한다.

---

## ② 시스템 구성

```
[브라우저/앱 SDK]
   └─ signals: {
        behavioral_biometrics: { mouse_speed_variance, form_fill_duration_ms, clipboard_paste_count },
        session_context:        { tab_focus_changes, page_dwell_time_ms },
        network_context:        { is_tor, is_vpn, is_proxy }
      }
         │
         ▼
┌─────────────────────────────────────────┐
│  analyze_signals()                       │
│  (behavioral_signals.py)                 │
│                                          │
│  score = 0.0                             │
│  ├─ BOT_MOUSE_PATTERN  +0.3             │
│  ├─ FAST_FORM_FILL     +0.4             │
│  ├─ EXCESSIVE_PASTE    +0.2             │
│  ├─ HIGH_TAB_SWITCHING +0.1             │
│  ├─ VERY_SHORT_DWELL   +0.15            │
│  ├─ TOR_DETECTED       +0.5             │
│  ├─ VPN_DETECTED       +0.2             │
│  └─ PROXY_DETECTED     +0.15            │
│                                          │
│  risk_score = min(sum, 1.0)             │
└──────────────┬──────────────────────────┘
               │ SignalRiskResult
               ▼
routes_fraud._evaluate_one()
  → signal_analysis 필드로 응답에 포함
  (현재는 모델/규칙 판정에 직접 영향 없음)

┌───────────────────────────────────────┐
│  DeviceStore (device_store.py)         │
│  device_id → deque[DeviceRecord]       │
│  DeviceFingerprintRule 에서 사용        │
└───────────────────────────────────────┘
```

| 파일 | 역할 |
|---|---|
| `app/services/behavioral_signals.py` | 8가지 시그널 가중 합산 → SignalRiskResult |
| `app/services/device_store.py` | 디바이스-사용자 매핑 이력 (60분 윈도우) |

## ③ 동작 흐름

```
1. /v1/evaluate 요청 바디의 signals 필드가 dict 형태로 전달됨
2. _evaluate_one() 첫 줄에서 analyze_signals(signals) 호출 — 모델보다 먼저 실행
3. behavioral_biometrics → 마우스/폼/클립보드 3개 항목 체크
4. session_context → 탭 전환 횟수, 페이지 체류 시간 2개 항목 체크
5. network_context → Tor/VPN/Proxy 3개 항목 체크
6. 발동된 항목의 가중치를 누적, min(sum, 1.0) 으로 클리핑
7. SignalRiskResult(risk_score, flags, detail) 반환
8. _evaluate_one() 응답의 signal_analysis 필드로 노출
   ↳ flags 가 비어있으면 signal_analysis 자체가 None 으로 생략
```

## ④ 핵심 코드 분석

### 4-1. 8가지 시그널 가중 합산

```python
# behavioral_signals.py:26-99
def analyze_signals(signals: dict[str, Any] | None) -> SignalRiskResult:
    if not signals:
        return SignalRiskResult(risk_score=0.0, flags=[], detail={})

    score = 0.0
    flags: list[str] = []
    detail: dict[str, Any] = {}

    biometrics = signals.get("behavioral_biometrics", {})

    mouse_var = biometrics.get("mouse_speed_variance")
    if mouse_var is not None and mouse_var < 0.01:  # 봇 의심
        score += 0.3
        flags.append("BOT_MOUSE_PATTERN")

    fill_ms = biometrics.get("form_fill_duration_ms")
    if fill_ms is not None and fill_ms < 3000:      # 자동 입력 의심
        score += 0.4
        flags.append("FAST_FORM_FILL")

    paste = biometrics.get("clipboard_paste_count")
    if paste is not None and paste >= 3:
        score += 0.2
        flags.append("EXCESSIVE_PASTE")

    # ... session, network 항목들

    if network.get("is_tor"):
        score += 0.5
        flags.append("TOR_DETECTED")

    risk_score = min(score, 1.0)
    return SignalRiskResult(risk_score=round(risk_score, 4), flags=flags, detail=detail)
```

[behavioral_signals.py:26](fraud-service/app/services/behavioral_signals.py:26)

**시그널별 가중치 요약:**

| 시그널 | 조건 | 가중치 | 판단 근거 |
|---|---|---|---|
| `BOT_MOUSE_PATTERN` | mouse_speed_variance < 0.01 | +0.3 | 사람의 마우스는 분산이 크다 |
| `FAST_FORM_FILL` | form_fill_duration_ms < 3000 | +0.4 | 3초 미만 폼 완성은 사람에게 불가능 |
| `EXCESSIVE_PASTE` | clipboard_paste_count ≥ 3 | +0.2 | 반복 붙여넣기는 자동화 도구 패턴 |
| `HIGH_TAB_SWITCHING` | tab_focus_changes > 10 | +0.1 | 다중 계정 탭 전환 의심 |
| `VERY_SHORT_DWELL` | page_dwell_time_ms < 2000 | +0.15 | 2초 미만 체류는 페이지를 읽지 않은 것 |
| `TOR_DETECTED` | is_tor = true | +0.5 | 익명화 네트워크, 가장 높은 가중치 |
| `VPN_DETECTED` | is_vpn = true | +0.2 | 위치 은폐 시도 |
| `PROXY_DETECTED` | is_proxy = true | +0.15 | 중간자 개입 가능성 |

TOR 탐지 +0.5와 FAST_FORM_FILL +0.4가 가장 높다. 두 개만 동시에 발동해도 score가 0.9를 넘는다.

### 4-4. DeviceStore — 디바이스-계정 매핑 이력

```python
# device_store.py:30-41
def record(self, device_id: str, user_id: str) -> None:
    if not device_id or not user_id:
        return
    rec = DeviceRecord(user_id=user_id)
    with self._lock:
        self._data[device_id].append(rec)

def unique_users_in_window(self, device_id: str, window_minutes: int = 60) -> set[str]:
    cutoff = datetime.now(tz=timezone.utc) - timedelta(minutes=window_minutes)
    with self._lock:
        records = list(self._data.get(device_id, []))
    return {r.user_id for r in records if r.ts >= cutoff}
```

[device_store.py:30](fraud-service/app/services/device_store.py:30)

`DeviceFingerprintRule.evaluate()` 가 호출될 때 `device_store.record()` → `unique_users_in_window()` 를 차례로 호출한다. 즉 **평가와 기록이 같은 요청 안에서** 일어나므로, 방금 들어온 이번 거래도 이력에 포함되어 탐지될 수 있다. `deque(maxlen=500)` 으로 상한을 두어 메모리 오버플로를 방지한다.

## ⑤ 설계 포인트 / 트러블슈팅 거리

- **행동 시그널이 최종 판정에 영향을 주지 않는다**: `analyze_signals()` 의 결과인 `signal_result` 는 현재 응답 필드(`signal_analysis`)에만 담기고, `model_action` / `rule_action` / `final_action` 계산에는 쓰이지 않는다. 즉 Tor로 접속해 3초 안에 폼을 완성해도 이 시스템 단독으로는 차단되지 않는다. 설계상 "Layer 1 사전 스크리닝" 의도는 있지만 실제 판정 경로에 연결이 빠져있다. `signal_result.risk_score` 를 `FraudEvaluateRequest.score` 에 합산하거나, rule_action 산정 시 threshold를 두는 방식으로 연결이 가능하다.

- **임계값이 전부 하드코딩**: `mouse_var < 0.01`, `fill_ms < 3000`, `tab_changes > 10` 등 모든 임계값이 함수 본문에 리터럴로 박혀 있다. 사용자 모집단이나 기기 환경에 따라 적절한 기준이 달라지는데, 조정하려면 코드 수정 → 배포가 필요하다. 임계값을 설정 파일 또는 환경변수로 분리하면 운영 유연성이 높아진다.

- **가중치 합산의 상한 클리핑만 있고 하한 없음**: `score`가 0.0 미만이 될 수 없어 하한 문제는 없지만, 1.0 클리핑 후에는 어떤 시그널이 몇 개 더 발동했는지 점수로 구분되지 않는다. TOR+FAST_FORM_FILL(=0.9) 과 TOR+FAST_FORM_FILL+BOT_MOUSE(=1.0 클리핑)이 score 상으로는 차이가 사라진다. `flags` 개수로 보완할 수 있지만, 원점수를 clamp 전에 별도 보존하면 severity 분석에 유용하다.

- **DeviceStore 도 인메모리**: `profile_store` 와 마찬가지로 `device_store` 역시 인메모리 `defaultdict`이다. 재시작 또는 멀티 인스턴스 배포 시 디바이스-계정 이력이 초기화되어 `DeviceFingerprintRule` 이 동일 디바이스 다중 계정을 탐지하지 못한다. Redis sorted set + TTL 구조로 교체하면 멀티 인스턴스에서도 이력이 공유된다. (✅ ROADMAP W2-#3 — `device:users:{device_id}` ZSET (member=user_id\|ts, score=epoch) + 자동 ZREMRANGEBYSCORE + 키 TTL 2시간, Redis 미가용 시 deque 폴백)

- **클라이언트가 시그널을 조작할 수 있다**: `signals` 는 클라이언트가 직접 전달하는 필드다. 공격자가 정상 범위의 `mouse_speed_variance`, `form_fill_duration_ms` 값을 위조하면 모든 바이오메트릭 시그널을 우회할 수 있다. 서버 측에서 독립적으로 수집하거나, SDK 서명 검증 메커니즘을 추가해야 실질적인 방어가 된다. (✅ ROADMAP W1-#6 — `BEHAVIOR_SIGNAL_SECRET` HMAC-SHA256 + 5분 타임스탬프 윈도우 검증, 미서명 시 `UNVERIFIED_SIGNALS` 플래그 + 점수 0.5배 감쇠, IP/국가는 서버 관찰값으로 강제 덮어쓰기)

### 도메인 확장 로드맵 — Layer 1 스크리너 본격화

현재 Layer 1 은 "탐지하지만 차단에는 영향 없는" 미연결 상태이며, 8개 휴리스틱은 임계값 하드코딩 + 클라이언트 변조 가능이라는 구조적 약점을 가진다. [#12 로드맵](12_실시간_사기_점수_IF_RF_하이브리드.md#도메인-확장-로드맵-이상-거래-스크리닝에서-fds로) · [#13 로드맵](13_규칙_엔진.md#도메인-확장-로드맵-사기-유형별-룰셋-본격화)과 별개로, 행동 시그널 자체를 강화하는 5개 트랙을 정리한다.

#### Track α. 판정 경로 연결 (탐지 → 차단)
- **결손**: `signal_result.risk_score` 가 응답 필드에만 담기고 `final_action` 산정에 미반영
- **추가**: [`routes_fraud.py`](fraud-service/app/api/routes_fraud.py) `_evaluate_one()` 에서 `signal_result.risk_score >= 0.7` 시 ML score 에 가산하거나, 자체적으로 `SOFT_REVIEW` 액션을 만들어 [`policy_merge`](fraud-service/app/services/policy_merge.py) 에 합류. 임계값은 false positive 분석 후 결정
- **부수 효과**: Tor + 폼 3초 완성 같은 명백한 봇 패턴이 즉시 차단됨
- **작업량**: 1일 (코드) + 2일 (캘리브레이션)
- **우선순위**: 최상 — 현재 가장 큰 설계 결함

#### Track β. 키스트로크 다이내믹스 추가
- **결손**: 마우스 속도·폼 시간만 봄. 사용자 고유의 타이핑 리듬(키 누름→떼는 간격, 키 간 간격)은 미수집 → 봇이 우회 쉬움
- **추가**: 클라이언트 SDK 가 `keystroke_intervals_ms: list[float]` 시그널 추가 수집. 서버에서 사용자별 타이핑 프로파일을 [`profile_store`](fraud-service/app/services/profile_store.py) 에 누적, 현재 거래 입력의 코사인 유사도 < 임계값 시 BOT_TYPING 플래그 발동
- **데이터**: 자체 사용자 타이핑 + 봇 시뮬레이션(자동화 도구 Selenium/Playwright) 라벨
- **작업량**: SDK 1일 + 서버 2일 + 라벨 수집 1일

#### Track γ. ML 분류기 도입 (휴리스틱 → 학습 모델)
- **결손**: 8개 시그널의 가중치가 코드 상수 `FLAG_WEIGHTS = {...}`. 시그널 간 상호작용·비선형성 미반영
- **추가**: 봇/사람 라벨 데이터로 LightGBM 또는 소형 MLP 학습. `analyze_signals()` 가 휴리스틱 + ML 점수 max 또는 ensemble 로 결합
- **데이터**: Track β 의 봇 시뮬레이션 + 자체 정상 사용자 + Kaggle 봇 트래픽 공개 데이터셋
- **의존성**: Track β (키스트로크 시그널이 추가되면 정확도 크게 상승)
- **작업량**: 데이터 1주 + 학습 3일 + 통합 1일

#### Track δ. 임계값 외부화 + 운영 토글
- **결손**: `mouse_var<0.01`, `fill_ms<3000`, `tab_changes>10` 등 임계값이 함수 본문 리터럴
- **추가**: `behavioral_signals_config.yaml` 외부 파일 또는 환경변수로 분리. `/admin/signal-thresholds` 라우터로 런타임 조정. [#13 Track D](13_규칙_엔진.md#track-d-룰-토글임계값-영속화) 의 Redis 영속화 패턴 그대로 적용
- **작업량**: 2일

#### Track ε. 시그널 조작 방지 (서명·서버 측 수집)
- **결손**: 클라이언트가 시그널을 위조하면 우회 가능. 모든 시그널이 클라이언트에서 평문으로 전송됨
- **추가 (다층)**:
  1. **HMAC 서명**: SDK 가 시그널 + 타임스탬프 + 디바이스 키로 HMAC 생성. 서버에서 검증 → 위조 즉시 BLOCK
  2. **서버 사이드 시그널 보강**: TLS fingerprint(JA3), HTTP header 순서, `User-Agent` ↔ `sec-ch-ua` 일관성 — 클라이언트 손이 안 닿는 영역
  3. **시그널 plausibility 체크**: `mouse_speed_variance=0.0` 처럼 의심스럽게 정상인 값 자체를 이상치로 간주하는 anti-spoofing 룰
- **의존성**: SDK 코드 협업 필요
- **작업량**: 1주

### 예상 질문 & 답변 (발표 Q&A 대비)

> 도메인 확장 관련 질문은 위 [도메인 확장 로드맵](#도메인-확장-로드맵-layer-1-스크리너-본격화) 절의 Q&A 매핑 참고.

**Q1. 8가지 시그널이 구체적으로 뭔가요?**
> 행동 바이오메트릭(마우스 속도 분산·폼 작성 시간·클립보드 붙여넣기) + 세션 컨텍스트(탭 포커스 변경·페이지 체류 시간) + 네트워크(Tor·VPN·Proxy 여부). 8개를 가중합해 0~1 위험 점수.

**Q2. 봇이 마우스 움직임을 사람처럼 흉내내면?**
> 현재 휴리스틱은 그런 정교한 봇에 우회당할 수 있습니다. 키스트로크 다이내믹스 추가([Track β](#track-β-키스트로크-다이내믹스-추가))와 ML 분류기 도입([Track γ](#track-γ-ml-분류기-도입-휴리스틱--학습-모델))이 후속 대응.

**Q3. Tor 접속자를 무조건 차단하면 정상 사용자(프라이버시 중시) 배제 아닌가요?**
> 네, 현재는 Tor 시그널이 단일로 BLOCK까진 안 가고 위험 점수 가산만. ML 모델 점수와 합쳐 종합 판정이라 정상 Tor 사용자는 정상 거래 패턴이면 통과.

**Q4. 클라이언트 SDK가 시그널을 위조하면 우회 가능하지 않나요?**
> ⑤절에서 인정한 약점입니다. HMAC 서명 + 서버 사이드 시그널 보강이 [Track ε](#track-ε-시그널-조작-방지-서명서버-측-수집)에 정리.

**Q5. 모바일 앱에서도 같은 시그널이 수집되나요?**
> 현재는 웹 SDK 위주. 모바일은 가속도계·터치 압력 등 다른 시그널이 필요해 별도 SDK 필요. 모바일 SDK는 후속 작업.

## ⑥ 한 줄 정리

마우스 움직임·폼 작성 속도·Tor 접속 여부 등 8가지 행동 시그널을 가중 합산해 봇·자동화·익명 네트워크를 ML 모델이 개입하기 전에 사전 선별하는 Layer 1 스크리너 — 단, 현재는 최종 차단 판정에 직접 연결되어 있지 않아 탐지에 그친다.
