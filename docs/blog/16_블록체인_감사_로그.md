# #16 블록체인 감사 로그 — 해시 체인으로 변조를 탐지하는 불변 감사 트레일

## ① 개요

PayWise의 fraud-service는 모든 거래 판정 결과를 두 군데에 동시에 기록한다. 한쪽은 `audit.jsonl` 파일(빠른 조회용 평문 로그), 다른 한쪽은 **SHA-256 해시 체인으로 연결된 블록 시퀀스**다. 후자는 비트코인 블록체인과 동일한 원리로 — 각 블록이 이전 블록의 해시를 포함하므로, 중간의 어떤 레코드를 한 글자라도 수정하면 그 시점부터 모든 후속 블록의 해시가 깨진다. 추가로 머클 리프(Merkle leaf)를 함께 저장해 오프체인 데이터 변조까지 탐지한다. "감사 로그가 변조되지 않았음"을 수학적으로 증명할 수 있는 구조다.

> 분산 합의(consensus) 없이 **단일 노드 인메모리 + JSON 파일 영속화** 방식이다. P2P 네트워크나 채굴(PoW) 은 없다. 비트코인의 "블록체인" 데이터 구조만 차용한 형태로, "변조 탐지(detection)"는 가능하지만 "변조 방지(prevention)"는 보장하지 않는다는 점을 명시할 필요가 있다.

```
1. /v1/fraud/evaluate 가 _evaluate_one(tx_data) 호출

      └─ self._save()                            ← tmp 파일 → atomic replace

   - GET /v1/audit/chain/verify → 전체 체인 무결성

   - GET /v1/audit/chain/merkle-root → 모든 leaf 의 머클 루트
```

물리적으로는 한 클래스 안에 모두 담지만, `to_onchain()`/`to_offchain()` 메서드로 두 뷰를 분리해 노출할 수 있다. 향후 진짜 분산 블록체인으로 이전할 때, 온체인엔 `(index, block_hash, prev_hash, merkle_leaf, timestamp)` 만 올리고 원문은 별도 DB에 두는 구조로 자연스럽게 확장 가능하다.

### 4-2. block_hash 계산 — 결정성을 보장하는 직렬화

```python
# blockchain_audit.py:65-81
def compute_hash(self) -> str:
    payload = json.dumps(
        {
            "index": self.index,
            "timestamp": self.timestamp,
            "transaction_id": self.transaction_id,
            "user_id": self.user_id,
            "action": self.action,
            "score": round(self.score, 6),
            "rule_ids": sorted(self.rule_ids),
            "amount": self.amount,
            "prev_hash": self.prev_hash,
        },
        sort_keys=True,
        ensure_ascii=False,
    )
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()
```

[blockchain_audit.py:65](fraud-service/app/services/blockchain_audit.py:65)

해시 결정성을 위한 세 가지 설계가 보인다:
- `sort_keys=True` — dict 키 순서로 인한 비결정성 제거
- `round(score, 6)` — 부동소수점 표현 차이 흡수 (예: `0.1+0.2`)
- `sorted(rule_ids)` — 리스트 순서 변동 흡수

해시 입력에서 **`reason_code` 와 `merkle_leaf` 는 빠져있다**. `block_hash` 는 "온체인 식별자"이고, `reason_code` 는 오프체인 데이터(`merkle_leaf` 로 별도 보호)라는 분리 의도다. 즉 reason_code 가 변조되면 block_hash 는 멀쩡하지만 merkle_leaf 검증에서 잡힌다.

### 4-3. merkle_leaf — 오프체인 원문의 무결성 지문

```python
# blockchain_audit.py:83-96
def compute_merkle_leaf(self) -> str:
    """오프체인 원문 데이터의 SHA-256 해시 (Merkle leaf)."""
    off_chain = {
        "transaction_id": self.transaction_id,
        "user_id": self.user_id,
        "action": self.action,
        "score": round(self.score, 6),
        "rule_ids": sorted(self.rule_ids),
        "reason_code": self.reason_code,
        "amount": self.amount,
        "timestamp": self.timestamp,
    }
    payload = json.dumps(off_chain, sort_keys=True, ensure_ascii=False)
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()
```

[blockchain_audit.py:83](fraud-service/app/services/blockchain_audit.py:83)

block_hash 계산식에서 빠져있던 `reason_code` 가 여기엔 포함된다. 결과적으로:
- **온체인(block_hash)**: 핵심 메타데이터의 무결성 보장
- **오프체인(merkle_leaf)**: 원문 전체(`reason_code` 포함)의 무결성 보장

두 해시가 서로 다른 입력을 보호하므로 어느 쪽이든 변조되면 검증에 걸린다.

### 4-4. Genesis 블록 — 체인의 진입점

```python
# blockchain_audit.py:142-161
_GENESIS_PREV = "0" * 64

def _make_genesis() -> AuditBlock:
    blk = AuditBlock(
        index=0,
        timestamp=datetime.now(tz=timezone.utc).isoformat(),
        transaction_id="GENESIS",
        user_id="SYSTEM",
        action="INIT",
        score=0.0,
        rule_ids=[],
        reason_code="Chain initialised",
        amount=0.0,
        prev_hash=_GENESIS_PREV,           # 64자리 0
    )
    blk.merkle_leaf = blk.compute_merkle_leaf()
    blk.block_hash = blk.compute_hash()
    return blk
```

[blockchain_audit.py:142](fraud-service/app/services/blockchain_audit.py:142)

비트코인 Genesis와 동일한 컨벤션으로 `prev_hash = "000...0"` (64개 0)을 사용한다. 다만 비트코인의 Genesis는 모든 노드가 합의한 고정값(satoshi 의 메시지 포함)이지만, 여기서는 매 인스턴스 시작 시 새 timestamp로 다른 Genesis가 생성된다. 결과적으로 **인스턴스마다 Genesis 가 다르므로 체인 자체가 인스턴스 종속적**이다 — 멀티 노드 구성이라면 첫 Genesis 를 합의해야 한다.

### 4-5. append — 락 보호된 단일 트랜잭션

```python
# blockchain_audit.py:186-215
def append(
    self,
    transaction_id: str, user_id: str, action: str,
    score: float, rule_ids: list[str],
    reason_code: str = "", amount: float = 0.0,
) -> AuditBlock:
    with self._lock:
        prev = self._chain[-1]
        blk = AuditBlock(
            index=prev.index + 1,
            timestamp=datetime.now(tz=timezone.utc).isoformat(),
            transaction_id=transaction_id,
            user_id=user_id,
            action=action,
            score=score,
            rule_ids=rule_ids,
            reason_code=reason_code,
            amount=amount,
            prev_hash=prev.block_hash,           # ← 체이닝의 핵심
        )
        blk.merkle_leaf = blk.compute_merkle_leaf()
        blk.block_hash = blk.compute_hash()
        self._chain.append(blk)
        self._save()                              # ← 매 append 마다 디스크 fsync
        return blk
```

[blockchain_audit.py:186](fraud-service/app/services/blockchain_audit.py:186)

`with self._lock:` 안에서 prev 조회 → 새 블록 생성 → 추가 → 저장이 원자적으로 일어난다. 이 락이 없으면 두 스레드가 같은 prev 를 보고 두 블록을 만들어 경쟁 상태가 발생한다.

비용 관점에서 주목할 점은 **매 append 마다 `_save()` 가 호출되어 전체 체인을 JSON 으로 다시 직렬화한다**는 것이다. 체인이 길어질수록 append 의 latency 가 선형 증가한다.

### 4-6. 3중 무결성 검증 — verify

```python
# blockchain_audit.py:217-248
def _verify_unlocked(self) -> dict[str, Any]:
    if not self._chain:
        return {"valid": False, "error": "Empty chain"}

    for i, blk in enumerate(self._chain):
        if blk.compute_hash() != blk.block_hash:                # ① 블록 자체 변조
            return {"valid": False, "error": f"Block {i}: hash mismatch", ...}

        if i > 0 and blk.prev_hash != self._chain[i - 1].block_hash:   # ② 체이닝 끊김
            return {"valid": False, "error": f"Block {i}: prev_hash broken", ...}

        if blk.merkle_leaf and blk.compute_merkle_leaf() != blk.merkle_leaf:  # ③ 오프체인 변조
            return {"valid": False, "error": f"Block {i}: merkle_leaf mismatch", ...}

    return {
        "valid": True,
        "chain_length": len(self._chain),
        "latest_hash": self._chain[-1].block_hash,
        "merkle_root": self.get_merkle_root_unlocked(),
    }
```

[blockchain_audit.py:217](fraud-service/app/services/blockchain_audit.py:217)

세 가지 변조 시나리오를 모두 잡는다:
1. **블록 필드 변조**: 누군가 `score` 값을 0.95 → 0.5 로 바꾸면 `compute_hash()` 가 새로 계산되어 저장된 `block_hash` 와 다르다.
2. **블록 삭제/순서 변경**: 중간 블록을 빼면 다음 블록의 `prev_hash` 가 새 prev 와 맞지 않는다.
3. **오프체인 원문 변조**: `reason_code` 만 바꿔도 `merkle_leaf` 가 다르게 계산된다.

흥미로운 설계는 `_verify_unlocked()` 와 `verify()` 의 분리다. 락을 이미 잡은 상태에서 호출되는 내부 경로(`_load()`)와 외부 API 진입점에서 락 중복 획득(데드락)을 피하기 위함이다.

### 4-7. Merkle Root — 전체 체인을 하나의 해시로 요약

```python
# blockchain_audit.py:123-139
def _compute_merkle_root(leaves: list[str]) -> str:
    if not leaves:
        return "0" * 64
    if len(leaves) == 1:
        return leaves[0]

    nodes = list(leaves)
    while len(nodes) > 1:
        if len(nodes) % 2 == 1:
            nodes.append(nodes[-1])  # 홀수면 마지막 노드 복제
        next_level = []
        for i in range(0, len(nodes), 2):
            combined = nodes[i] + nodes[i + 1]
            next_level.append(hashlib.sha256(combined.encode()).hexdigest())
        nodes = next_level
    return nodes[0]
```

[blockchain_audit.py:123](fraud-service/app/services/blockchain_audit.py:123)

표준 머클 트리 구성: 잎 노드 쌍을 해시로 묶어 한 단계씩 위로 올라간다. 홀수 개일 땐 마지막 노드를 복제하는 비트코인 방식과 동일하다. 결과적으로 N개 거래의 무결성을 단 하나의 해시로 요약할 수 있다 — 외부 감사관에게 "이 시점의 모든 로그는 이 hex 64자로 요약된다"고 제공할 수 있는 anchor.

다만 이 구현엔 **Merkle proof 생성 함수가 빠져있다**. 비트코인의 진정한 효용은 "특정 잎이 트리에 포함되었음을 O(log N) 해시만으로 증명"하는 데 있는데, 여기선 root 만 계산하고 inclusion proof 는 제공하지 않는다.

### 4-8. 영속화 — atomic write via tmp + replace

```python
# blockchain_audit.py:367-385
def _save(self) -> None:
    if self._persist_path is None:
        return
    self._persist_path.parent.mkdir(parents=True, exist_ok=True)
    data = [asdict(b) for b in self._chain]
    tmp = self._persist_path.with_suffix(".tmp")
    tmp.write_text(json.dumps(data, ensure_ascii=False, indent=2), encoding="utf-8")
    tmp.replace(self._persist_path)             # ← atomic on POSIX & Windows

def _load(self) -> None:
    raw = json.loads(self._persist_path.read_text(encoding="utf-8"))
    self._chain = []
    for item in raw:
        blk = AuditBlock(**item)
        self._chain.append(blk)
    # 로드 후 무결성 체크 (lock 이미 없는 상태이므로 _verify_unlocked 사용)
    result = self._verify_unlocked()
    if not result["valid"]:
        raise RuntimeError(f"Chain integrity check failed on load: {result['error']}")
```

[blockchain_audit.py:367](fraud-service/app/services/blockchain_audit.py:367)

`tmp.replace(self._persist_path)` 는 OS 레벨 atomic rename 을 보장한다 — 저장 중 프로세스가 죽어도 원본 파일은 깨지지 않거나 완전히 새 파일이 된다. 부분 쓰기(partial write) 위험을 차단하는 표준 패턴이다.

`_load()` 의 마지막 줄이 핵심이다 — 디스크에서 읽은 직후 무결성을 검증해 변조된 체인을 그대로 신뢰하지 않는다. 검증 실패 시 `RuntimeError` 가 발생해 **fraud-service 자체가 기동하지 못한다**. 운영 관점에서는 유사시 복구 옵션(snapshot rollback, 재초기화 플래그) 도 함께 고려할 만하다.

| 항목 | audit_logger (audit.jsonl) | audit_chain (audit_chain.json) |
|---|---|---|
| 형식 | JSONL append-only | JSON 배열 (전체 재기록) |
| 무결성 | 없음 (변조 가능) | SHA-256 체이닝 + 머클 리프 |
| 로테이션 | 10MB 마다 rotate, backup 3개 | 없음 (체인은 단조 증가) |
| 용도 | 운영 대시보드, 빠른 검색 | 법적 증명, 변조 탐지 |
| 비용 | append 1줄 | 전체 직렬화 + atomic write |

이 이중 기록은 **상호 검증** 효과도 있다. 한쪽이 변조되더라도 다른 쪽과 비교해 모순을 잡을 수 있다.

## ⑤ 설계 포인트 / 트러블슈팅 거리

- **변조 탐지(detection)는 가능하지만 변조 방지(prevention)는 미보장**: 단일 노드 인메모리 + 단일 JSON 파일 구조다. 공격자가 디스크 접근 권한을 얻으면 `audit_chain.json` 의 한 블록을 수정한 뒤 `compute_hash()` 로 재계산하고 이후 모든 후속 블록의 해시까지 다시 계산해 저장하면 검증을 통과한다. 진정한 방지를 위해서는 외부 anchor (예: 정기적으로 머클 루트를 공개 블록체인에 commit) 또는 분산 합의가 필요하다.

- **매 append 마다 전체 체인 재직렬화**: `_save()` 가 `[asdict(b) for b in self._chain]` 으로 전체 체인을 dict 로 변환한 뒤 JSON 직렬화한다. N 개 블록일 때 매 append 의 시간 복잡도가 O(N)이다. 6개월 누적 후 100만 건이 되면 단일 평가 호출이 수 초 걸릴 수 있다. append-only 파일 형식(JSONL) 으로 바꾸거나, RocksDB 같은 임베디드 KV 스토어를 쓰면 O(1) 으로 떨어진다. (✅ ROADMAP W3-#4 — JSONL append-only, 블록당 LF 1줄. 기존 `.json` 파일 자동 감지하여 1회성 마이그레이션)

- **인스턴스마다 다른 Genesis**: `_make_genesis()` 가 `datetime.now()` 를 timestamp 로 사용하므로 Genesis 의 `block_hash` 가 인스턴스마다 다르다. 멀티 노드 또는 재기동마다 새 체인이 생기는 셈이라, 분산 환경에서는 호환되지 않는다. 운영 시작 시 단 한 번 생성된 Genesis 블록을 환경변수 또는 초기 마이그레이션 산출물로 박제해야 한다. (✅ ROADMAP W3-#3 — `AUDIT_GENESIS_TIMESTAMP` 환경변수로 고정, 기본 `2025-01-01T00:00:00+00:00`. 인스턴스 간 동일 Genesis hash 보장)

- **머클 트리는 root 만, inclusion proof 없음**: `_compute_merkle_root()` 는 전체 트리를 매번 구성해 root 만 반환한다. "특정 거래가 이 root 에 포함되어 있음"을 외부에 증명하려면 sibling hash 들의 경로(Merkle proof) 가 필요한데, 그 함수는 미구현이다. 외부 감사관이 root 만 받고 검증하려면 결국 전체 체인을 다시 받아야 한다.

- **`_save()` 도 락 안에서 동기 디스크 I/O**: `append()` 의 `with self._lock:` 블록 안에서 디스크 쓰기까지 수행되므로 동시 평가 요청이 들어와도 직렬화된다. 사기 평가 자체가 ms 단위인데 디스크 I/O 가 수백 µs ~ 수 ms 추가된다. 큐 + 백그라운드 워커 패턴으로 분리하면 평가 응답 시간을 줄일 수 있다 — 단 그 경우 평가 후 즉시 chain 에 반영되지 않는 일관성 트레이드오프가 생긴다. (✅ ROADMAP W3-#6 — `audit-writer` 데몬 스레드 + `queue.Queue`. `append()` 가 enqueue 후 즉시 반환, 디스크 fsync는 백그라운드. `async_persist=False` 옵션으로 동기 모드도 선택 가능)

- **`audit_chain.json` 자체 변조 시 기동 불가**: `_load()` 가 검증 실패 시 `RuntimeError` 를 던진다. 디스크 손상이나 어떤 이유로든 단 한 블록이 깨지면 전체 fraud-service 가 기동하지 못한다. 변조 탐지의 엄격함과 가용성의 트레이드오프 — 운영 환경에선 "감사 로그 disabled 모드로 기동" 옵션 또는 "마지막 무결한 블록까지 트렁케이트" 옵션이 필요할 수 있다.

- **싱글턴 인스턴스가 모듈 import 시점에 초기화**: [blockchain_audit.py:389-390](fraud-service/app/services/blockchain_audit.py:389) 의 `audit_chain = BlockchainAuditChain(persist_path=_DEFAULT_PATH)` 가 모듈 import 만으로 디스크 I/O + 검증을 트리거한다. 테스트에서 이 모듈을 import 하는 순간 `logs/audit_chain.json` 을 건드리므로, 테스트 격리를 위해 환경변수로 경로를 오버라이드할 수 있게 만드는 것이 깔끔하다. (✅ ROADMAP W9-#14 — `AUDIT_CHAIN_PATH` 환경변수로 오버라이드 가능)

### 예상 질문 & 답변 (발표 Q&A 대비)

**Q1. 단일 노드 인메모리인데 "블록체인"이라 부르는 게 맞나요?**
> 비트코인의 **데이터 구조(해시 체인 + 머클 트리)**만 차용한 형태입니다. 분산 합의(consensus)·P2P·PoW가 없어 엄밀히는 "블록체인 시스템"이 아니라 **블록체인 영감 무결성 로그**가 정확. 발표 슬라이드와 멘트에서 "해시 체인 기반 감사 로그"로 표현 변경 예정.

**Q2. 분산 합의가 없는데 신뢰성은 어떻게 보장되나요?**
> "변조 *방지*(prevention)"는 보장 못 하지만 "변조 *탐지*(detection)"는 가능합니다. 누군가 한 블록을 수정하면 그 시점부터 모든 후속 블록의 해시가 깨져 검증 시 즉시 발각. 금융 감사에서 요구하는 "변조 흔적 보존" 요건은 만족하며, 운영급 분산 노드는 후속 작업.

**Q3. 머클 리프를 별도로 저장하는 이유는?**
> 블록 자체에는 트랜잭션 메타(액션·점수·rule_ids)만 담기고, 원본 거래 상세는 오프체인에 보관. 머클 리프 = `SHA-256(원본 거래)`를 블록에 담아두면 **오프체인 원본이 변조되었을 때 리프 해시 비교로 탐지**. 즉 온체인+오프체인 양쪽 변조를 모두 잡음.

**Q4. 운영 시 성능 부담은요?**
> 거래당 SHA-256 1~2회 + JSON append. ms 단위라 결제 지연에 영향 없음. 다만 ⑤절 지적대로 `_evaluate_one` 내부에서 동기 호출이라 P99에 누적될 수 있어 백그라운드 태스크 분리가 후속 작업.

**Q5. `audit_chain.json`이 손상되면 시스템이 죽나요?**
> 네, 현재는 검증 실패 시 `RuntimeError`로 fraud-service 자체가 기동 안 됩니다 — 변조 탐지의 엄격함과 가용성 트레이드오프. 운영 환경에선 "감사 로그 disabled 모드 기동" 또는 "마지막 무결한 블록까지 트렁케이트" 옵션이 필요한 후속 작업.

## ⑥ 한 줄 정리

SHA-256 해시 체인으로 거래 판정을 연결하고 머클 리프로 오프체인 원문 변조까지 탐지하는 — 비트코인 데이터 구조를 차용한 단일 노드 감사 트레일. "변조를 막지는 못해도, 변조되었음은 반드시 알 수 있는" 무결성 보장 시스템.
