# PayWise #8 — 카테고리 자동 분류

> 거래 데이터가 들어올 때 "이 거래는 식비인가, 쇼핑인가?"를 자동으로 결정해야 한다.
> PayWise는 이 분류를 **MCC 코드 우선, 가맹점명 키워드 fallback** 의 2단 결정 트리로 처리한다.

---

## ① 개요

PayWise의 카테고리 자동 분류는 [category_engine.py](backend/app/services/category_engine.py)에 정의된 순수 함수 3개로 구성된다. 입력은 국제 표준 가맹점 코드인 **MCC(Merchant Category Code)** 와 가맹점명 또는 메모 텍스트이며, 출력은 `SpendCategory` Enum 11개 중 하나다. 분류 로직에 ML이 없다 — 빠른 결정 속도와 100% 예측 가능한 동작이 요구되는 "거래 수집 경로"에 어울리는 설계다.

---

## ② 시스템 구성

```
┌──────────────────────┐     ┌──────────────────────────────┐
│  TransactionIngest   │     │ category_engine.py           │
│  (Pydantic 요청 모델)│ ──▶ │  classify(mcc, text)         │
│  .category: Enum     │     │    → classify_by_mcc(mcc)    │
└──────────────────────┘     │    → classify_by_keyword(txt)│
                             └──────────────┬───────────────┘
                                            │
                                            ▼
                             ┌──────────────────────────────┐
                             │ SpendCategory (Enum, 11개)   │
                             │ FOOD / SHOPPING / TRANSPORT  │
                             │ ENTERTAINMENT / EDUCATION    │
                             │ HEALTHCARE / HOUSING         │
                             │ UTILITIES / FINANCE / TRAVEL │
                             │ OTHER                        │
                             └──────────────────────────────┘
```

- **`SpendCategory`**: [spend.py:11](backend/app/schemas/spend.py:11) — `str, Enum` 으로 정의. `"food"` 등 소문자 문자열 값이 DB에 그대로 저장된다.
- **`TransactionIngest`**: [spend.py:27](backend/app/schemas/spend.py:27) — `category` 필드의 기본값이 `SpendCategory.OTHER`. 즉, 호출자가 MCC나 가맹점명을 넣지 않으면 `OTHER`로 보관된다.
- **`category_engine`**: 외부 의존성 없는 순수 함수 모듈. 싱글턴도, 상태도 없다.

---

## ③ 동작 흐름

`POST /v1/profile/ingest` 한 번의 요청에서 카테고리가 결정되는 순서를 따라가면 두 경로가 있다.

**경로 A — 호출자가 `category` 를 직접 지정**

1. 클라이언트가 `{"category": "food", ...}` 포함해서 전송.
2. `TransactionIngest` Pydantic 모델이 `SpendCategory.FOOD` 로 파싱.
3. `ingest_transaction()` 이 `.value`("food") 를 꺼내 DB에 저장.
4. `category_engine` 은 호출되지 않는다.

**경로 B — 카드사 원장 등 MCC/가맹점명만 있는 경우 (엔진 사용)**

1. 상위 통합 레이어가 `classify(mcc=5812, text="스타벅스_강남")` 호출.
2. `classify_by_mcc(5812)` — MCC 5812는 `range(5811, 5815)` 에 포함 → `SpendCategory.FOOD` 반환.
3. `OTHER` 가 아니면 바로 리턴, 키워드 단계는 스킵.
4. `OTHER` 였다면 `classify_by_keyword("스타벅스_강남")` → `"스타벅스"` 부분 매칭 → `SpendCategory.FOOD`.
5. 결정된 카테고리를 `TransactionIngest.category` 에 담아 ingest 흐름으로 넘긴다.

## ④ 핵심 코드 분석

### 1) MCC 범위 테이블

[category_engine.py:6-21](backend/app/services/category_engine.py:6)

```python
_MCC_MAP: dict[range, SpendCategory] = {
    range(5811, 5815): SpendCategory.FOOD,         # 레스토랑/카페
    range(5411, 5500): SpendCategory.FOOD,         # 식료품/마트
    range(5200, 5400): SpendCategory.SHOPPING,     # 의류/잡화
    range(5600, 5700): SpendCategory.SHOPPING,     # 의류
    range(5900, 6000): SpendCategory.SHOPPING,     # 기타 소매
    range(4011, 4800): SpendCategory.TRANSPORT,    # 교통/항공
    range(7800, 7999): SpendCategory.ENTERTAINMENT,
    range(7911, 7942): SpendCategory.ENTERTAINMENT,
    range(8200, 8300): SpendCategory.EDUCATION,
    range(8000, 8100): SpendCategory.HEALTHCARE,
    range(6000, 6200): SpendCategory.FINANCE,
    range(3000, 3500): SpendCategory.TRAVEL,
    range(7000, 7300): SpendCategory.TRAVEL,
    range(4900, 5000): SpendCategory.UTILITIES,
}
```

Python `range` 객체를 딕셔너리 키로 사용한다. 범위를 키로 쓰면 얼핏 이상해 보이지만, `in` 연산자(`mcc in mcc_range`) 가 `range.__contains__` 를 호출하기 때문에 동작은 올바르다. 성능도 문제없다 — 키 순회 횟수가 14번이라 선형 탐색이 실질적으로 O(1) 수준이다.

주목할 점은 `range(7800, 7999)` 와 `range(7911, 7942)` 가 **겹친다**. 딕셔너리를 삽입 순서대로 순회하므로 7800~7999가 먼저 매칭되고 7911~7942는 사실상 dead range다. 두 범위가 같은 카테고리(`ENTERTAINMENT`)를 가리키기 때문에 결과에는 영향이 없지만, 다른 카테고리로 나눠야 했다면 버그가 됐을 구조다.

### 2) 선형 탐색 — `classify_by_mcc()`

[category_engine.py:42-46](backend/app/services/category_engine.py:42)

```python
def classify_by_mcc(mcc: int) -> SpendCategory:
    for mcc_range, cat in _MCC_MAP.items():
        if mcc in mcc_range:
            return cat
    return SpendCategory.OTHER
```

`range.__contains__` 는 O(1)이지만 딕셔너리 전체를 순회해야 한다는 점에서 전체 복잡도는 O(n_ranges)다. 현재 14개 범위로는 무시할 수준이며, 100개를 넘기 전까지는 최적화 필요 없다.

### 3) 키워드 매칭 — `classify_by_keyword()`

[category_engine.py:49-54](backend/app/services/category_engine.py:49)

```python
def classify_by_keyword(text: str) -> SpendCategory:
    text_lower = text.lower()
    for keyword, cat in _KEYWORD_MAP.items():
        if keyword.lower() in text_lower:
            return cat
    return SpendCategory.OTHER
```

키워드와 입력 텍스트 모두 `.lower()` 처리하여 대소문자 차이를 흡수한다. 한국어는 대소문자가 없으므로 실질적으로는 영문 가맹점명("KT", "SKT") 을 위한 가드다. `keyword.lower() in text_lower` 는 부분 문자열 매칭이라 "스타벅스_강남" 처럼 접미사가 붙은 가맹점명도 "스타벅스" 키워드로 잡힌다.

현재 등록된 키워드는 17개 — 대형 플랫폼/통신사 위주의 고빈도 가맹점들이다.

### 4) 두 단계 결합 — `classify()`

[category_engine.py:57-64](backend/app/services/category_engine.py:57)

```python
def classify(mcc: int | None = None, text: str = "") -> SpendCategory:
    if mcc is not None:
        result = classify_by_mcc(mcc)
        if result != SpendCategory.OTHER:
            return result
    if text:
        return classify_by_keyword(text)
    return SpendCategory.OTHER
```

우선순위 로직이 명확하다: **MCC 있으면 MCC 먼저, MCC가 `OTHER`를 반환하면 텍스트로 보완, 둘 다 없으면 `OTHER`**. 호출자가 MCC만 알거나, 텍스트만 알거나, 둘 다 알거나 모두 이 함수 하나로 처리할 수 있다.

### 5) `SpendCategory` — `str, Enum` 의 선택

[spend.py:11-22](backend/app/schemas/spend.py:11)

```python
class SpendCategory(str, Enum):
    FOOD = "food"
    SHOPPING = "shopping"
    ...
    OTHER = "other"
```

`str, Enum` 다중 상속은 Pydantic과 JSON 직렬화 모두에서 이점이 있다. `SpendCategory.FOOD` 를 JSON으로 내보낼 때 `"FOOD"` 가 아닌 `"food"` 가 나오고, DB 저장 시 `.value` 를 별도로 꺼낼 필요가 없다 — [spend_profile_db.py:43](backend/app/services/spend_profile_db.py:43) 에서 `tx.category.value` 를 명시적으로 쓰지만, 사실 `category=tx.category` 로 써도 동작한다.

## ⑤ 설계 포인트

- **현재 호출 경로가 없다**: 코드베이스 전체를 검색하면 `category_engine` 이 임포트되는 곳이 없다. `ingest_transaction()` 은 이미 분류된 `category` 를 받아 저장하며, 시드 데이터([routes_seed.py:109](backend/app/api/routes_seed.py:109))는 `SpendCategory` 를 가중치 랜덤으로 직접 선택한다. 즉 엔진은 **준비됐지만 아직 배선되지 않은 상태**다. 카드사 API나 오픈뱅킹 연동 시 ingest 레이어에서 `classify()` 를 호출하는 글루 코드를 추가하는 것이 자연스러운 다음 단계.
- **MCC 범위 겹침 문제**: 앞서 설명한 `range(7800, 7999)` / `range(7911, 7942)` 겹침은 현재는 무해하지만, 향후 범위를 분리해 다른 카테고리에 배정할 때 실수가 발생할 수 있다. 딕셔너리 대신 정렬된 인터벌 리스트 + 이진탐색으로 구조를 바꾸면 겹침을 강제로 제거할 수 있다.
- **키워드 우선순위 없음**: `_KEYWORD_MAP` 은 순서 있는 dict지만, 매칭 우선순위가 명시적이지 않다. "배달의민족_쿠팡마트" 같이 두 키워드가 동시에 포함된 가맹점명은 삽입 순서대로 첫 번째 키워드가 이긴다. 현재 키워드 조합은 문제가 없지만, 키워드가 늘어날수록 이 암묵적 규칙이 관리 부담이 된다.
- **`OTHER` 의 두 의미**: `OTHER` 는 "분류 불가" 와 "호출자가 지정한 기타 카테고리" 를 동시에 의미한다. [routes_seed.py:139](backend/app/api/routes_seed.py:139) 에서 `cat if cat != SpendCategory.OTHER else SpendCategory.OTHER` 라고 아무 의미 없는 동일 분기가 남아있는 것도 이 모호함에서 비롯됐다.
- **확장 방향**: MCC 테이블 + 키워드 이후 다음 단계는 **가맹점명 임베딩 기반 유사도 분류**다. 등록되지 않은 신규 가맹점에 대한 `OTHER` 비율을 줄이는 데 효과적이며, 분류 결과를 `category_engine` 이 아닌 외부 모델 서비스로 위임하는 구조로 자연스럽게 이어진다.

### 예상 질문 & 답변 (발표 Q&A 대비)

**Q1. 왜 ML 분류기가 아닌 룰 기반인가요?**
> 거래 수집 경로는 **빠른 결정 속도와 100% 예측 가능한 동작**이 우선. MCC는 국제 표준 가맹점 코드라 결정적 분류 가능. ML은 결제 후 분석에서 활용(K-Means/XGBoost).

**Q2. MCC 코드가 없는 거래는?**
> 가맹점명/메모 키워드 fallback으로 분류. 키워드도 없으면 `OTHER`. 향후 LLM 임베딩으로 의미 기반 분류 추가 여지.

## ⑥ 한 줄 정리

PayWise의 카테고리 분류는 **MCC 범위 테이블 → 키워드 fallback** 의 두 단계 순수 함수로 구현됐으며, 현재는 ingest 경로에 아직 배선되지 않은 "준비된 컴포넌트" 상태다.
