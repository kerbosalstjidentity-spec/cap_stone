# #13 규칙 엔진 — ML 모델이 놓친 패턴을 잡는 10개 룰의 설계

## ① 개요

ML 모델은 학습 데이터에 없는 신종 사기 패턴에 취약하다. PayWise의 규칙 엔진은 "모델이 학습하기 전에도 알 수 있는" 명시적 조건들을 코드로 표현하고, 모델 점수와 나란히 평가한 뒤 더 강한 쪽을 최종 조치로 채택한다. 10개 규칙이 `Rule` 추상 클래스를 구현하는 전략 패턴으로 설계되어 있으며, 런타임 중 개별 규칙을 토글할 수 있다.

---

## ② 시스템 구성

```
[FraudServiceManager.get_rule_action()]
         │
         ├─ access_list.is_whitelisted()  ← 화이트리스트면 PASS, 규칙 생략
         │
         └─ rule_engine.evaluate_all(tx, profile)
                  │
                  ├─ BlacklistRule        → BLOCK  (user_id / IP 블랙리스트)
                  ├─ DeviceFingerprintRule→ REVIEW (디바이스 다중 계정)
                  ├─ AmountBlockRule      → BLOCK  (금액 ≥ 500만)
                  ├─ AmountReviewRule     → REVIEW (금액 ≥ 100만)
                  ├─ TimeRiskRule         → REVIEW (새벽 + 고액)
                  ├─ VelocityRule         → BLOCK  (10분 내 3건)
                  ├─ SplitTransactionRule → REVIEW (소액 5건 쪼개기)
                  ├─ ForeignIpRule        → REVIEW (해외 IP + 30만↑)
                  ├─ AmountSpikeRule      → SOFT_REVIEW (평균 5배 초과)
                  └─ NewMerchantRule      → SOFT_REVIEW (신규 가맹점)
                              │
                         get_strongest()  ← max(ACTION_RANK) 선택
                              │
                     (rule_action, rule_ids)
```

| 파일 | 역할 |
|---|---|
| `app/services/rule_engine.py` | 10개 규칙 정의 + RuleEngine 오케스트레이터 |
| `app/services/profile_store.py` | 사용자 거래 이력 + velocity 계산 (인메모리) |
| `app/services/access_list.py` | 블랙리스트 / 화이트리스트 저장소 |
| `app/services/policy_merge.py` | ACTION_RANK 상수 공유 |

## ③ 동작 흐름

```
1. FraudServiceManager.get_rule_action() 호출
2. access_list.is_whitelisted(user_id) 확인 → 화이트리스트면 ("PASS", "WHITELIST") 즉시 반환
3. profile_store.get_profile(user_id) 로 UserProfile 조회
   ↳ 이력 없으면 None — velocity 의존 규칙은 평가 건너뜀
4. rule_engine.evaluate_all(tx, profile) 에서 등록된 규칙 순서대로 평가
   ↳ 각 Rule.evaluate() 는 조건 미충족 시 None 반환 (발동 안 함)
   ↳ 발동 시 RuleResult(rule_id, action, detail) 반환
5. get_strongest(results) 에서 ACTION_RANK 기준 max action 선택
   ↳ 발동 규칙이 여러 개라도 가장 강한 action 하나로 수렴
6. 발동한 모든 rule_id 를 콤마로 연결해 감사 로그에 기록
7. FraudServiceManager.get_final_action() 에서 merge_actions(rule_action, model_action)
   → 모델/규칙 중 강한 쪽이 최종 조치
```

### 4-1. Rule 추상 클래스 + RuleResult

```python

    rule_id: str
    action: str

class Rule(ABC):
    rule_id: str
    enabled: bool = True

    @abstractmethod
    def evaluate(self, tx: dict[str, Any], profile: UserProfile | None) -> RuleResult | None:
        """발동 시 RuleResult 반환, 미발동 시 None."""
```

[rule_engine.py:25](fraud-service/app/services/rule_engine.py:25)

`None` 반환이 "미발동"을 뜻하는 패턴이다. `RuleEngine.evaluate_all` 이 None 이 아닌 것만 결과 목록에 모아 반환하므로, 개별 룰은 발동 여부 판단에만 집중하면 된다. `enabled` 플래그로 런타임 중 토글도 가능하다.

### 4-2. 규칙 10개 요약 — 조건과 action

| 규칙 | 발동 조건 | Action | 의존 |
|---|---|---|---|
| BlacklistRule | user_id 또는 IP가 블랙리스트에 존재 | BLOCK | access_list |
| DeviceFingerprintRule | 동일 device 60분 내 2개 이상 계정 | REVIEW | device_store |
| AmountBlockRule | 금액 ≥ 5,000,000원 | BLOCK | - |
| AmountReviewRule | 금액 ≥ 1,000,000원 | REVIEW | - |

| SplitTransactionRule | 금액 ≤ 100,000원 AND 1분 내 5건 | REVIEW | UserProfile |
| ForeignIpRule | 해외 IP AND 금액 ≥ 300,000원 | REVIEW | - |

### 4-3. `evaluate_all` + `get_strongest` — 전체 평가 흐름

```python
# rule_engine.py:280-298
def evaluate_all(self, tx, profile) -> list[RuleResult]:
    with self._lock:
        rules = list(self._rules)   # 스냅샷으로 복사해 락 범위 최소화
    results = []
    for rule in rules:
        res = rule.evaluate(tx, profile)
        if res is not None:
            results.append(res)
    return results

def get_strongest(self, results: list[RuleResult]) -> tuple[str, str]:
    if not results:
        return "PASS", ""
    best     = max(results, key=lambda r: ACTION_RANK.get(r.action, 0))
    rule_ids = ",".join(r.rule_id for r in results)
    return best.action, rule_ids
```

[rule_engine.py:280](fraud-service/app/services/rule_engine.py:280)

`evaluate_all` 내부에서 `list(self._rules)` 로 스냅샷을 만든 뒤 락을 해제하고 평가한다. 락을 평가 루프 전체에 걸면 토글이 블로킹되기 때문에, 복사 → 해제 → 루프 패턴이 의도적이다. 한 가지 트레이드오프: 스냅샷 이후 토글이 발생하면 이번 요청에는 반영되지 않는다.

`get_strongest` 는 발동된 모든 rule_id를 `,`로 묶어 반환한다. 감사 로그에서 "어떤 규칙들이 발동했는가"를 추적할 수 있다.

### 4-4. 시간 파싱 이중 경로 — TimeRiskRule

```python
# rule_engine.py:86-102
def evaluate(self, tx, profile):
    hour = tx.get("hour", -1)
    if hour == -1:                                   # hour 필드 없으면
        ts = tx.get("timestamp")
        if isinstance(ts, str):
            try:
                hour = datetime.fromisoformat(ts).hour  # timestamp 에서 파싱
            except ValueError:
                return None
        else:
            return None
    amount = float(tx.get("amount", 0))
    if self.start_hour <= hour < self.end_hour and amount >= self.amount_threshold:
        return RuleResult(self.rule_id, "REVIEW", f"새벽 {hour}시 {amount:,.0f}원")
    return None
```

[rule_engine.py:86](fraud-service/app/services/rule_engine.py:86)

`hour` 필드가 있으면 그것을, 없으면 `timestamp` 문자열을 파싱한다. 파싱 실패 시 조용히 `None` (미발동) 처리한다. 이 방어적 처리 덕분에 `hour` 필드를 보내지 않은 요청도 타임스탬프만 있으면 규칙이 작동한다.

### 4-5. Velocity 계산 — profile_store

VelocityRule과 SplitTransactionRule은 `profile.velocity` 를 읽는다.

```python
# profile_store.py:122-134
def _calc_velocity(self, history: list[TxRecord]) -> dict[str, int]:
    now    = datetime.now(tz=timezone.utc)
    result = {"1m": 0, "5m": 0, "15m": 0}
    for r in history:
        ts    = r.timestamp if r.timestamp.tzinfo else r.timestamp.replace(tzinfo=timezone.utc)
        delta = (now - ts).total_seconds() / 60
        if delta <= 1:  result["1m"] += 1
        if delta <= 5:  result["5m"] += 1
        if delta <= 15: result["15m"] += 1
    return result
```

[profile_store.py:122](fraud-service/app/services/profile_store.py:122)

history 전체를 매 요청마다 선형 순회(`O(N)`)해서 계산한다. `_MAX_HISTORY = 500` 으로 상한이 있어 최악의 경우도 500번 비교로 제한된다. 다만 `get_profile` 이 이미 history 를 복사한 뒤 `_calc_velocity` 를 호출하므로, velocity 만 필요한 경우에도 전체 프로파일이 계산된다.

### 4-6. VelocityRule의 window_key 버그

```python
# rule_engine.py:116-119
def evaluate(self, tx, profile):
    window_key = f"{self.window_minutes}m" if self.window_minutes in (1, 5, 15) else "5m"
    count = profile.velocity.get(window_key, 0)
    if count >= self.max_count:
        return RuleResult(self.rule_id, "BLOCK", f"{self.window_minutes}분 내 {count}건")
```

[rule_engine.py:116](fraud-service/app/services/rule_engine.py:116)

`window_minutes` 기본값은 `10`인데, `velocity` 딕셔너리에는 `"10m"` 키가 없다. `window_minutes not in (1, 5, 15)` 이면 fallback 으로 `"5m"` 을 읽는다. 결과적으로 10분 창으로 설정해도 5분 창 데이터를 평가하게 된다. 이 괴리는 `detail` 메시지("10분 내 N건")와 실제 계산 기준("5m")이 불일치하는 문제로 이어진다.

### 4-7. 블랙리스트 — user_id 또는 IP 즉시 차단

```python
# access_list.py:40-46
def is_blacklisted(self, user_id: str = "", ip: str = "") -> ListEntry | None:
    with self._lock:
        if user_id and (e := self._blacklist.get(f"user_id:{user_id}")):
            return e
        if ip and (e := self._blacklist.get(f"ip:{ip}")):
            return e
    return None
```

[access_list.py:40](fraud-service/app/services/access_list.py:40)

키를 `"user_id:{value}"` 형식으로 만들어 단일 dict 에 user_id 와 IP 두 종류를 함께 관리한다. 키 충돌 없이 두 차원을 하나의 컬렉션으로 처리하는 간단한 네임스페이싱이다.

### 4-8. 화이트리스트 — 규칙 전체 생략, 모델만 평가

```python
# fraud_service.py:39-46
def get_rule_action(self) -> tuple[str, str]:
    from app.services.access_list import access_list
    user_id = self.tx.get("user_id", "")
    if user_id and access_list.is_whitelisted(user_id):
        return "PASS", "WHITELIST"

```

[fraud_service.py:39](fraud-service/app/services/fraud_service.py:39)

화이트리스트 사용자는 룰 평가 자체를 건너뛴다. 규칙이 BLOCK 을 반환해도 모델 단독 판정만 남는다. 따라서 화이트리스트 사용자에게 모델 점수가 0.95 이상이면 여전히 BLOCK 된다 — 화이트리스트는 규칙 면제이지, 모델 면제가 아니다.

### 4-9. 런타임 토글 + 스레드 세이프

```python
# rule_engine.py:271-278
def toggle_rule(self, rule_id: str) -> bool | None:
    with self._lock:
        for r in self._rules:
            if r.rule_id == rule_id:
                r.enabled = not r.enabled
                return r.enabled
    return None
```

[rule_engine.py:271](fraud-service/app/services/rule_engine.py:271)

프로세스 재시작 없이 특정 규칙을 끌 수 있다. 예를 들어 ForeignIpRule 이 특정 국가의 정상 해외 출장자들을 과다 차단한다면, 운영팀이 API 한 번으로 해당 규칙만 비활성화할 수 있다. 다만 재시작하면 모두 `enabled=True` 로 초기화된다 — DB 또는 Redis 에 상태를 영속화하는 구조가 없다.

## ⑤ 설계 포인트 / 트러블슈팅 거리

- **VelocityRule window_key 불일치**: 기본 `window_minutes=10` 이지만 velocity 딕셔너리에 `"10m"` 키가 없어 fallback 으로 `"5m"` 데이터를 평가한다. `detail` 메시지는 "10분"이라 쓰면서 실제 판단은 5분 기준이 되는 논리 오류다. 해결책은 velocity 계산 창 목록을 확장하거나 `window_minutes` 기본값을 5로 맞추는 것이다.

- **velocity 계산의 매 요청 선형 순회**: `_calc_velocity` 는 최근 history 전체를 순회한다. 건수 상한이 500으로 고정이라 실용적으로는 문제가 없지만, 요청 빈도가 높아지면 누적 부하가 된다. sliding window counter (deque + 만료) 또는 Redis sorted set 으로 교체하면 O(1) 조회가 가능하다. (✅ ROADMAP W2-#7 — `_prune_expired` 로 60분 밖 record 만 amortized O(1) pop + `_count_within` 가 `bisect_left` 로 O(log N) 카운트. Redis 백엔드는 ZRANGEBYSCORE 로 동일 복잡도)

- **NewMerchantRule의 미흡한 merchant 이력 체크**: `tx_count <= 1` 이면 신규 merchant 로 간주한다. 전체 거래 수로 판단하기 때문에 거래가 2건 이상인 사용자가 처음 방문하는 가맹점에서 고액 결제를 해도 이 규칙은 발동하지 않는다. `UserProfile` 에 `known_merchants: set[str]` 필드를 추가하면 실제 첫 거래 가맹점 여부를 정확히 판단할 수 있다.

- **규칙 토글 상태 미영속**: `toggle_rule` 결과가 인메모리에만 남아 프로세스 재시작 시 초기화된다. 운영 중에 비활성화한 규칙이 배포 이후 자동 복구(재활성화)되어 예상치 못한 차단이 발생할 수 있다. Redis 또는 DB 기반 토글 상태 저장이 필요하다. (✅ ROADMAP W2-#4 — `rule:toggles` Redis Hash, 토글 시 즉시 영속화 + 엔진 init 시 자동 로드. 추가로 `evaluate_all`이 enabled=False 룰을 실제로 스킵하도록 누락된 분기 fix)

- **profile_store의 인메모리 구조**: velocity 계산의 기준이 되는 이력이 메모리에만 존재하므로, 서비스 재시작 또는 멀티 인스턴스 배포 시 히스토리가 초기화된다. 환경변수 `PROFILE_STORE=redis` 로 Redis 전환 코드가 미리 준비되어 있어([profile_store.py:139](fraud-service/app/services/profile_store.py:139)), 인터페이스는 동일하게 유지하면서 백엔드만 교체할 수 있다.

### 도메인 확장 로드맵 — 사기 유형별 룰셋 본격화

현재 10개 룰은 **금액·시간·빈도·해외 IP** 같은 일반 통계 이상치 위주로 짜여 있다. [#12 로드맵](12_실시간_사기_점수_IF_RF_하이브리드.md#도메인-확장-로드맵-이상-거래-스크리닝에서-fds로)에서 정의한 도메인 사기(보이스피싱·머니뮬·계정탈취) 검출에는 **사기 유형 특화 룰**과 **데이터 기반 임계값 학습**이 필요하다. 룰 엔진 자체의 운영 성숙도 트랙도 함께 정리한다.

#### Track A. 사기 유형 특화 룰 추가 (도메인 룰 7종)
- **결손**: 현재 룰은 "큰 금액", "야간", "고빈도" 같은 통계적 이상에만 반응. 사기 시나리오와의 1:1 대응 부재
- **추가 룰 후보**:

  | 룰 ID | 발동 조건 | 타깃 사기 유형 | Action |
  |---|---|---|---|
  | `VoicePhishingPatternRule` | 신규 수취인 + 거액(≥3M) + 야간 + 노인 사용자 (age≥60) | 보이스피싱 | BLOCK |
  | `MoneyMuleInOutRule` | 입금 직후 10분 내 동일 금액의 95%+ 출금 | 머니뮬 | REVIEW |
  | `ImpossibleTravelRule` | 직전 거래 IP 위치와 1시간 내 1000km↑ 이격 | 계정 탈취 | BLOCK |
  | `DormantAccountReactivationRule` | 30일 휴면 후 첫 거래가 거액 송금 | 계정 탈취 | REVIEW |
  | `RoundAmountMultipleRule` | 동일 금액 정수배(100/500/1000만) 다발 송금 | 자금세탁 계층화 | REVIEW |
  | `NewDeviceLargeTransferRule` | 신규 디바이스 첫 거래가 거액 + 신규 수취인 | 계정 탈취 | BLOCK |
  | `RapidFanOutRule` | 1시간 내 5명 이상 다른 수취인에게 송금 | 머니뮬 fan-out | REVIEW |

- (✅ ROADMAP W6.5-#3 — `MoneyMuleRule` (rule_id `MONEY_MULE_HUB`) 구현. 그래프 피처 `sender_fan_in_count ≥ 3` AND `sender_pass_through_ratio ≥ 0.8` 조건에서 BLOCK. `policy_merge.classify_fraud_type` 매핑 우선순위에 BLACKLIST 다음으로 등재. e2e: 4명에게 받은 후 90% 통과시킨 mule 의 추가 송금 → BLOCK + fraud_type=MONEY_MULE)
- (✅ ROADMAP W6.5-#4 — `LayeringRule` (rule_id `LAYERING_CHAIN`) 구현. hub 가 아닌 *체인* 패턴 검출 — `sender_pass_through_ratio ≥ 0.9` AND `sender_recent_inbound_min_ago ≤ 10분` AND `sender_fan_in_count < 3` (mule 룰 영역과 분리) → REVIEW. 새 그래프 피처 `sender_recent_inbound_min_ago` 추가. e2e: A→B→C 체인 시뮬레이션에서 B 의 다음 송금에서 발동 + fraud_type=MONEY_MULE)

- **코드 변경 위치**: [`rule_engine.py`](fraud-service/app/services/rule_engine.py) 룰 클래스 7개 추가 + `_DEFAULT_RULES` 등록. 일부 룰은 [`UserProfile`](fraud-service/app/services/profile_store.py) 에 `age` / `last_active_at` / `known_recipients: set[str]` 필드 확장 필요
- **의존성**: #12 Track 1 (PaySim) 또는 합성 라벨 데이터 — 임계값 검증용
- **작업량**: 룰당 0.5일 × 7 = 3~4일

#### Track B. 임계값 자동 튜닝 (하드코딩 → 학습)
- **결손**: `AmountBlockRule=5_000_000`, `AmountReviewRule=1_000_000` 같은 임계값이 코드 상수. 운영 데이터 분포를 반영하지 못함
- **추가**: 라벨 데이터에서 ROC/PR 커브 기반 최적 임계값 산출 → `SYSTEM_CONFIG` 에 주입. 룰별 정밀도/재현율을 [`stats_collector`](fraud-service/app/services/stats_collector.py) 에 누적해 주기적 재계산
- **부수 산출물**: 룰별 false positive rate 대시보드 — 운영팀이 "어떤 룰이 정상 거래를 과차단하는지" 즉시 확인
- **작업량**: 2일 (스크립트) + 대시보드 1일

#### Track C. 룰 가중 점수화 (binary fire → soft score)
- **결손**: 현재 `evaluate()` 는 발동/미발동 이진 결과. "조건은 일부만 맞지만 의심스러움" 같은 회색 영역 표현 불가
- **추가**: `RuleResult` 에 `confidence: float` 필드 추가. 예: `AmountReviewRule` 이 100만원에서 0.5, 300만원에서 1.0 식의 ramp 함수. `get_strongest` 대신 가중합 + threshold 정책 옵션 추가
- **장점**: 모델 점수와 같은 [0,1] 스케일이 되어 [`policy_merge`](fraud-service/app/services/policy_merge.py) 에서 가중 평균 정책으로 진화 가능
- **의존성**: Track B 선행 권장 (가중치 캘리브레이션을 위해)
- **작업량**: 3일

#### Track D. 룰 토글·임계값 영속화
- **결손**: `toggle_rule` 과 `SYSTEM_CONFIG` 가 인메모리 → 재시작 시 초기화되어 운영팀이 끈 룰이 자동 부활
- **추가**: Redis hash (`rule_engine:toggle:{rule_id} → bool`, `rule_engine:threshold:{rule_id} → float`) 로 영속화. 부팅 시 [`rule_engine.py`](fraud-service/app/services/rule_engine.py) 가 Redis 에서 상태 복원
- **작업량**: 1일

### 예상 질문 & 답변 (발표 Q&A 대비)

> 도메인 확장 관련 질문은 위 [도메인 확장 로드맵](#도메인-확장-로드맵-사기-유형별-룰셋-본격화) 절의 Q&A 매핑 참고.

**Q1. ML 점수만으로 충분하지 않나요? 왜 룰 엔진을 병행하나요?**
> ML 모델은 학습 데이터에 없는 신종 패턴에 취약하고, 학습되기 전에도 명백히 의심스러운 거래(예: 5초 내 동일 금액 5건)는 코드로 즉시 막을 수 있습니다. 또 룰은 **설명 가능성**이 명시적이라 사용자에게 "왜 차단되었는가"를 즉시 답할 수 있음.

**Q2. 새 룰 추가/수정은 어떻게 하나요?**
> `Rule` 추상 클래스를 상속해 `evaluate()`만 구현하면 됩니다. `_DEFAULT_RULES`에 등록하면 자동 평가에 합류. 전략 패턴이라 한 룰의 변경이 다른 룰에 영향 없음. 핫 토글(`/admin/rules/toggle`)도 가능.

**Q3. 룰 우선순위는 어떻게 정했나요?**
> `ACTION_RANK = {PASS: 0, SOFT_REVIEW: 1, REVIEW: 2, BLOCK: 3}`. 여러 룰이 동시 발동하면 max(rank)로 가장 강한 action을 따릅니다. 룰별 가중치는 없고 단순 max-rank — 단순함의 대가로 false positive가 BLOCK까지 끌어올릴 위험.

**Q4. False positive(정상 거래 차단)는 어떻게 관리하나요?**
> ① 룰 토글로 즉시 비활성화, ② `stats_collector`에 룰별 발동 통계 누적, ③ 화이트리스트 우회. 다만 ⑤절 지적대로 **토글 상태가 인메모리**라 재시작 시 초기화되는 게 약점. Redis 영속화는 [도메인 확장 로드맵 Track D](#track-d-룰-토글임계값-영속화)에서 처리.

**Q5. 룰이 너무 단순하지 않나요? ML로 룰을 학습할 수는 없나요?**
> 가능합니다 — 결정 트리에서 룰 추출(rule extraction)이나 RuleFit 같은 알고리즘이 후보. 다만 본 시스템은 "운영 명시성"을 우선해 사람이 작성한 휴리스틱 + 향후 [Track C soft scoring](#track-c-룰-가중-점수화-binary-fire--soft-score)으로 ML 점수와 같은 [0,1] 스케일로 진화 예정.

## ⑥ 한 줄 정리

ML 모델이 확률로 답하기 어려운 "명시적 사기 신호"를 10개 전략 규칙으로 포착하고, 모델 action과 max-rank 병합으로 조합하여 — 모델 단독 또는 규칙 단독보다 강한 다층 방어선을 구성한다.
