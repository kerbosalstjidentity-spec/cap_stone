# #22 모델 평가 — SRS 검증 대시보드: 벤치마크·위협 테스트·컴플라이언스

## ① 개요

PayWise의 마지막 기능은 시스템 전체를 자기 자신으로 평가하는 **SRS 검증 대시보드**다. `/v1/evaluation` 라우터는 네 가지 성능 벤치마크, 네 가지 위협 시나리오, GDPR/금융보안원/전자금융거래법을 포함한 규제 준수 체크리스트를 HTTP 요청 한 번으로 실행하고 반환한다. 핵심 로직은 `fds_scripts/evaluation_suite.py`에 집중되어 있으며, `routes_evaluation.py`는 이를 API로 래핑하는 얇은 어댑터다.

> **구현 실태**: 벤치마크와 위협 시나리오 테스트는 **실제 PayWise 컴포넌트(blockchain_audit, abac_engine, fraud_service 등)를 호출하지 않는다**. 대신 SHA-256/HMAC 연산을 인-프로세스에서 반복해 timing을 측정하거나, Python 딕셔너리 캐시로 nonce 검증을 시뮬레이션한다. 즉 "ABAC 접근 제어가 5000번 평가에 X ms 걸린다"는 결과는 fraud-service의 `abac_engine.evaluate()`가 아니라 local 시뮬레이션의 측정값이다. 규제 준수 체크리스트는 IMPLEMENTED/SIMULATED/DESIGNED 세 단계로 정직하게 자체 평가하며, "외부 감사를 대체하지 않는다"고 명시한다.

## ④ 핵심 코드 분석

### 4-1. 벤치마크 — 프로토콜 대신 SHA-256 timing 측정

```python
# evaluation_suite.py:29-58 (blockchain_vs_central 요약)
# 중앙형: MD5 dict 생성
for i in range(n_transactions):
    _ = {"tx_id": f"TX-{i}", "hash": hashlib.md5(str(i).encode()).hexdigest()}

# 블록체인: SHA256 해시 체인
prev = "0" * 64
for i in range(n_transactions):
    data = json.dumps({"tx_id": f"TX-{i}", "prev": prev}, sort_keys=True)
    prev = hashlib.sha256(data.encode()).hexdigest()
```

[evaluation_suite.py:29](fds_scripts/evaluation_suite.py:29)

**측정하는 것**: MD5 vs SHA256의 해시 연산 속도 차이.  
**측정하지 않는 것**: 실제 fraud-service의 `blockchain_audit.append_block()`과 그에 수반되는 파일 I/O·체인 직렬화·Merkle 계산.

`overhead_pct`는 SHA256이 MD5보다 얼마나 느린지를 나타낼 뿐이며, "PayWise의 블록체인 감사가 중앙형 대비 몇 % 오버헤드인지"가 아니다. 이 수치를 SRS 성능 목표와 비교하는 것은 맥락 오류다.

### 4-2. 위협 테스트 — 암호 수학 검증, 시스템 통합 테스트 아님

```python
# evaluation_suite.py:209-239 (replay attack 요약)
nonce_cache: set[str] = set()
for _ in range(n_trials):
    nonce = secrets.token_hex(16)
    if nonce not in nonce_cache:
        first_accepted += 1
        nonce_cache.add(nonce)
    if nonce in nonce_cache:
        replays_blocked += 1

status = "PASS" if (first_accepted == n_trials and replays_blocked == n_trials) else "FAIL"
```

[evaluation_suite.py:209](fds_scripts/evaluation_suite.py:209)

이 테스트는 Python `set`의 hash collision 확률이 0임을 확인하는 것이다. `secrets.token_hex(16)`으로 생성된 nonce 1000개 모두 set에 들어가고, 같은 nonce는 다시 set에 들어가지 않는다는 것은 수학적으로 자명하다. **항상 PASS** 다. "PayWise의 JWT nonce 검증 코드가 리플레이 공격에 안전한가"는 이 테스트가 알려주지 않는다. 실제 `/v1/auth/login` 엔드포인트에 동일 요청을 두 번 보내는 통합 테스트가 필요하다.

`test_insider_threat_defense`도 같은 패턴이다: SHA-256의 preimage 저항성(무작위 추측이 충돌하지 않음)과 HMAC 변조 탐지를 확인한다. 이것은 암호 알고리즘 속성이지 PayWise 구현의 속성이 아니다.

### 4-3. 컴플라이언스 체크리스트 — 3단계 정직 자체 평가

```python
# evaluation_suite.py:383-412 (일부)
{"item": "가명처리 (Pseudonymization)", "srs": "SRS 1,5,8",
 "status": "SIMULATED",
 "implementation": "PID 생성 API 존재 — 자동 로테이션 미구현",
 "limitation": "PID 인메모리 저장, 로테이션 스케줄러 없음"},

{"item": "데이터 삭제권 (Right to Erasure)", "srs": "SRS 5,9",
 "status": "DESIGNED",
 "implementation": "동의 철회 API 존재",
 "limitation": "실제 데이터 삭제 트리거 미연결"},
```

[evaluation_suite.py:401](fds_scripts/evaluation_suite.py:401)

**IMPLEMENTED / SIMULATED / DESIGNED** 세 단계 구분이 이 프로젝트에서 가장 솔직한 자기 평가다. 각 항목에 `limitation` 필드가 있어 "무엇이 안 됐는지"를 명시한다. 예: PID는 인메모리라 재시작 시 소실, 삭제권은 API만 있고 실제 삭제 미연결.

15개 항목 집계 결과: IMPLEMENTED 6개(40%), SIMULATED 7개(46.7%), DESIGNED 2개(13.3%). `production_ready_rate = 40.0%`, `coverage_rate = 86.7%`.

### 4-4. sys.path 조작 — 컨테이너 경로 의존

```python
# routes_evaluation.py:15-17
_fds_dir = str(Path(__file__).resolve().parent.parent.parent.parent / "fds_scripts")
if _fds_dir not in sys.path:
    sys.path.insert(0, _fds_dir)

from evaluation_suite import (...)
```

[routes_evaluation.py:15](backend/app/api/routes_evaluation.py:15)

`routes_evaluation.py`의 위치: `backend/app/api/routes_evaluation.py` → `.parent` 4번 올라가면 프로젝트 루트 → `/fds_scripts` 경로를 동적으로 추가한다. `fds_scripts/evaluation_suite.py`가 프로젝트 루트에 존재하므로 docker-compose 마운트 환경에서는 동작한다. 그러나 **`evaluation_suite.py`를 Python 패키지가 아닌 `sys.path` 조작으로 임포트**하기 때문에, 테스트 환경이나 다른 디렉터리에서 실행하면 `ModuleNotFoundError`가 난다. `fds_scripts`를 `pyproject.toml`에 패키지로 등록하거나, 코드를 backend 패키지 내부로 이동하는 것이 더 견고하다.

## ⑤ 설계 포인트 / 트러블슈팅 거리

- **위협 테스트 4개 모두 항상 PASS**: 테스트 로직이 암호 알고리즘의 수학적 속성(SHA256 preimage 저항, HMAC 불가위조)을 확인하는 것이라 결과가 결정론적이다. 코드 경로를 바꿔도, PayWise의 실제 인증/거래 흐름에 취약점이 생겨도 이 테스트는 항상 PASS를 반환한다. 진짜 보안 검증은 `httpx.AsyncClient`로 실제 엔드포인트에 요청을 보내는 통합 테스트나 SAST/DAST 도구를 통해야 한다.

- **`run_full_evaluation` 의 존재하지 않는 key 참조 버그**: 직접 실행 시 호출되는 `run_full_evaluation()` 함수 내부에서 `summary['compliance_rate']` 를 두 번 참조하지만([evaluation_suite.py:524-525](fds_scripts/evaluation_suite.py:524)), `generate_compliance_checklist()`가 반환하는 dict의 summary 에는 `compliance_rate` 키가 없다 — 실제 키는 `production_ready_rate` 와 `coverage_rate` 다. CLI 실행 시 `KeyError: 'compliance_rate'` 로 스크립트가 종료된다. API 경로는 `run_full_evaluation`을 호출하지 않아 영향을 받지 않는다.

- **`/v1/evaluation/full` 이 모든 연산을 동기 순차 실행**: `test_insider_threat_defense`는 SHA-256 preimage를 100 × 100 = 10,000번 계산한다. 서버 부하가 높은 상태에서 이 엔드포인트를 반복 호출하면 100ms+ 단위의 이벤트루프 블로킹이 발생한다. `asyncio.to_thread`로 감싸거나, 캐싱(`functools.lru_cache`, TTL 설정)으로 반복 실행을 줄이는 것이 권장된다.

- **벤치마크 결과가 환경에 따라 달라진다**: SHA256 1000회 timing은 CPU 성능·캐시 상태·Python GIL 경합에 따라 편차가 크다. 동일 환경에서도 10% 이상 변동이 생긴다. 운영자가 "이번 배포 후 `blockchain_vs_central` overhead가 늘었다"고 오판할 수 있다. 측정 환경(CPU 코어 수, warm-up 여부)을 응답에 함께 기록하거나, 절대 수치 대신 반복 측정 평균과 표준편차를 제공해야 한다.

- **컴플라이언스 `IMPLEMENTED` 분류 과대 계상 가능성**: 체크리스트는 정적 dict이므로 코드가 변경되어도 status가 자동 갱신되지 않는다. 예를 들어 #15에서 확인했듯 `ABACEngine.evaluate()`는 미들웨어에서 실제로 호출되지 않는데, "ABAC 8-룰 엔진 (직급+위치+시간+기기)" 항목은 `IMPLEMENTED`로 표기되어 있다. 체크리스트가 코드 실태를 자동 반영하려면 각 항목에 연결된 통합 테스트 통과 여부를 status로 삼는 CI 파이프라인이 필요하다.

### 예상 질문 & 답변 (발표 Q&A 대비)

**Q1. 벤치마크가 실제 시스템 호출이 아니라 SHA-256 1000회 측정이라는 게 무슨 뜻?**
> ⑤절·#4와 같은 시뮬레이션 패턴. 실제 ABAC/ABE 호출 path를 instrumentation해서 real latency를 측정하는 게 정직한 벤치마크. 후속 작업.

**Q2. 자체 평가 컴플라이언스를 외부 기관이 인정하나요?**
> 자체 시뮬레이션은 **외부 감사를 대체하지 않는다**고 코드와 응답에 명시. 진짜 인증은 KISA·금융보안원 외부 감사 필요. 발표에선 "내부 자체 평가 체계"로 한정.

## ⑥ 한 줄 정리

SHA-256/HMAC 인-프로세스 시뮬레이션으로 4종 벤치마크와 4종 위협 테스트를 항상-PASS로 반환하고, IMPLEMENTED/SIMULATED/DESIGNED 3단계로 자체 평가하는 SRS 검증 대시보드 — 위협 테스트가 실제 시스템 통합 경로를 건드리지 않아 진짜 보안 검증이 아니고, 컴플라이언스 status는 코드 변경에 자동 동기화되지 않는다.
