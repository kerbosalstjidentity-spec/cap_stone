# #18 A/B 테스트 (모델 비교) — Shadow 평가로 운영 트래픽을 보호하면서 신모델을 검증한다

## ① 개요

새 사기 탐지 모델을 학습했다. 곧바로 프로덕션에 올렸다가 false positive가 폭증하면 정상 결제까지 차단되는 사고가 난다. 그렇다고 오프라인 테스트셋만으로 검증하면 실제 트래픽 분포와의 괴리가 남는다. `app/scoring/ab_test.py`는 이 딜레마를 **shadow 평가 + 점진적 트래픽 라우팅** 두 단계로 해소한다. A 모델(현행 운영)과 B 모델(후보)을 같은 거래에 동시에 적용하되, 응답에 사용되는 점수는 A 또는 환경변수로 지정한 비율의 B만 사용한다. tx_id 해시 기반 결정적 라우팅으로 동일 거래는 항상 같은 분기에 들어간다. 단, 현재 구현은 모듈만 존재하고 **`shadow_evaluate()`가 실제 평가 파이프라인에 연결되어 있지 않은** 절반 완성 상태다.

## ③ 동작 흐름

```
[설계상 의도된 흐름]
1. 서비스 부팅 시 MODEL_B_PATH 로 두 번째 모델 번들 로드
2. /v1/evaluate 요청 도착 → FraudService 가 X 피처 벡터 구성
3. shadow_evaluate(tx_id, X, bundle_a, bundle_b) 호출
4. 두 모델 모두로 예측 (병렬 가능, 현재는 순차)
5. _route_to_b(tx_id) 가 결정적으로 True/False 반환
   - tx_id MD5 → 16진수 정수 → mod 100 → AB_TRAFFIC_PCT 미만이면 B
6. serving 변수에 따라 final_score 결정
7. _record(serving, action) 으로 통계 누적
8. 운영자가 /api/ab-stats 로 두 모델의 PASS/REVIEW/BLOCK 분포 비교

[현재 실제 흐름]
1~2. 동일
3. shadow_evaluate() 가 정의만 되어있고 호출되지 않음 ← 갭
4~7. 발생 안 함
8. /api/ab-stats 는 항상 빈 딕셔너리 반환
```

## ④ 핵심 코드 분석

### 4-1. tx_id 해시 기반 결정적 라우팅

```python
# ab_test.py:26-31
def _route_to_b(tx_id: str) -> bool:
    """tx_id 해시 기반 결정적 라우팅."""
    if _TRAFFIC_PCT <= 0:
        return False
    h = int(hashlib.md5(tx_id.encode()).hexdigest(), 16) % 100
    return h < _TRAFFIC_PCT
```

[ab_test.py:26](fraud-service/app/scoring/ab_test.py:26)

**왜 random이 아니라 해시인가**: 같은 `tx_id`는 재시도되어도 동일한 분기에 들어간다. 사용자가 결제를 재시도했을 때 첫 번째는 A로, 두 번째는 B로 평가되어 결과가 달라지면, 운영자가 "왜 결과가 바뀌었나" 디버깅이 불가능하다. MD5 해시는 암호 강도가 약하지만 라우팅 분포 균등성에는 충분하다.

**경계값 처리**: `_TRAFFIC_PCT=0`이면 즉시 False 반환 — `bundle_b`를 로드해도 shadow 비교만 수행하고 응답에는 항상 A를 쓴다. `_TRAFFIC_PCT=100`이면 모든 트래픽이 B로 간다.

### 4-2. shadow 평가 — 두 모델 동시 호출

```python
# ab_test.py:44-74
def shadow_evaluate(tx_id, X, bundle_a, bundle_b) -> dict[str, Any]:
    import numpy as np

    def _predict(bundle: dict) -> float:
        model = bundle.get("model")
        if model is None:
            return 0.0
        proba = model.predict_proba(X)
        return float(np.asarray(proba).ravel()[0])

    score_a = _predict(bundle_a)
    score_b = _predict(bundle_b) if bundle_b else None

    serving = "b" if (_route_to_b(tx_id) and bundle_b is not None) else "a"
    final_score = score_b if serving == "b" else score_a

    return {
        "score_a": round(score_a, 6),
        "score_b": round(score_b, 6) if score_b is not None else None,
        "serving": serving,
        "score": final_score,
    }
```

[ab_test.py:44](fraud-service/app/scoring/ab_test.py:44)

**`.ravel()[0]` 의 함정**: `predict_proba`는 sklearn에서 `(n_samples, n_classes)` 형태로 반환된다. 이진 분류에서 보통 `proba[:, 1]`(positive 클래스 확률)을 사용하는데, `ravel()[0]`은 첫 번째 샘플의 **negative 클래스(class 0) 확률**을 가져온다. 이게 의도라면 점수가 "정상 확률"이 되고, 의도가 아니라면 모든 점수가 뒤집혀 BLOCK/PASS 판정이 정반대가 된다. `ensemble.py`(#12)에서는 `model.predict_proba(X)[:, 1]`을 쓰므로 일관성이 깨진다.

**병렬화 누락**: A와 B 예측이 순차 호출이다. XGBoost 한 번 추론이 보통 1~5ms이지만, 두 모델 합치면 P99 지연이 2배가 된다. `concurrent.futures.ThreadPoolExecutor`로 묶으면 latency를 한쪽 모델 수준으로 유지할 수 있다.

### 4-3. 액션 카운터의 모호한 키 정규화

```python
# ab_test.py:34-41
def _record(variant: str, action: str) -> None:
    with _lock:
        _stats[variant]["count"] += 1
        key = action.lower().replace("_review", "").replace("soft_", "")
        if key in ("block", "review", "pass"):
            _stats[variant][key] += 1
        elif "review" in action.lower():
            _stats[variant]["review"] += 1
```

[ab_test.py:34](fraud-service/app/scoring/ab_test.py:34)

`action`은 #12에서 본 4단계 — `BLOCK`, `REVIEW`, `SOFT_REVIEW`, `PASS` — 가 들어올 자리다. 정규화 로직:

| 입력 action | `replace("_review","")` | `replace("soft_","")` | 최종 key | 카운트 |
|---|---|---|---|---|
| `BLOCK` | `block` | `block` | `block` | block+1 |
| `REVIEW` | `""` | `""` | `""` | 첫 if 통과 못함, elif 분기 → review+1 |
| `SOFT_REVIEW` | `soft_` | `""` | `""` | 첫 if 통과 못함, elif 분기 → review+1 |
| `PASS` | `pass` | `pass` | `pass` | pass+1 |

결과적으로 `REVIEW`와 `SOFT_REVIEW`가 같은 `review` 카운터에 합산된다. **위험 수준이 다른 두 액션이 통계상 구분되지 않는다.** 운영자가 신모델의 SOFT_REVIEW 비율 변화를 보고 싶어도 데이터가 없다. `_stats` 스키마에 `soft_review` 키를 별도로 두는 편이 모델 비교 분석에 훨씬 유용하다.

### 4-4. 모듈 로드 시점 환경변수 캡처

```python
# ab_test.py:19-20
_MODEL_B_PATH = os.getenv("MODEL_B_PATH", "")
_TRAFFIC_PCT = int(os.getenv("AB_TRAFFIC_PCT", "0"))
```

[ab_test.py:19](fraud-service/app/scoring/ab_test.py:19)

환경변수가 **모듈 import 시점에 한 번만 읽힌다**. `AB_TRAFFIC_PCT`를 운영 중 동적으로 조정하려면 프로세스를 재시작해야 한다. 카나리 트래픽 비율을 5% → 10% → 25%로 점진적 확대하는 표준 A/B 운영 시나리오에서 매번 프로세스 재시작은 부담이다. `_route_to_b` 안에서 매번 `os.getenv`를 읽거나, 관리 API로 갱신 가능한 모듈 레벨 setter를 두는 편이 유연하다. `_TRAFFIC_PCT` 음수/100 초과값에 대한 입력 검증도 없다.

## ⑤ 설계 포인트 / 트러블슈팅 거리

- **shadow_evaluate가 어디서도 호출되지 않는다**: `routes_fraud.py`나 `FraudService._evaluate_one`은 `ensemble.compute_score`만 사용한다. `ab_test.shadow_evaluate`를 임포트조차 하지 않는다. `_record()`도 호출 지점이 없어 `_stats`는 영원히 비어 있다. 운영자가 `/api/ab-stats`를 호출해도 `{}`만 돌아온다. **모듈 단위 테스트는 가능하지만 실제 카나리 배포에는 활용 불가능**한 절반 구현 상태다. wiring 작업: ① `FraudService.__init__`에서 `MODEL_B_PATH` 번들 로드, ② `_evaluate_one`에서 `compute_score` 대신 `shadow_evaluate` 호출, ③ 액션 결정 직후 `_record(result["serving"], final_action)` 추가.

- **A/B 분기가 "모델"만 비교하고 임계값은 공유한다**: `shadow_evaluate`는 점수만 두 모델로 다르게 산출하지만, 그 뒤에 적용되는 BLOCK/REVIEW 임계값(0.95/0.35/0.005)은 동일하다. 신모델의 점수 분포가 A와 다르면(예: B가 전체적으로 낮은 점수를 출력) 같은 임계값 적용 시 BLOCK률이 폭락할 수 있다. 모델 번들에 임계값까지 포함시켜 페어로 비교해야 공정한 A/B가 된다.

- **승자 판정 메트릭이 없다**: `_stats`는 단순히 PASS/REVIEW/BLOCK 카운트만 누적한다. A/B 테스트의 본질 — "어느 모델이 더 정확한가" — 를 판정하려면 ground truth(실제 사기 여부) 라벨과의 매칭 후 precision/recall 비교가 필요하다. 현재 구조에서는 두 모델의 액션 분포 차이만 볼 수 있을 뿐, "B가 진짜 더 좋은가"에 답할 수 없다. chargeback 결과를 콜백으로 받아 라벨링하는 별도 파이프라인 필요.

- **MD5 충돌은 분포에 영향 없음, 다만 보안 의미는 0**: `hashlib.md5`는 암호적으로 깨졌지만 라우팅 분포 균등성에는 문제없다. 단, 누군가 `_TRAFFIC_PCT=5`인 상태에서 의도적으로 B에 들어가는 tx_id를 만들고 싶다면 brute-force 가능하다. 외부에서 tx_id를 통제할 수 있는 환경이라면 공격자가 의도적으로 신모델만 타겟팅해 약점을 탐색할 수 있다. 서버 측 시크릿을 섞은 HMAC으로 라우팅 키를 만들면 예측 불가능해진다. (✅ ROADMAP W7-#8 — `AB_HMAC_SECRET` env 설정 시 `hmac.new(secret, tx_id, sha256)` 기반 라우팅, 미설정 시 기존 MD5 폴백)

- **score_b 가 None일 때 routing이 자동 fallback**: `serving = "b" if (_route_to_b(tx_id) and bundle_b is not None) else "a"` — `bundle_b`가 None이면 무조건 A로 라우팅된다. 이는 안전한 default이지만, **B 모델 로드 실패가 조용히 묻힌다**. 운영자가 "B로 5%가 가야 한다"고 설정했는데 실제로는 0%라는 사실을 통계에서밖에 알 수 없다. 부팅 시 `bundle_b is None and _MODEL_B_PATH != ""`이면 ERROR 로그를 남겨야 한다.

(✅ ROADMAP W7-#6 — `_evaluate_one` 끝에 `ab_test._record(variant, final_action)` 호출, `routes_score.py /v1/score` 가 `MODEL_B_PATH` 설정 시 `shadow_evaluate` 호출하여 `score_a/score_b/serving` 응답 노출)

### 예상 질문 & 답변 (발표 Q&A 대비)

**Q1. shadow_evaluate가 wiring 안 됐다는데 동작은 하나요?**
> 모듈은 완성됐지만 실제 평가 파이프라인(`_evaluate_one`)에 연결돼 있지 않아 현재 호출되지 않습니다. 즉 "절반 완성". 발표 슬라이드 8 "진행 중" 항목으로 표기하고, 5~6월 wiring 후속 작업.

**Q2. 결정적 해시 라우팅이 왜 필요한가요?**
> 같은 거래가 호출마다 다른 모델로 갈리면 사용자 경험이 일관되지 않음. tx_id 해시 % 100 < AB_TRAFFIC_PCT 라우팅으로 동일 거래 항상 같은 분기 보장.

## ⑥ 한 줄 정리

같은 tx_id는 항상 같은 분기로 가는 결정적 해시 라우팅 + shadow 평가로 두 모델을 동시 검증하는 A/B 프레임워크 — 단, `shadow_evaluate`가 실제 평가 파이프라인에 wiring되어 있지 않고 SOFT_REVIEW가 REVIEW와 합쳐 집계되어 현재는 운영 가능한 상태가 아니다.
