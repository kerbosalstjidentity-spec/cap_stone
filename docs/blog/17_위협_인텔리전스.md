# #17 위협 인텔리전스 — CP-ABE로 암호화된 기관 간 사기 패턴 공유

## ① 개요

은행 A가 발견한 신종 피싱 패턴을 은행 B와 공유하고 싶다. 그런데 모든 기관에 다 공개하면 공격자도 알게 된다. 위협 인텔리전스 모듈은 이 딜레마를 **CP-ABE 접근 구조식**으로 풀어낸다. 패턴의 공개 요약(summary)은 누구나 볼 수 있지만, 구체적인 IoC(indicator of compromise)나 시그니처(detail)는 게시자가 지정한 속성 조건을 만족하는 기관만 열람할 수 있다. 파일 주석에는 "Layer 5 — ABE 암호화 사기 인텔리전스 공유 API"로 명시되어 있으며, 앞서 분석한 ABE 엔진(#15)의 `evaluate_access_structure`를 직접 활용한다.

> **구현 실태**: 실제 데이터 암호화는 수행되지 않는다 — `IntelligenceEntry.detail` 은 평문 dict 그대로 인메모리에 보관되며 ([intelligence_store.py:64](fraud-service/app/services/intelligence_store.py:64)), 접근 제어는 조회 시점의 `evaluate_access_structure()` 결과로 detail 필드를 `[ENCRYPTED: …]` 문자열로 치환할지 여부만 결정한다. 따라서 본 모듈은 CP-ABE의 진의(데이터 자체에 정책을 묶은 암호문)에 비해 **접근 정책 평가 시뮬레이션** 수준이며, 메모리 덤프 또는 직렬화 파일에 직접 접근하면 모든 detail이 평문으로 노출된다. #15에서 분석한 ABE 엔진의 한계(charm-crypto 미도입, HMAC+AES-GCM 경량 구현)가 그대로 이어진다.

## ② 시스템 구성

```
게시 기관
  │
  │  POST /v1/intelligence/publish
  │  { publisher_institution, pattern_type, summary,
  │    access_policy, detail, tags }
  ▼
┌──────────────────────────────────────────────┐
│  IntelligenceStore (intelligence_store.py)    │
│                                              │
│  _entries: list[IntelligenceEntry]           │
│  ├─ entry_id   INTEL-000001                 │
│  ├─ summary    (비암호화, 공개)              │
│  ├─ access_policy  "(role:analyst AND …)"   │
│  └─ detail     { ioc_list, … }  ← 정책 가드│
└──────────────────┬───────────────────────────┘
                   │
  GET /v1/intelligence/query?pattern_type=BLACKLIST
                   │
                   ▼
┌──────────────────────────────────────────────┐
│  evaluate_access_structure(policy, user_attrs)│
│  (abe_engine.py:166)                         │
│                                              │
│  has_access = True  → detail 원본 반환       │
│  has_access = False → "[ENCRYPTED: …]"       │
└──────────────────────────────────────────────┘
                   │
               조회 기관
```

|---|---|

| `app/services/intelligence_store.py` | In-memory 저장소 + 접근 필터링 |
| `app/services/abe_engine.py` | `evaluate_access_structure` 제공 |

**패턴 유형 4종:**

| pattern_type | 의미 |
|---|---|
| `BLACKLIST` | 차단 대상 IP·계좌·디바이스 목록 |

## ③ 동작 흐름

```
[게시 흐름]
1. POST /v1/intelligence/publish 수신
2. IntelligenceStore.publish() 호출
3. threading.Lock 획득 → _counter 증가 → entry_id 생성
4. IntelligenceEntry 객체 생성 (detail 을 평문 그대로 저장)
5. _entries 에 append → Lock 해제
6. { status: "published", entry_id, published_at } 반환

[조회 흐름]
1. GET /v1/intelligence/query 수신
2. ABE 미들웨어가 request.state.abe_attrs 에 속성 주입
3. attrs dict → "key:value" 형식의 set 으로 변환
4. IntelligenceStore.query(user_attrs, pattern_type, tag) 호출
5. Lock 내에서 _entries 순회
   5a. pattern_type / tag 필터 적용
   5b. evaluate_access_structure(entry.access_policy, user_attrs) 호출
   5c. has_access=True → detail 원본, False → "[ENCRYPTED: …]"
6. { total, accessible, entries } 반환
```

## ④ 핵심 코드 분석

### 4-1. 게시 — entry_id 채번과 잠금 범위

```python
# intelligence_store.py:52-65
def publish(self, ...) -> IntelligenceEntry:
    with self._lock:
        self._counter += 1
        entry = IntelligenceEntry(
            entry_id=f"INTEL-{self._counter:06d}",
            ...
            published_at=datetime.now(tz=timezone.utc).isoformat(),
        )
        self._entries.append(entry)
        return entry
```

[intelligence_store.py:52](fraud-service/app/services/intelligence_store.py:52)

`_counter` 증가와 `_entries.append`가 같은 Lock 블록 안에 있어 경쟁 조건(race condition)이 없다. 단, `published_at` 타임스탬프도 Lock 내부에서 생성되므로, 고부하 상황에서 여러 게시 요청이 순차 처리되면 타임스탬프 간격이 실제 요청 도착 순서와 다소 다를 수 있다.

### 4-2. 조회 — 속성 변환과 접근 필터링

```python
# routes_intelligence.py:56-62
attrs = getattr(request.state, "abe_attrs", {})
if isinstance(attrs, dict):
    user_attrs = {f"{k}:{v}" for k, v in attrs.items()}
else:
    user_attrs = set()
```

[routes_intelligence.py:56](fraud-service/app/api/routes_intelligence.py:56)

ABE 미들웨어가 `request.state.abe_attrs`를 `{"role": "analyst", "dept": "fraud_team"}` 형태로 주입하면, 라우터가 `{"role:analyst", "dept:fraud_team"}` set으로 변환해 `evaluate_access_structure`에 전달한다. 미들웨어가 없거나 속성이 dict가 아니면 빈 set이 되어 **모든 패턴의 detail이 `[ENCRYPTED: …]`로 차단**된다.

### 4-3. 접근 제어 — evaluate_access_structure

```python
# intelligence_store.py:82-93
has_access = evaluate_access_structure(entry.access_policy, user_attrs)
item = {
    ...
    "detail": entry.detail if has_access else "[ENCRYPTED: 접근 권한 부족]",
    "has_access": has_access,
}
```

[intelligence_store.py:82](fraud-service/app/services/intelligence_store.py:82)

`evaluate_access_structure`는 `"(role:analyst OR role:admin) AND dept:fraud_team"` 형식의 불리언 식을 `AccessTree`로 빌드해 평가한다. 빌드 실패 시 `eval()` fallback이 호출된다(#15에서 분석한 RCE 위험 동일하게 적용).

**와일드카드 예시:**
```
access_policy = "role:* AND dept:fraud_team"
→ role 속성이 어떤 값이든 fraud_team 소속이면 접근 허용
```

### 4-4. 응답 구조 — 접근 가능 수 집계

```python
# routes_intelligence.py:63-68
results = intelligence_store.query(user_attrs, pattern_type, tag)
accessible = sum(1 for r in results if r["has_access"])
return {
    "total": len(results),
    "accessible": accessible,
    "entries": results,
}
```

[routes_intelligence.py:63](fraud-service/app/api/routes_intelligence.py:63)

`total` / `accessible` 분리 설계가 유용한 이유: 조회 기관이 "총 30개 패턴 중 12개만 볼 수 있다"는 사실을 알게 되어, 더 높은 속성 권한 확보 필요성을 인지할 수 있다.

## ⑤ 설계 포인트 / 트러블슈팅 거리

- **detail이 평문으로 저장된다**: `IntelligenceEntry.detail`은 Python dict 그대로 `_entries`에 보관된다. 접근 제어는 조회 시점의 `evaluate_access_structure` 결과로만 결정된다. 즉 저장소 자체(메모리 덤프, 직렬화 파일)에 접근하면 모든 detail이 평문으로 노출된다. ABE의 진의(데이터를 암호화해 복호화 키를 속성에서 파생)에 비해 현재 구현은 **접근 제어 시뮬레이션**에 가깝다. 실제 배포 환경에서는 `detail`을 AES-GCM으로 암호화하고, 속성 기반 키로만 복호화 가능하도록 바꿔야 한다.

- **In-memory 저장 → 재시작 시 소멸**: `intelligence_store`는 모듈 수준 싱글턴이다. 서비스 재시작 또는 멀티 인스턴스 배포 시 모든 게시된 패턴이 사라진다. 운영 환경에서는 PostgreSQL 또는 Redis 백엔드로 교체해야 한다.

- **게시자 인증 없음**: `POST /publish`의 `publisher_institution`은 요청 바디에서 자유롭게 지정된다. 어느 기관이나 타 기관 이름으로 인텔리전스를 게시할 수 있다. JWT 클레임이나 mTLS 클라이언트 인증서로 게시 기관을 검증해야 위·변조를 막을 수 있다.

- **query Lock이 전체 순회를 잡는다**: `query()` 메서드는 Lock을 잡은 채로 `_entries` 전체를 순회하고 `evaluate_access_structure`를 호출한다. 엔트리가 수천 개 이상이거나 접근 구조식이 복잡하면 Lock 경합이 길어져 `publish()`가 대기하게 된다. Lock 범위를 `_entries` 복사본 획득까지만으로 줄이고 순회는 Lock 밖에서 수행하면 처리량이 개선된다.

- **`[ENCRYPTED: …]` 문자열이 일관성 없는 타입**: `detail` 필드는 원래 `dict[str, Any]`인데 접근 불가 시 `str`이 들어간다. 클라이언트가 타입 체크 없이 `result["detail"]["ioc_list"]`를 접근하면 `TypeError`가 발생한다. `detail`을 `dict | None`으로 정의하고 접근 불가 시 `None`을 반환하거나, 별도 `encrypted: bool` 필드를 두는 편이 더 안전하다.

### 예상 질문 & 답변 (발표 Q&A 대비)

**Q1. 실제로 암호화가 안 된다는데 의미가 있나요?**
> ⑤절에서 정직하게 인정. 현재는 **접근 정책 평가 시뮬레이션** 수준이라 운영급 보안은 아닙니다. CP-ABE 인터페이스를 동일하게 유지해 charm-crypto 도입 시 교체 가능하게 한 게 가치.

**Q2. 기관 간 공유의 실제 사용 사례는?**
> 은행 A가 신종 피싱 패턴을 발견하면 summary는 모두에게 공개, detail(IoC·시그니처)은 access policy를 만족하는 기관만 열람. 발표에선 시연 데모 위주.

## ⑥ 한 줄 정리

기관 간 사기 패턴을 공유할 때 CP-ABE 접근 구조식으로 열람 권한을 제어하는 위협 인텔리전스 저장소 — 단, 실제 암호화는 없고 조회 시점 속성 평가로만 detail을 차단하는 시뮬레이션 수준이라 저장소 직접 접근에는 취약하다.
