# [T1] 신원 보증 레이어 — Spoofing 위협을 막는 두 겹

> **보안 위협 모델 시리즈 1편**. STRIDE의 첫 글자 **S(Spoofing)** 에 대응하는 PayWise의 방어선. JWT(소유 기반의 약한 1차 게이트)와 FIDO2/WebAuthn(공개키 암호의 강한 보강)이 어떻게 같은 위협을 두 겹으로 막는지를 본다.

---

## ① 관점 정의

"이 요청을 보낸 게 정말 그 사람인가?"라는 질문에 대한 PayWise의 답은 **두 단계**다. 1차로 비밀번호 검증 + JWT 발급으로 약한 신원 보증, 2차로 FIDO2 공개키 챌린지로 디바이스 보유 증명. 이 글은 두 레이어가 막는 위협의 종류와, **어디서부터 어디까지 책임을 지는지**의 경계선을 본다.

---

## ② 전체 흐름도

```
공격자 시나리오 (예시)
  ① 비밀번호 탈취 시도 (피싱·재사용)
  ② JWT 도용 시도 (XSS·중간자)
  ③ 디바이스 도용 시도 (SIM swap·세션 하이재킹)

방어선
  ┌─ 1차: bcrypt + JWT ───────────────────────────┐
  │  [routes_auth.py:login]                       │
  │  bcrypt verify → access(짧은 TTL) + refresh   │
  │  JWT는 서명만 검증, 디바이스 무관              │
  │                                                 │
  │  → 비밀번호가 새면 무력화. ①에 취약           │
  └─────────────────────────────────────────────────┘
                    │
                    ▼
  ┌─ 2차: FIDO2/WebAuthn ─────────────────────────┐
  │  [routes_fido.py:register|authenticate]       │
  │  서버 challenge → 인증기 서명 → 검증           │
  │  공개키는 서버, 개인키는 인증기 안              │
  │  → ①·② 무력화. ③도 디바이스 분실·탈취가 필요 │
  └─────────────────────────────────────────────────┘
```

## ③ 단계별 핵심

### 단계 1: 비밀번호 + bcrypt — 1차 신원의 한계

[`backend/app/auth/jwt.py`](../../../backend/app/auth/jwt.py) 의 `hash_password()` / `verify_password()` 가 bcrypt 로 암호 해시·검증을 한다. 이건 "비밀번호 DB가 새도 평문이 새지는 않게" 하는 보호선이지 **요청자 신원 보증은 아니다**. 비밀번호가 피싱·크리덴셜 스터핑으로 새면 1차 방어는 통째로 무력화된다.

### 단계 2: JWT의 서명 검증 — 디바이스 비독립성

[`backend/app/auth/jwt.py`](../../../backend/app/auth/jwt.py) 의 `create_access_token()` / `decode_token()` 은 HS256으로 서명·검증한다. JWT는 토큰 내용이 위변조됐는지만 본다 — **누가 들고 있는지는 보지 않는다**. 따라서 XSS로 토큰이 새면 그대로 도용된다. 이는 JWT의 본질적 한계로, 짧은 TTL + refresh 회전이 최선의 완화책이지만 [`#1 글`](../../01_기본인증_회원가입_로그인_JWT.md) 에서 짚었듯 회전 정책은 미구현.

### 단계 3: FIDO2 등록 — 공개키 등록의 비대칭성

[`backend/app/api/routes_fido.py`](../../../backend/app/api/routes_fido.py) 의 `/register/begin` 이 서버 측 nonce를 발급하고, `/register/finish` 에서 인증기가 만든 공개키를 받아 `FidoCredential` 테이블에 저장한다. **개인키는 서버를 떠난 적이 없다** — TPM/Secure Enclave 안에 머문다 ([`#2 FIDO2`](../../02_FIDO2_WebAuthn_등록_인증.md) 의 ④ 참조). 비밀번호 모델 대비 비대칭성이 핵심 보안 이득.

### 단계 4: FIDO2 인증 — 챌린지-응답으로 도용 방지

`/authenticate/begin` 이 서버 challenge를 발급하고, 인증기가 개인키로 서명해 `/authenticate/finish` 로 보낸다. 서버는 등록 시 받은 공개키로 검증. 같은 challenge가 두 번 사용되지 않게 nonce는 일회성. 이로써 **재전송 공격(replay), 중간자(MitM)** 가 막힌다.

### 단계 5: 두 레이어의 결합 — Step-up 트리거 시점

평상시엔 1차(JWT)만으로 통과. 위험 거래가 감지되면 [`J2`](../journey/02_로그인과_적응형_인증.md) → [`J4`](../journey/04_사기_탐지부터_차단까지.md) 의 흐름으로 step-up이 발동되어 2차(FIDO2 또는 TOTP)를 강제한다. 즉 **FIDO2는 항상 켜져 있는 게 아니라, 위협 신호가 있을 때 동원되는 예비 방어선**이다.

## ⑤ 통합 설계 트레이드오프

- **HS256 vs RS256**: 현재 단일 백엔드에서 HS256(대칭) 으로 충분하지만, 다중 서비스가 토큰 검증을 분산할 경우 비밀키 공유가 부담. RS256 전환 시 검증 키 분산이 쉬워진다.
- **JWT 블랙리스트 부재**: 로그아웃·계정 잠금 시 토큰을 즉시 무효화하는 메커니즘이 없다. TTL 만료까지 토큰이 살아 있는 점이 운영 환경 약점.
- **FIDO2 등록의 선택성**: 신규 사용자가 등록을 미루면 [`J1`](../journey/01_가입과_온보딩.md) 에서 본 것처럼 1차 방어만 남는다. 등록률을 높이는 UX 설계(예: 가입 완료의 정의 변경)가 보안 정책과 맞물린다.
- **인증기 분실 시나리오**: 백업 코드·관리자 복구 흐름이 명시적으로 미구현. 이는 [`#2 글`](../../02_FIDO2_WebAuthn_등록_인증.md) 의 확장 영역.
- **TOTP의 위치**: TOTP는 1차(`/login/totp`) 와 2차(step-up) 양쪽에서 쓰이는데, 같은 코드 입력이 의미가 다르다는 점이 사용자 혼동 소지.

---

## ⑥ 한 줄 정리

신원 보증은 비밀번호+JWT의 약한 1차 게이트와 FIDO2 공개키의 강한 2차 보강이 **위협 신호에 따라 동원되는** 두 겹 구조다.
