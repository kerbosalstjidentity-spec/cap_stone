# [T3] 접근 제어와 암호 — 인증된 사용자라도 다 볼 수는 없다

> **보안 위협 모델 시리즈 3편**. STRIDE의 **Information Disclosure(정보 유출)·Elevation(권한 상승)** 에 대응하는 PayWise의 두 겹 방어선 — ABAC 정책 평가와 ABE 속성 기반 암호화. 같은 자원이 같은 사용자에게도 **속성 조합에 따라 다르게 보이는** 구조를 본다.

---

## ① 관점 정의

PayWise의 접근 제어는 RBAC(역할 기반)이 아니라 **ABAC(속성 기반)** 다. 단순히 "관리자/일반 사용자" 가 아니라 (역할 + 보안 등급 + 위치 + 부서 + 자원 민감도) 의 조합으로 결정된다. 그리고 ABAC 통과 후에도 카드 번호 같은 민감 필드는 **ABE로 한 겹 더 암호화**되어 있어, 키를 가진 자만 복호화한다. 이 글은 두 레이어가 어떻게 분업하는지를 본다.

---

## ② 전체 흐름도

```
인증된 사용자 (JWT 보유) → 자원 접근 시도
   │
   ▼
ABAC 평가 (services/abac_engine.py — 8개 룰)
   │
   ├─ Rule 1: user_role 기반 기본 허용/거부
   ├─ Rule 2: clearance ≥ resource_sensitivity?
   ├─ Rule 3: location 화이트리스트?
   ├─ Rule 4: 시간대 정책?
   ├─ Rule 5: 자원 소유자 == 요청자?
   ├─ Rule 6~8: 도메인 특수 룰
   │
   ▼
결과: { allowed: true/false, masked_fields: [...] }
   │
   ├─ allowed=false → 403
   └─ allowed=true
       │
       ▼
ABE 복호화 (services/abe_engine.py)
   │
   ├─ 사용자 속성으로 키 파생
   ├─ 매칭 정책 충족 시 복호화 성공
   └─ 미충족 시 마스킹된 값 그대로
       │
       ▼
응답: { resource_data with masked fields }

   ▼
모든 시도는 audit_logger 에 기록 → 블록체인 감사 (T5)
```

---

## ③ 단계별 핵심

### 단계 1: ABAC 평가의 입력

[`fraud-service/app/services/abac_engine.py`](../../../fraud-service/app/services/abac_engine.py) 가 받는 입력은 (a) 사용자 속성: role, clearance, department, location, (b) 자원 속성: sensitivity, owner_id, type, (c) 환경 속성: timestamp, request_ip. 이 셋의 카르테시안 조합으로 룰이 평가된다 ([`#15 ABAC`](../../15_ABAC_ABE_접근제어.md)).

### 단계 2: 룰 평가의 순차성

8개 룰이 **순차 평가**되며, 한 룰이라도 명시적 거부면 즉시 deny. 단, 마스킹은 누적된다 — 즉 모든 룰을 통과해야 비로소 모든 필드가 보인다. **deny-first + mask-accumulate** 정책.

### 단계 3: 마스킹된 필드의 처리

Allowed=true 라도 응답에 포함된 `masked_fields` 가 비어있지 않을 수 있다. 예: 보안팀이 일반 사용자 거래를 조회할 때 거래 자체는 보이지만 카드번호는 `**** **** **** 1234` 로 마스킹. 이는 ABAC만으로 처리되며 ABE까지 가지 않는 일반 마스킹.

### 단계 4: ABE 키 파생

[`fraud-service/app/services/abe_engine.py`](../../../fraud-service/app/services/abe_engine.py) 의 ABE는 사용자 속성으로 키를 파생한다. **암호문 자체에 정책이 박혀 있어**, 정책 미충족자는 키 파생이 불가능하다 ([`#15 ABE 절`](../../15_ABAC_ABE_접근제어.md)). RBAC의 "권한 체크 후 평문 반환" 과 다른 점은 **권한 체크와 복호화가 같은 연산**이라는 것.

### 단계 5: 정책 변경 시 재암호화 비용

ABE의 약점 — 정책이 바뀌면 암호문 자체를 다시 만들어야 한다 ([`#15 글`](../../15_ABAC_ABE_접근제어.md) 의 트레이드오프 절). 이는 운영 비용 측면에서 큰 부담으로, 자주 바뀌는 정책에는 ABAC + 일반 대칭 암호가 더 현실적.

### 단계 6: 모든 접근의 감사 기록

ABAC allow/deny 결과와 ABE 복호화 시도 모두 [`audit_logger`](../../../fraud-service/app/services/audit_logger.py) 를 거쳐 [`T5 감사`](05_감사와_관측.md) 의 블록체인 체인에 적재된다. 즉 **누가 무엇을 보려 했고, 시스템이 무엇을 거절했는지**의 기록이 부인 방지 장치 역할을 한다.

## ⑤ 통합 설계 트레이드오프

- **ABAC 룰의 두 곳 분산**: fraud-service의 8개 룰 ([`#15 글`](../../15_ABAC_ABE_접근제어.md)) 과 backend 보안 대시보드의 5개 룰 시뮬레이터 ([`#4 글`](../../04_보안_대시보드.md)) 가 별개로 존재. 정책 변경 시 동기화 부담.
- **속성 출처의 신뢰성**: clearance·location·department 같은 속성은 사용자 프로필에서 오는데, 이 프로필 자체의 무결성 보증이 명시적이지 않다. 속성을 거짓으로 만들면 ABAC가 우회될 수 있다.
- **ABE의 운영 비용**: 정책 변경 = 재암호화. 캡스톤 단계에선 정책이 거의 안 바뀌어 무관하지만 실서비스로 가면 키 회전·정책 업데이트 비용이 ABE 도입 결정의 핵심 변수.
- **마스킹 정책의 일관성**: 어떤 필드를 마스킹할지가 룰별로 흩어져 있다. 자원 스키마에 `sensitivity_level` 메타데이터를 두고 ABAC가 일괄 적용하는 구조가 더 견고.
- **요청 IP·위치의 위변조**: 환경 속성으로 쓰는 IP는 클라이언트가 자칭한 값이 아니라 서버가 관측한 값이어야 한다. 프록시 헤더(X-Forwarded-For) 신뢰 정책이 명시적이지 않다.

---

## ⑥ 한 줄 정리

PayWise의 접근 제어는 ABAC가 **누가 볼 수 있는지를 결정**하고 ABE가 **민감 필드는 볼 자격이 키 파생으로 표현되는** 두 겹으로, 정책의 분산과 ABE 운영 비용이 다음 보강 영역이다.
