# [T2] 적응형 인증 레이어 — 세션이 살아 있어도 다시 묻는 이유

> **보안 위협 모델 시리즈 2편**. 신원이 일단 보증된 후에도 **세션 탈취·계정 도용** 같은 위협은 살아남는다. PayWise는 Step-up 인증과 행동 시그널 분석을 묶어 "정상 세션 안의 비정상"을 잡아낸다.

---

## ① 관점 정의

[`T1`](01_신원_보증_레이어.md) 의 신원 보증이 **로그인 시점**의 방어라면, 적응형 인증은 **세션 수명 전체에 걸친** 방어다. 같은 JWT를 들고 있어도 디바이스가 바뀌었거나, 로그인 시간대가 평소와 다르거나, 직전 거래의 위험 점수가 임계값을 넘으면 시스템이 다시 묻는다. STRIDE의 **Tampering(세션 탈취)·Elevation(권한 상승)** 에 대응한다.

---

## ② 전체 흐름도

```
정상 로그인 통과 → JWT 보유
   │
   ├─ 행동 시그널 누적 (login, totp, stepup 이벤트)
   │   StepUpSession 테이블에 시간순 저장
   │
   ├─ fraud-service가 거래마다 risk_score 갱신
   │   (사용자 프로필에 누적)
   │
   ▼
사용자가 보호 페이지/액션 시도
   │
   ▼
POST /v1/auth/stepup/challenge
   │
   ├─ _get_risk_score() → fraud-service 조회
   │   (장애 시 0.0 fallback)
   │
   ├─ score < 0.6 → 통과
   │
   └─ score ≥ 0.6
       ├─ TOTP 등록자 → method = "totp"
       ├─ FIDO 등록자 → method = "fido"
       └─ 무등록 → 경고만 (정책 한계)

   ▼
인증 성공 → 새 access_token 발급
StepUpSession.verified = true (재사용 방지)
```

---

## ③ 단계별 핵심

### 단계 1: 행동 시그널의 누적

[`fraud-service/app/services/behavioral_signals.py`](../../../fraud-service/app/services/behavioral_signals.py) 가 디바이스 핑거프린트·로그인 시간대·IP 변화 등을 추적한다 ([`#14 행동 시그널`](../../14_행동_시그널_분석.md)). 이는 별도 인증이 아니라 **각 사용자의 평소 패턴 모델**이다. 평소와 다른 패턴이면 risk_score가 끌어올려진다.

### 단계 2: 위험 거래 트리거의 비동기성

거래 평가([`J4`](../journey/04_사기_탐지부터_차단까지.md))의 결과가 사용자 프로필에 risk_score로 반영된다. 핵심은 이게 **즉시 사용자 차단으로 이어지지 않는다**는 점. 다음 보호 액션 시점에 step-up으로 회신된다 — 즉 사용자 입장에선 "거래 후 다음 행동에서 갑자기 OTP가 뜨는" 경험.

### 단계 3: 임계값 비교의 단순성

[`backend/app/api/routes_stepup.py:66`](../../../backend/app/api/routes_stepup.py:66) 의 `risk_score < settings.STEPUP_RISK_THRESHOLD` 비교는 단일 상수(기본 0.6) 와의 비교. 사용자별·세그먼트별·시간대별 임계값이 아니라 **시스템 전역 상수**라는 점이 본 시리즈에서 주목할 약점.

### 단계 4: Method 우선순위와 Fallback

[`routes_stepup.py:38`](../../../backend/app/api/routes_stepup.py:38) 의 `_determine_method()` 가 TOTP > FIDO > none 우선순위로 결정한다. FIDO Credential 존재 확인은 별도 DB 조회로 분리되어 있다 ([routes_stepup.py:78](../../../backend/app/api/routes_stepup.py:78)). 둘 다 없으면 `method="none"` + 경고만 — **정책적으로 강제할 수 없는 한계**가 명확히 노출된다.

### 단계 5: 일회성 토큰의 재사용 방지

[`routes_stepup.py:151`](../../../backend/app/api/routes_stepup.py:151) 의 `if stepup_session.verified` 체크가 토큰 재사용을 막는다. 즉, **한 번의 step-up 통과는 한 번의 보호 액션에만 해당**. 다단계 워크플로우 중간에 또 위험 신호가 뜨면 새 토큰이 필요.

### 단계 6: 검증 성공 후의 권한 갱신

[`routes_stepup.py:179`](../../../backend/app/api/routes_stepup.py:179) 에서 새 access_token 이 발급된다. 이는 **"step-up 통과 == 더 높은 신원 신뢰 레벨"** 을 토큰 갱신으로 표현한 것. 이 새 토큰의 서명에는 step-up 통과 정보가 들어가지 않는데, 향후 ABAC 정책에서 "최근 step-up 통과 여부"를 속성으로 쓰려면 토큰 페이로드 확장이 필요하다.

## ⑤ 통합 설계 트레이드오프

- **Fail-open 정책**: [`routes_stepup.py:34`](../../../backend/app/api/routes_stepup.py:34) 의 `except Exception: return 0.0` 은 fraud-service 장애 시 step-up을 자동 비활성화한다. 가용성 우선이지만 보안 관점에선 약점. 캐시된 직전 스코어 fallback이 더 보수적.
- **단일 임계값의 거칢**: 0.6 전역 상수는 false-positive(정상 사용자에게 불필요한 마찰) 와 false-negative(위험 사용자가 통과) 의 균형을 사용자별로 조정할 수 없다. 이는 운영 데이터로 학습하는 임계값 추천 모델로 발전 가능.
- **토큰에 step-up 흔적 부재**: 통과 후 새 access_token 에 step-up 통과 사실이 인코딩되지 않는다. ABAC 같은 사후 정책에서 활용하려면 페이로드 확장 필요.
- **무등록 사용자에 대한 정책 공백**: TOTP·FIDO2 둘 다 없으면 [`routes_stepup.py:85`](../../../backend/app/api/routes_stepup.py:85) 가 경고만 출력. 위험 거래임에도 통과시키는 셈으로, 운영에선 "강제 등록 페이지로 리다이렉트" 같은 정책이 필요.
- **행동 시그널의 적시성**: [`#14 글`](../../14_행동_시그널_분석.md) 에서 짚은 대로 시그널 갱신이 동기적이지 않으면 직전 위협이 점수에 반영되기 전에 사용자가 빠져나갈 수 있다.

---

## ⑥ 한 줄 정리

적응형 인증은 신원 보증 이후의 위협을 **risk_score → 임계값 → step-up** 의 단순 파이프라인으로 막지만, 임계값과 fail-open 정책이 시스템 전역 상수라는 점이 운영화의 1순위 보강 영역이다.
