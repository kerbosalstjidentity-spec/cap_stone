# [T4] 거래 위험 방어선 — 사기 거래는 ML 단독으로 막을 수 없다

> **보안 위협 모델 시리즈 4편**. STRIDE의 직접 분류는 어렵지만 PayWise 도메인에서 가장 큰 위협 — **사기 거래 자체**. ML 앙상블·규칙 엔진·A/B 테스트의 3겹 방어가 false-positive와 false-negative의 줄다리기를 어떻게 다루는지를 본다.

---

## ① 관점 정의

거래 위험은 신원 위협과 다르다. **인증 통과한 정상 사용자의 거래 자체가 사기일 수 있다** (예: 카드 도용 후 결제). 이때 막는 주체는 인증이 아니라 거래 평가다. PayWise는 (1) 모델 단일 의존을 피해 IF+XGBoost 앙상블, (2) ML 약점을 룰로 보강, (3) 신·구 모델을 A/B로 안전 전환의 세 축으로 이 위협에 대응한다.

---

## ② 전체 흐름도

```
거래 한 건 도착
   │
   ▼
ML 앙상블 (scoring/ensemble.py)
   │
   ├─ XGBoost: P(사기) 확률
   ├─ Isolation Forest: 이상치 정도 → 정규화
   └─ 0.7·XGB + 0.3·IF = 앙상블 점수
       │
       ├─ A/B 테스트 (scoring/ab_test.py)
       │   └ 일부 트래픽은 신모델 번들로 평가
       │     결과를 비교 분석으로 누적
   │
   ▼
규칙 엔진 (services/rule_engine.py)
   │
   ├─ 결정적 룰 (예: 야간+해외+고액)
   ├─ 화이트/블랙 리스트
   └─ ML 점수 + 룰 결과 병합 (services/policy_merge.py)
       │
       ▼
   action: PASS / REVIEW / BLOCK
       │
       ├─ PASS  → 통과
       ├─ REVIEW → step-up 사용자 회신 (T2)
       └─ BLOCK  → 즉시 차단 + 알림
```

## ③ 단계별 핵심

### 단계 1: 단일 모델의 위험성

XGBoost 단독이라면 학습 분포 밖의 새 패턴(adversarial drift)에 취약하다. Isolation Forest 는 정상 분포를 학습해 **레이블 없이도 이상을 잡는다**. 두 모델은 서로 다른 가정으로 작동하므로 한쪽이 속아도 다른 쪽이 알아챌 가능성이 있다 ([`#12 사기 점수`](../../12_실시간_사기_점수_IF_RF_하이브리드.md)).

### 단계 2: 가중치 0.7/0.3의 의미

[`fraud-service/app/scoring/ensemble.py:13`](../../../fraud-service/app/scoring/ensemble.py:13) 의 `ALPHA=0.7, BETA=0.3` 는 **지도 학습이 더 정확하다는 가정** 위에 비지도를 보강 신호로 둔 것. 데이터 라벨 품질에 따라 이 비율은 재조정 대상.

### 단계 3: ML 폴백의 안전성

[`ensemble.py:38`](../../../fraud-service/app/scoring/ensemble.py:38) 의 `if iso is None: return xgb_proba, None` 은 IF 번들이 빠지면 자동 XGBoost 단독으로 폴백한다. 시스템이 **모델 일부 손실에도 죽지 않는다**는 점이 운영 견고성의 핵심.

### 단계 4: 룰 엔진의 거부권

[`fraud-service/app/services/rule_engine.py`](../../../fraud-service/app/services/rule_engine.py) 의 룰은 ML 점수와 무관하게 BLOCK을 강제할 수 있다 ([`#13 규칙 엔진`](../../13_규칙_엔진.md)). 예: ML이 0.3 점수를 줘도 "야간+고액+해외 첫 거래" 룰이 발동되면 BLOCK. ML의 약점인 **희귀 패턴 미탐을 룰이 보완**한다.

### 단계 5: 정책 병합의 OR vs AND

[`policy_merge.py`](../../../fraud-service/app/services/policy_merge.py) 의 현재 정책은 둘 중 하나라도 BLOCK이면 BLOCK 인 보수적 OR. false-negative(놓치는 사기)를 줄이지만 false-positive(정상이 막힘) 가 늘어난다. 비즈니스 손실 비용 함수에 따라 이 결합 방식은 조정 대상.

### 단계 6: A/B 테스트로의 안전 전환

[`fraud-service/app/scoring/ab_test.py`](../../../fraud-service/app/scoring/ab_test.py) 가 user_id 해시 기반으로 트래픽을 신·구 모델에 분배한다 ([`#18 A/B 테스트`](../../18_AB_테스트_모델_비교.md)). 신모델이 평균적으로 더 나아도 **특정 세그먼트에서 회귀**할 수 있는데, A/B 비교가 이를 잡아낸다. 모델 교체를 일괄 적용하지 않고 점진적으로 검증.

## ⑤ 통합 설계 트레이드오프

- **하드코딩 가중치**: 0.7/0.3 상수가 코드에 박혀 있다 ([ensemble.py:13](../../../fraud-service/app/scoring/ensemble.py:13)). 운영에선 환경변수 또는 SYSTEM_CONFIG 로 빼야 하지만 미완. 코드 주석에도 "나중에" 라고 명시.
- **OR 결합의 false-positive 비용**: 보수적 결합은 차단을 늘리지만 정상 사용자에게 step-up·차단 마찰을 늘린다. 비즈니스가 어느 비용을 더 싫어하는지에 따라 가중 평균/AND/임계값 조정의 방향이 갈린다.
- **A/B 트래픽 비율 부재**: 현재 [`ab_test.py:34`](../../../fraud-service/app/scoring/ab_test.py:34) 부근의 분배가 단순 해시 기반. 점진적 롤아웃(1% → 10% → 50%) 같은 동적 비율 조정은 미구현 — 신모델 검증 시 위험 노출.
- **정규화 분포 가정**: IF 점수 정규화 [`ensemble.py:23`](../../../fraud-service/app/scoring/ensemble.py:23) 의 `LOW=-0.5, HIGH=-0.05` 는 학습 시점 분포 가정. 모델 재학습 후 분포가 바뀌면 정규화가 의미를 잃을 수 있다.
- **adversarial 시나리오 부재**: 공격자가 ML 학습 분포를 탐색하며 우회하는 시나리오에 대한 명시적 방어(예: feature drift 모니터링)는 [`M4`](../mlops/04_운영_관측과_향후_과제.md) 에서 다룰 향후 과제.
