# [T5] 감사와 관측 — 부인 방지의 마지막 보루

> **보안 위협 모델 시리즈 5편 (마지막)**. STRIDE의 **R(Repudiation, 부인)** 에 대응. "내가 하지 않았다" 를 막는 방법은 **변경할 수 없는 기록**이고, "비슷한 일이 다시 생길까" 를 막는 방법은 **유사 패턴 탐지**다. 블록체인 감사·보안 대시보드·위협 인텔리전스의 3겹 관측을 본다.

---

## ① 관점 정의

앞선 4개 글의 모든 결정(인증·접근·거래)은 결국 **기록과 관측의 대상**이 된다. PayWise는 (1) SHA-256 해시 체인으로 부인 방지, (2) 보안 대시보드로 시연 통합, (3) 위협 인텔리전스로 패턴 학습 루프를 만든다. 이 글은 사후 단계의 위협 — 기록 위변조, 사후 조사 우회, 동일 패턴 재발 — 을 어떻게 막는지를 본다.

   │       /audit/chain, /audit/verify API 노출
   │

   │     └ 시간대별 PASS/REVIEW/BLOCK 통계 집계

  /security              보안 점수·이벤트

## ③ 단계별 핵심

### 단계 1: 표준 감사 로그 포맷

[`fraud-service/app/services/audit_logger.py`](../../../fraud-service/app/services/audit_logger.py) 가 전 모듈의 감사 이벤트를 표준 스키마(transaction_id, user_id, action, score, timestamp)로 정규화한다. **단일 포맷이 단일 검색 가능성**을 만든다.

### 단계 2: 해시 체인의 무결성 보증

[`fraud-service/app/services/blockchain_audit.py`](../../../fraud-service/app/services/blockchain_audit.py) 의 핵심: 각 블록이 직전 블록의 `block_hash` 를 `prev_hash` 로 포함하며, 자신의 hash 도 (data + prev_hash) 의 SHA-256. 한 블록을 임의로 바꾸면 **그 이후 모든 블록의 hash 가 깨진다** ([`#16 블록체인 감사`](../../16_블록체인_감사_로그.md)). 이는 "진짜 블록체인" 이 아니라 단일 노드 해시 체인이지만, 부인 방지에는 충분하다 (운영자가 직접 위조하지 않는 한).

### 단계 3: 두 개의 체인 — 의도된 분리

backend의 `_AUDIT_CHAIN` ([`routes_security_dashboard.py`](../../../backend/app/api/routes_security_dashboard.py)) 은 fraud-service 체인과 별개의 인메모리 데모 체인이다 ([`#4 보안 대시보드`](../../04_보안_대시보드.md) 참조). 시연 안정성을 위한 의도적 분리지만, **단일 진실 출처가 없다는 점**이 본 위협 모델 관점에서 약점. 이상적으로는 backend가 fraud-service 체인을 read-only 미러로 가져와야 한다.

### 단계 4: 무결성 검증 API

backend의 `GET /v1/security/audit/verify` 가 체인을 처음부터 순회하며 prev_hash 일치성을 검증한다 ([`#4 글`](../../04_보안_대시보드.md) 의 ④-2). 어긋나는 첫 블록을 찾아 즉시 false 반환. **검증 자체가 사용자에게 노출되는 보안 기능**이라는 점이 PayWise의 차별점.

### 단계 5: 통계 집계와 보안 점수

[`fraud-service/app/services/stats_collector.py`](../../../fraud-service/app/services/stats_collector.py) 가 시간대별 PASS/REVIEW/BLOCK 분포를 집계한다. 이 통계가 보안 대시보드의 "보안 점수" 라는 단일 숫자로 응축된다 ([`#4 글`](../../04_보안_대시보드.md) ②). 한 숫자가 시스템 전체 건강도를 표현하는 게 시연용으론 강력하지만, **점수 산출 룰의 해석 가능성**은 운영 단계에서 보강 영역.

### 단계 6: 위협 인텔리전스 — 다음 결정으로의 피드백

[`fraud-service/app/api/routes_intelligence.py`](../../../fraud-service/app/api/routes_intelligence.py) 와 [`intelligence_store.py`](../../../fraud-service/app/services/intelligence_store.py) 가 "한 사용자에게서 일어난 BLOCK" 의 패턴(IP·디바이스·MCC)을 다른 사용자에 대한 사전 차단 신호로 회신한다 ([`#17 위협 인텔`](../../17_위협_인텔리전스.md)). 즉 **사후 단계가 다음 사전 결정의 입력**이 되는 학습 루프.

## ⑤ 통합 설계 트레이드오프

- **두 체인의 분리 비용**: 시연 안정성을 위한 의도적 분리지만 정합성·신뢰의 단일 출처가 없다. fraud-service 체인을 backend가 read-only 미러로 동기화하면 위협 모델이 한 결정의 한 기록으로 좁혀진다.
- **단일 노드 해시 체인의 한계**: 운영자가 audit_chain.json 을 직접 위조하면 무결성이 깨진다. 진짜 분산 합의(예: 다중 노드 PoA)는 캡스톤 범위를 넘지만, 외부 타임스탬프 서버에 주기적 앵커링 정도는 보강 가능.
- **보안 점수의 블랙박스성**: 한 숫자가 시스템 건강도를 표현하지만 산출 룰이 어디에 있고 어떤 가중치인지가 사용자에게 투명하지 않다. 점수의 brake-down 노출이 시연 신뢰성을 높인다.
- **위협 인텔의 외부 연동 부재**: 캡스톤 단계는 시뮬레이션 DB. OSINT/상용 피드 연동 시 false-positive 폭증을 막기 위한 신뢰도 가중 매칭이 필요.
- **감사 로그의 보존 정책**: 장기 보관·삭제·열람 정책이 코드 레벨에서 명시되지 않았다. 컴플라이언스(예: 개인정보 5년 보관) 관점에서 정책 모듈화 필요.
