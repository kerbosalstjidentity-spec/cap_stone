# [J1] 가입과 온보딩 — 신규 사용자가 PayWise에 자리잡기까지

> **사용자 여정 시리즈**의 첫 글. 회원가입 클릭 한 번이 끝이 아니라, 비밀번호 → JWT 발급 → 데모 데이터 시딩 → FIDO2 등록까지의 일련의 단계가 어떻게 맞물리는지를 따라간다.

---

## ① 관점 정의

PayWise는 가입 직후의 **빈 대시보드**를 허용하지 않는다. 회원가입 한 번에 (1) 기본 인증 자격(JWT 한 쌍), (2) 3개월치 데모 거래·소비 데이터, (3) FIDO2 등록 권유까지가 한 묶음으로 흘러야 비로소 "온보딩 완료"다. 이 글은 **가입 직후의 첫 30초**를 한 화면에 펼쳐보는 글이다. 기능 단위로 보면 #1·#2가 따로 있지만, 실제 사용자 경험에서는 둘이 끊김 없이 이어지므로 한 번에 봐야 한다.

---

## ② 전체 흐름도

```
┌─ Frontend (Next.js) ─────────────────────────┐
│  /auth/register   (이메일·비번·닉네임 입력)   │
└────────────┬─────────────────────────────────┘
             │ POST /v1/auth/register
             ▼
┌─ Backend (FastAPI) ──────────────────────────┐
│  1) 이메일 중복 검사                          │
│  2) bcrypt 비밀번호 해시                      │
│  3) User 행 INSERT                            │
│  4) JWT access + refresh 발급                 │
│  5) routes_seed.seed_user_data() 자동 호출    │
│     └ 3개월치 거래 + 카테고리 + 분석 결과 시딩 │
└────────────┬─────────────────────────────────┘
             │ 201 Created { access_token, refresh_token }
             ▼
┌─ Frontend ───────────────────────────────────┐
│  토큰을 localStorage 저장 → /dashboard 진입    │
│  (이미 시딩된 분석 결과가 즉시 렌더링)         │
│                                               │
│  사이드바 "보안 설정" 진입을 유도              │
└────────────┬─────────────────────────────────┘
             │ POST /v1/auth/fido/register/begin
             ▼
┌─ Backend ────────────────────────────────────┐
│  WebAuthn challenge 발급 (서버 측 nonce)       │
│  → 브라우저 navigator.credentials.create()    │
│  → 인증기(YubiKey/Touch ID/Windows Hello)에서  │
│    공개키 쌍 생성, 서명 반환                  │
│  → /fido/register/finish 에서 검증·저장       │
└──────────────────────────────────────────────┘
```

## ③ 단계별 핵심

### 단계 1: 회원가입 트랜잭션

[`routes_auth.py:73`](../../../backend/app/api/routes_auth.py:73) 의 `register()` 가 핵심이다. 이메일 중복 검사 → bcrypt 해시 → `User` 삽입까지 한 트랜잭션. 비밀번호 해싱은 `hash_password()` 한 줄로 위임한다.

### 단계 2: JWT 한 쌍 즉시 발급

가입 응답에 access·refresh 두 토큰이 함께 실려나간다. 별도 "이메일 인증 메일" 단계가 없는데, 이는 **캡스톤 시연 환경**에서 흐름을 끊지 않기 위한 의도된 단순화다. 운영 환경이라면 [`#1 기본 인증`](../../01_기본인증_회원가입_로그인_JWT.md) 글에서 짚은 이메일 검증 단계가 추가되어야 한다.

### 단계 3: 자동 시딩 — 빈 대시보드 회피

[`routes_auth.py:94`](../../../backend/app/api/routes_auth.py:94) 의 `seed_user_data(user_id, session, months=3, tx_per_month=40)` 호출이 이 여정의 핵심 디자인 결정이다. 회원가입 응답이 끝나기 전에 약 120건의 데모 거래·카테고리·소비 패턴이 적재되므로, 사용자가 처음 본 `/dashboard`는 이미 KMeans 군집·LSTM 예측·감정 분석 결과가 채워진 상태가 된다. 이 시딩은 [`#5 KMeans`](../../05_소비_패턴_분석_KMeans_군집화.md), [`#6 LSTM`](../../06_지출_예측_LSTM_시계열.md), [`#9 감정`](../../09_감정_기반_소비_분석.md) 모듈을 즉시 작동시킬 수 있도록 페이로드를 맞춰 생성된다.

### 단계 4: FIDO2 등록 유도

[`routes_fido.py`](../../../backend/app/api/routes_fido.py) 의 `/register/begin` → `/register/finish` 두 단계가 [`#2 FIDO2`](../../02_FIDO2_WebAuthn_등록_인증.md) 의 본 글에서 이미 깊이 다뤄졌다. 여정 관점에서 강조할 점은 **FIDO2 등록을 가입 흐름의 "마지막 단계"가 아닌 "선택적 보강"으로 두었다**는 것이다. 사용자가 등록을 미루더라도 [`#3 Step-up`](../../03_Step-up_인증_위험거래_추가인증.md) 가 위험 거래 발생 시 다시 권유한다.

## ⑤ 통합 설계 트레이드오프

- **자동 시딩의 양면성**: 데모 환경에서는 "빈 대시보드 회피"라는 강력한 UX 이점이 있지만, 운영 환경이라면 가짜 데이터가 그대로 들어가는 셈. 회원가입 트랜잭션 안에서 동기 호출되므로 시딩이 느려지면 가입 자체가 느려지는 결합도 존재 ([routes_auth.py:96](../../../backend/app/api/routes_auth.py:96) 에서 `try/except` 로 막아두긴 했다).
- **이메일 검증 생략**: 캡스톤 시연 편의로 의도적으로 생략. 그러나 가입 직후 발급되는 JWT가 곧바로 사기 탐지·블록체인 감사·ABAC 같은 민감 영역으로 통과되므로, 운영 환경에선 이 흐름의 "취약점"이 된다.
- **FIDO2 등록 유도 시점**: 가입 직후가 아니라 **첫 위험 거래 발생 시 step-up으로 권유**하는 패턴이 더 자연스러운지에 대해선 캡스톤 발표 시 토론거리가 된다. 현재는 가입 직후·보안 설정 메뉴 양쪽에서 권유.
- **Refresh 토큰 회전**: refresh 토큰이 발급은 되지만, 운영 회전(rotation) 정책은 [`#1 글`](../../01_기본인증_회원가입_로그인_JWT.md) 에서 짚었듯 미구현 영역.

---

## ⑥ 한 줄 정리

회원가입 → JWT → 데모 시딩 → FIDO2 권유의 4단계가 **단일 트랜잭션처럼 묶여** 신규 사용자에게 "이미 작동하는 시스템"을 30초 안에 보여주는 것이 PayWise 온보딩의 설계 의도다.
