# [J4] 사기 탐지부터 차단까지 — 거래 한 건이 점수가 되고, 점수가 행동이 되는 순간

> **사용자 여정 시리즈 4편**. 거래가 도착해서 (1) 모델이 점수를 매기고, (2) 규칙이 그 점수를 보정하고, (3) 행동 시그널이 가중치를 더하고, (4) 결과가 PASS/REVIEW/BLOCK 으로 떨어지는 흐름을 따라간다. 그리고 BLOCK이 곧장 [`J2`](02_로그인과_적응형_인증.md) 의 step-up으로 어떻게 회신되는지까지.

---

## ① 관점 정의

PayWise 사기 탐지의 핵심은 **단일 모델이 아니다**. Isolation Forest(비지도 이상치) + XGBoost(지도 분류)의 가중 앙상블 점수에 규칙 엔진의 보정과 행동 시그널의 가중이 차례로 얹혀 최종 결정으로 응축된다. 이 글은 거래 → 점수 → 결정 → 사용자 차단/재인증의 전체 사슬을 본다.

---

## ② 전체 흐름도

```
거래 발생 (실제 결제 or 시뮬레이터)
   │
   ▼
POST /v1/score  (fraud-service)
   │
   ├─ scoring/features.py   특성 추출
   ├─ scoring/model_loader.py  joblib 번들 로드
   ├─ scoring/ensemble.py
   │   └ XGBoost 확률 = xgb_proba
   │     IsolationForest score → 정규화 → anomaly
   │     final = 0.7 * xgb_proba + 0.3 * anomaly
   │
   ▼
POST /v1/fraud/evaluate
   │
   ├─ services/rule_engine.py
   │   └ 금액·시간·국가·MCC 등 룰 통과 여부
   │
   ├─ services/behavioral_signals.py
   │   └ 디바이스·로그인 패턴 가중치
   │
   ├─ services/policy_merge.py
   │   └ ML 점수 + 룰 결과 → 최종 action 결정
   │
   ▼
응답: { action: "PASS" | "REVIEW" | "BLOCK", score, reasons[] }
   │
   ├─ PASS  → 거래 승인
   ├─ REVIEW → 백엔드가 step-up 챌린지 트리거
   │           (사용자에게 TOTP/FIDO 요구)
   └─ BLOCK → 즉시 차단 + 알림 발송 (#21)

   ▼ 모든 결과는
services/audit_logger.py + blockchain_audit.py 에 기록
```

## ③ 단계별 핵심

### 단계 1: 특성 추출

[`fraud-service/app/scoring/features.py`](../../../fraud-service/app/scoring/features.py) 가 거래 한 건에서 모델 입력 벡터를 만든다. 시간대·금액 로그·국가·MCC 코드 등이 들어간다 ([`#12 사기 점수`](../../12_실시간_사기_점수_IF_RF_하이브리드.md) 의 ④ 참고).

### 단계 2: 하이브리드 앙상블

[`fraud-service/app/scoring/ensemble.py:29`](../../../fraud-service/app/scoring/ensemble.py:29) 의 `ensemble_score()` 가 두 모델 출력을 합친다. 가중치는 상수 `ALPHA=0.7, BETA=0.3` ([ensemble.py:13](../../../fraud-service/app/scoring/ensemble.py:13)). Isolation Forest가 번들에 없으면 자동으로 XGBoost 단독으로 폴백 ([ensemble.py:38](../../../fraud-service/app/scoring/ensemble.py:38)). 이 폴백 패턴 덕에 **모델 일부가 빠져도 시스템이 죽지 않는다**.

### 단계 3: 룰 엔진의 보정

[`fraud-service/app/services/rule_engine.py`](../../../fraud-service/app/services/rule_engine.py) 가 ML 점수와 별개로 결정적 룰을 평가한다 ([`#13 규칙 엔진`](../../13_규칙_엔진.md)). "야간+고액+해외" 같은 조합은 ML이 통과시켜도 룰이 BLOCK 처리할 수 있다. 즉, **룰은 ML의 거부권**.

### 단계 4: 행동 시그널의 가중

[`fraud-service/app/services/behavioral_signals.py`](../../../fraud-service/app/services/behavioral_signals.py) 가 사용자의 디바이스 변경·평소와 다른 시간대 로그인 등을 가중치로 변환한다 ([`#14 행동 시그널`](../../14_행동_시그널_분석.md)). 이는 점수 자체가 아니라 **점수의 신뢰 보정**이다.

### 단계 5: 정책 병합과 최종 결정

[`fraud-service/app/services/policy_merge.py`](../../../fraud-service/app/services/policy_merge.py) 가 (ML 앙상블 점수, 룰 통과 여부, 행동 가중치)를 받아 PASS/REVIEW/BLOCK 중 하나를 골라낸다. **3개 입력의 우선순위·결합 방식**이 이 모듈에 응축돼 있다.

### 단계 6: REVIEW → step-up 회신

REVIEW 응답을 받은 백엔드는 사용자의 다음 요청 시 [`routes_stepup.py`](../../../backend/app/api/routes_stepup.py) 의 `/challenge` 가 자연스럽게 발동되도록 fraud-service의 `risk_score` 를 갱신한다. 즉, **이 글의 끝은 [`J2`](02_로그인과_적응형_인증.md) 의 단계 3과 만난다**. 사용자 입장에선 "거래 후 다음 행동에서 갑자기 TOTP를 요구당하는" 경험.

### 단계 7: 모든 결과의 감사 기록

PASS·REVIEW·BLOCK 어느 결과든 [`fraud-service/app/services/audit_logger.py`](../../../fraud-service/app/services/audit_logger.py) 와 [`blockchain_audit.py`](../../../fraud-service/app/services/blockchain_audit.py) 에 SHA-256 해시 체인으로 적재된다 ([`J5`](05_사후_감시와_감사.md) 에서 이어 본다).

## ⑤ 통합 설계 트레이드오프

- **하드코딩된 가중치 0.7/0.3**: [ensemble.py:13](../../../fraud-service/app/scoring/ensemble.py:13) 에 상수로 박혀 있다. 운영에선 사용자 세그먼트·시간대별로 조정해야 하지만 현재는 단일 값. 주석에도 "나중에 SYSTEM_CONFIG 또는 .env로 빼도 됨" 으로 미완 표시.
- **선형 정규화의 단순함**: [ensemble.py:23](../../../fraud-service/app/scoring/ensemble.py:23) 의 `LOW=-0.5, HIGH=-0.05` 클리핑이 IF 분포를 가정하고 있다. 모델 재학습 시 분포가 바뀌면 가중치가 의미를 잃는 잠재 문제.
- **룰 vs ML 우선순위 모호성**: 현재 정책 병합은 OR 형태로 보수적(둘 중 하나라도 BLOCK이면 BLOCK)이지만, false positive 비용이 큰 비즈니스에선 AND나 신뢰 가중 평균이 적절. [`#13 글`](../../13_규칙_엔진.md) 의 트레이드오프 절 참조.
- **REVIEW의 사용자 경험 마찰**: step-up이 너무 자주 트리거되면 사용자가 OTP 피로(OTP fatigue)를 겪는다. 임계값 0.6의 의미는 [`J2`](02_로그인과_적응형_인증.md) 와 동일하게 시스템 공통 상수 — 사용자별 적응형으로 가는 게 다음 단계.
- **Kafka 미연결**: 평가 결과가 다른 서비스로 비동기 전파되어야 하는 시점이 있지만 현재 [`#19 Kafka`](../../19_Kafka_이벤트_스트림.md) 는 코드만 있고 broker 미연결.

## ⑥ 한 줄 정리

거래 한 건은 ML 앙상블 + 규칙 + 행동 시그널의 **3겹 평가**를 거쳐 PASS/REVIEW/BLOCK 으로 응축되며, REVIEW는 곧 사용자에게 step-up이라는 마찰을 만든다.
