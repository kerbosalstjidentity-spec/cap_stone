# [J2] 로그인과 적응형 인증 — 같은 비밀번호, 다른 결과

> **사용자 여정 시리즈 2편**. "로그인" 한 단어 안에 비밀번호 검증·리스크 평가·Step-up 분기·세션 갱신이 모두 들어 있다. 같은 사용자가 같은 비밀번호로 들어와도 **그날의 위험 신호**에 따라 다른 경로를 타는 흐름을 따라간다.

---

## ① 관점 정의

PayWise의 로그인은 "맞으면 통과·틀리면 실패"의 단순 게이트가 아니다. fraud-service가 매기는 리스크 스코어, 사용자의 등록된 2FA 수단, 직전 로그인의 행동 시그널이 **로그인 직후의 추가 인증 요구 여부**를 결정한다. 이 글은 로그인 한 번이 시스템 안에서 **분기 트리**로 펼쳐지는 모습을 본다.

---

## ② 전체 흐름도

```
사용자 (이메일 + 비번 입력)
   │
   ▼
POST /v1/auth/login
   │
   ├─ bcrypt verify_password() → 실패 시 보안이벤트 기록 후 401
   │
   ├─ 성공: access + refresh JWT 발급
   │   │
   │   ▼
   ├─ TOTP 활성? → /login/totp 한 단계 더 (#1 영역)
   │
   ▼
프론트가 보호 페이지 진입 시도 (예: /strategy, /security)
   │
   ▼
GET 또는 사용자 액션 → POST /v1/auth/stepup/challenge
   │
   ├─ fraud-service에 fetch_fraud_profile(user_id)
   │   └ 응답의 risk_score 추출
   │
   ├─ risk_score < 0.6 → required=False, 그대로 통과
   │
   └─ risk_score ≥ 0.6
       ├─ 사용자 totp_enabled? → method = "totp"
       ├─ FIDO Credential 등록? → method = "fido"
       └─ 둘 다 없음 → method = "none" + 경고
              ▼
       stepup_token 발급 (10분 TTL)
              ▼
       POST /v1/auth/stepup/verify  (TOTP 코드 또는 FIDO assertion)
              ▼
       성공 시 새 access_token 발급, StepUpSession.verified = true
```

---

## ③ 단계별 핵심

### 단계 1: 비밀번호 검증과 보안 이벤트 기록

[`routes_auth.py`](../../../backend/app/api/routes_auth.py) 의 `login` 핸들러는 `verify_password()` 결과와 무관하게 `_log_security_event()` 를 호출해 **성공/실패 양쪽 모두**를 `StepUpSession` 테이블에 누적한다 ([routes_auth.py:41](../../../backend/app/api/routes_auth.py:41)). 이 누적이 [`#14 행동 시그널`](../../14_행동_시그널_분석.md) 의 입력이 된다.

### 단계 2: TOTP 1차 게이트

`totp_enabled=True` 사용자는 비밀번호 통과 후에도 TOTP 코드를 한 번 더 받는다. 이는 step-up과 별개의 "1차 2FA"로, [`#1 글`](../../01_기본인증_회원가입_로그인_JWT.md) 에서 다룬 영역. 여정 관점에서는 **로그인 한 번에 들어 있는 두 개의 2FA 트리거 (TOTP at login vs TOTP at step-up)** 를 구분해서 보는 게 핵심이다.

### 단계 3: 리스크 스코어 조회

[`routes_stepup.py:26`](../../../backend/app/api/routes_stepup.py:26) 의 `_get_risk_score()` 가 `fetch_fraud_profile(user_id)` 로 fraud-service의 `/v1/profile/{user_id}` 를 조회한다. 실패 시 0.0 반환 — 즉, **fraud-service 장애 시 step-up은 자동으로 비활성화**된다. 이는 가용성 우선의 의도된 fail-open 정책이지만, 트레이드오프 거리.

### 단계 4: 임계값 비교와 분기

[`routes_stepup.py:66`](../../../backend/app/api/routes_stepup.py:66) 의 `risk_score < settings.STEPUP_RISK_THRESHOLD` (기본 0.6) 비교가 분기점. 이상이면 `_determine_method()` 로 TOTP/FIDO 우선순위를 정한다. 등록된 2FA가 하나도 없으면 `method="none"` + 경고 메시지로 끝나는데, 이는 **사용자에게 등록을 강제할 수 없는 정책적 한계**다.

### 단계 5: stepup_token 발급과 DB 기록

[`routes_stepup.py:94`](../../../backend/app/api/routes_stepup.py:94) 의 `create_stepup_token()` 으로 발급된 토큰은 일반 access 토큰과 `type` 필드로 구분된다. `StepUpSession` 행이 동시에 INSERT 되어 검증 단계에서 매칭되며, **재사용 방지**를 위해 `verified` 플래그가 한 번만 True 로 바뀐다 ([routes_stepup.py:151](../../../backend/app/api/routes_stepup.py:151)).

### 단계 6: 검증과 토큰 갱신

[`routes_stepup.py:120`](../../../backend/app/api/routes_stepup.py:120) 의 `verify_challenge()` 가 (a) 토큰 type 검증, (b) DB 세션 매칭, (c) TTL 검사, (d) 메서드별 코드/assertion 검증, (e) 새 access_token 발급까지 한 번에 처리한다. 즉 **step-up 성공 == 새 권한 부여**의 의미가 명시적으로 토큰 갱신으로 표현된다.

## ⑤ 통합 설계 트레이드오프

- **Fail-open 정책**: fraud-service 장애 시 step-up이 비활성화되는 건 가용성 우선이지만 보안 관점에선 약점. 운영에선 임계값 동적 조정이나 캐시된 직전 스코어 fallback을 고민해야 한다.
- **임계값 0.6 고정**: 한 사용자의 평소 패턴이 아니라 전 시스템 공통 상수. 사용자별 적응형 임계값(예: 거래 평균 X% 이상)이 더 정교하지만 미구현.
- **두 개의 TOTP 트리거**: 로그인 직후 TOTP와 step-up TOTP가 둘 다 존재. 사용자 입장에선 "왜 또?"라는 마찰이 생길 수 있어, UX 관점에선 통합 여지.
- **`verified` 플래그 단일 사용**: step-up 토큰은 한 번만 쓰이고 파기. 다단계 워크플로우 중간에 새 step-up이 필요하면 새 토큰을 받아야 한다.
- **로그인 실패 누적과 잠금 정책**: 실패도 `StepUpSession` 에 기록되지만 N회 잠금 같은 정책은 아직 명시적으로 없다.

---

## ⑥ 한 줄 정리

PayWise 로그인은 비밀번호 검증 + 리스크 스코어 조회 + 2FA 메서드 분기 + 토큰 갱신이 **한 흐름의 분기 트리**로 묶인 적응형 인증 게이트다.
