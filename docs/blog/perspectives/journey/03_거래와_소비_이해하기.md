# [J3] 거래와 소비 이해하기 — 한 건의 결제가 5개의 관점으로 펼쳐진다

> **사용자 여정 시리즈 3편**. 거래 한 건이 PayWise에 들어오면 카테고리·패턴·예측·과소비·감정 5개의 분석 모듈을 동시에 자극한다. 사용자가 `/analysis` 한 페이지에서 보는 풍경이 어떻게 만들어지는지를 따라간다.

---

## ① 관점 정의

PayWise의 차별점은 "거래 내역 보기"가 아니라 **"거래에서 의미 만들기"** 다. 같은 카드 결제 한 건이 (1) 자동 분류된 카테고리, (2) 군집화된 소비 패턴, (3) 다음 달 예측, (4) 과소비 점수와 SHAP 설명, (5) 감정 라벨까지 동시에 출력된다. 이 글은 이 5개 모듈이 **공통 입력 위에서 어떻게 다른 출력을 만드는가**를 본다.

---

## ② 전체 흐름도

```
거래 데이터 (회원가입 시 시딩 또는 시뮬레이터)
  └ Transaction 테이블 (user_id, amount, merchant, ts, ...)
       │
       ├──── ① category_engine
       │     └ 키워드/룰 → category_id 부여 → spend_profile 누적
       │
       ├──── ② ml/clustering (KMeans)
       │     └ 카테고리별 소비 비율 벡터 → 군집 할당
       │
       ├──── ③ ml/forecasting (LSTM)
       │     └ 최근 N개월 시계열 → 다음 달 카테고리별 지출 예측
       │
       ├──── ④ ml/classifier + xai_engine (XGBoost + SHAP)
       │     └ 과소비 확률 + 기여도 상위 특성 설명
       │
       └──── ⑤ emotion_engine
             └ 메모/시간대/카테고리 기반 감정 라벨 (스트레스·계획·충동…)

       ▼
프론트 /analysis 페이지가
  GET /v1/analysis, /v1/spend-profile, /v1/xai, /v1/emotion 호출
  → 5개 카드 동시 렌더링
```

---

## ③ 단계별 핵심

### 단계 1: 카테고리 분류가 모든 분석의 전제

[`backend/app/services/category_engine.py`](../../../backend/app/services/category_engine.py) 가 키워드 룰 + 가맹점 매핑으로 카테고리를 부여한다. 이 결과가 **나머지 4개 모듈의 공통 입력 축**이 된다 ([`#8 카테고리`](../../08_카테고리_자동_분류.md)). 잘못된 카테고리 매핑은 군집·예측·과소비·감정 모두에 동시 오염을 유발하는 단일 장애점.

### 단계 2: 군집화로 "이 사용자의 소비 유형" 추출

[`backend/app/ml/clustering.py`](../../../backend/app/ml/clustering.py) 의 KMeans가 카테고리별 비율 벡터를 받아 군집 ID를 매긴다 ([`#5 KMeans`](../../05_소비_패턴_분석_KMeans_군집화.md)). 군집 결과는 `spend_profile_db` 에 저장되어 다른 모듈이 재사용한다.

### 단계 3: 예측은 "내 미래 지출"의 거울

[`backend/app/ml/forecasting.py`](../../../backend/app/ml/forecasting.py) 의 LSTM 모델이 최근 시계열로 다음 달 카테고리별 지출을 예측한다 ([`#6 LSTM`](../../06_지출_예측_LSTM_시계열.md)). 사용자가 보는 "다음 달 식비 예상 +12%" 같은 숫자가 이 단계의 산출물.

### 단계 4: 과소비 분류 + XAI 설명

[`backend/app/ml/classifier.py`](../../../backend/app/ml/classifier.py) 가 XGBoost 로 과소비 확률을 매기고, [`backend/app/services/xai_engine.py`](../../../backend/app/services/xai_engine.py) 가 SHAP 값으로 "어느 특성이 점수를 끌어올렸는지" 상위 N개를 뽑는다 ([`#7 XAI`](../../07_과소비_분류_XAI_XGBoost_SHAP.md)). 사용자에게는 점수만이 아니라 **이유를 함께** 보여준다.

### 단계 5: 감정 라벨로 "왜 그렇게 썼나" 채색

[`backend/app/services/emotion_engine.py`](../../../backend/app/services/emotion_engine.py) 는 거래 메모·시간대·카테고리 조합을 룰 기반으로 분석해 "스트레스성", "계획성", "충동성" 라벨을 붙인다 ([`#9 감정`](../../09_감정_기반_소비_분석.md)). ML 모델 없이 룰만으로 동작하는 최소 구현이지만, UX 임팩트는 크다.

### 단계 6: 5개 결과의 동시 렌더링

프론트 `/analysis` 페이지는 5개 API를 **병렬로** 호출한다. 한 모듈이 늦으면 그 카드만 스피너가 도는 식의 느슨한 결합. 이 비동기성 덕에 LSTM 예측이 1초 걸려도 다른 카드는 즉시 뜬다.

## ⑤ 통합 설계 트레이드오프

- **단일 장애점으로서의 카테고리 분류**: 룰 미스가 있으면 4개 다른 모듈로 오염이 번진다. 운영에선 카테고리 confidence score를 함께 저장해 하위 모듈이 가중치로 쓰는 구조가 더 견고하다.
- **5개 모듈 출력의 일관성 부재**: 같은 사용자에 대해 "절약형 군집(#5)"인데 "과소비 위험 70%(#7)"가 동시에 나올 수 있다. 모듈 간 의미 통합은 미구현 — 프론트가 단순 나열한다.
- **감정 라벨의 룰 의존성**: ML 없이 룰 기반이라 시연엔 충분하지만 새 패턴 추가가 코드 수정과 재배포로 이어진다. 향후 [`#9 글`](../../09_감정_기반_소비_분석.md) 의 확장 절에서 다룬 룰 외부화가 필요. (✅ ROADMAP W5-#8 — `backend/app/policies/emotion_rules.json` 외부화 + `reload_emotion_rules()` 핫 로드, `EMOTION_RULES_PATH` env 오버라이드)
- **시드 데이터에 의존한 분석 품질**: 실제 거래가 적은 신규 사용자는 [`J1`](01_가입과_온보딩.md) 에서 시딩된 120건에 의존한다. 시딩 분포가 ML 모델 결과를 왜곡할 가능성.

---

## ⑥ 한 줄 정리

거래 한 건은 카테고리를 거쳐 5개 분석 모듈로 동시에 펼쳐지며, 사용자가 보는 `/analysis` 페이지는 **이 병렬 출력의 시각적 합성**이다.
