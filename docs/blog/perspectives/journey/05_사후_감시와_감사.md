# [J5] 사후 감시와 감사 — 결정이 끝난 뒤에 남는 것들

> **사용자 여정 시리즈 5편 (마지막)**. 거래·인증·차단의 결정이 일단 내려진 뒤, 시스템은 그 결정을 어떻게 **기록·증명·관측·학습**하는가? 알림 → 보안 대시보드 → 블록체인 감사 → ABAC 접근 제어 → 위협 인텔리전스의 사후 레이어를 본다.

---

## ① 관점 정의

PayWise의 사후 단계는 단순 로깅이 아니다. (1) 사용자에게 **즉시 알림**, (2) 보안 대시보드의 **종합 시연**, (3) 해시 체인으로 **부인 방지**, (4) ABAC/ABE로 **사후 접근의 권한 제어**, (5) 위협 인텔리전스의 **유사 패턴 탐지**가 한 묶음으로 동작한다. 이 글은 결정이 내려진 뒤의 풍경을 따라간다.

---

## ② 전체 흐름도

```
[J4] 의 BLOCK / REVIEW / PASS 결정
      │
      ├──── ① 알림: notification_service + push_service
      │     └ in-app 토스트 + 디바이스 푸시 (#21)
      │
      ├──── ② 블록체인 감사: audit_logger + blockchain_audit
      │     └ SHA-256 prev_hash 체인으로 묶음 (#16)
      │       (fraud-service: audit_chain.json)
      │       (backend: 인메모리 미러, /audit/* API)
      │
      ├──── ③ ABAC 평가
      │     └ 보안팀이 사용자의 거래 상세 조회 시도
      │       → user_role + clearance + location 등 속성 평가
      │       → allowed / masked_fields 결정 (#15)
      │
      ├──── ④ ABE 암호화
      │     └ 민감 필드(PAN, 주민번호 등)는 속성 기반 암호화
      │       → 권한자만 복호화 가능 (#15 ABE 절)
      │
      └──── ⑤ 위협 인텔리전스 매칭
            └ IP·디바이스·MCC 패턴이 외부 위협 DB와 매칭되는지
              (#17 — 캡스톤은 시뮬레이션 DB)

      ▼
사용자/관리자 진입점:
  /security              메인 보안 점수
  /security/blockchain   감사 체인 뷰어
  /security/protocols    ABAC 테스트 + 6개 프로토콜 카드
  /security/mydata       동의 + PID 관리
```

## ③ 단계별 핵심

### 단계 1: 사용자에게 즉시 알림

[`backend/app/services/notification_service.py`](../../../backend/app/services/notification_service.py) 가 in-app 알림을 큐에 넣고, [`fraud-service/app/services/push_service.py`](../../../fraud-service/app/services/push_service.py) 가 디바이스 푸시를 발사한다 ([`#21 알림`](../../21_알림_시스템.md)). BLOCK은 즉시·고우선, PASS는 일반 거래 알림. **알림이 늦으면 사기 차단의 의미가 줄어든다**는 점에서 비동기 큐의 지연 관리가 중요하다.

### 단계 2: 블록체인 감사 — 두 개의 체인

[`fraud-service/app/services/blockchain_audit.py`](../../../fraud-service/app/services/blockchain_audit.py) 가 **운영 체인**(JSON 파일 영속화)이고, [`backend/app/api/routes_security_dashboard.py`](../../../backend/app/api/routes_security_dashboard.py) 의 `_AUDIT_CHAIN: list[dict]` 가 **시연용 인메모리 미러**다 ([`#16 블록체인 감사`](../../16_블록체인_감사_로그.md), [`#4 보안 대시보드`](../../04_보안_대시보드.md)). 두 체인이 별개로 운영되는 점이 본 시리즈에서 처음으로 명확해진다 — 이는 의도적 분리(시연 안정성 vs 운영 무결성)지만 **단일 진실 출처가 없다는 점**은 트레이드오프.

### 단계 3: ABAC — 사후 조회의 게이트

보안팀·관리자가 사후 조사 목적으로 거래 상세를 보려 할 때 [`fraud-service/app/services/abac_engine.py`](../../../fraud-service/app/services/abac_engine.py) 가 8개 룰로 평가한다 ([`#15 ABAC`](../../15_ABAC_ABE_접근제어.md)). 결과는 단순 allow/deny 가 아니라 **마스킹된 필드 목록**. 즉 한 명의 사용자에게 같은 자원이 다르게 보인다.

### 단계 4: ABE — 민감 데이터의 추가 잠금

[`fraud-service/app/services/abe_engine.py`](../../../fraud-service/app/services/abe_engine.py) 의 ABE는 ABAC 통과 후에도 민감 필드(예: 카드 번호 전체)는 **속성 기반 암호화** 로 한 겹 더 잠근다 ([`#15 글의 ABE 절`](../../15_ABAC_ABE_접근제어.md)). 권한 매트릭스가 정책에 박혀 있어 정책 변경 시 재암호화가 필요한 점이 트레이드오프.

### 단계 5: 위협 인텔리전스 — 유사 패턴 매칭

[`fraud-service/app/api/routes_intelligence.py`](../../../fraud-service/app/api/routes_intelligence.py) 와 [`intelligence_store.py`](../../../fraud-service/app/services/intelligence_store.py) 가 IP·디바이스·MCC 패턴을 외부 위협 DB(시뮬레이션)와 매칭한다 ([`#17 위협 인텔`](../../17_위협_인텔리전스.md)). 한 사용자의 BLOCK이 곧 다른 사용자에 대한 사전 차단 신호로 이어지는 패턴 학습 루프의 시작점.

## ⑤ 통합 설계 트레이드오프

- **두 개의 감사 체인 분리**: backend의 인메모리 체인과 fraud-service의 파일 체인이 별개로 동작한다. 시연 안정성은 좋지만 **단일 진실 출처가 없는 것**은 운영에선 약점. backend가 fraud-service 체인을 read-only로 미러링하는 구조가 더 정합적.
- **인메모리의 휘발성**: backend `_AUDIT_CHAIN` 은 프로세스 재시작 시 초기화. 캡스톤 시연 컨텍스트에서는 OK이나 실서비스로 가려면 PostgreSQL/Redis 영속화 필요.
- **ABAC 룰 수의 차이**: backend 시뮬레이터는 5개 룰, fraud-service의 실제 엔진은 8개 룰 ([`#4 글`](../../04_보안_대시보드.md) 의 ⑤ 참조). 두 곳의 정책 일관성이 정책 변경 시 누가 먼저 갱신되는지에 따라 갈린다.
- **위협 인텔의 외부 연동 부재**: 캡스톤 단계에서는 시뮬레이션 DB. 실제 OSINT/상용 위협 피드 연동은 향후 과제로 [`#17 글`](../../17_위협_인텔리전스.md) 에서 짚었다.
- **알림 채널 단일화 부재**: in-app과 push가 별개 서비스로 분리. 채널 우선순위·중복 억제 정책이 명시적으로 정의되지 않았다.

---

## ⑥ 한 줄 정리

PayWise의 사후 단계는 알림·감사·접근 제어·암호화·위협 인텔이 **한 결정의 5개 그림자**처럼 동시에 남는 구조이며, 이 그림자들이 모이는 곳이 보안 대시보드다.
