# [P3] 추론 하이브리드 스코어 — 거래 한 건이 점수 한 줄로 응축되는 30ms

> **데이터 파이프라인 시리즈 3편**. 학습된 모델 번들이 메모리에 로드되어 있는 상태에서, 거래 한 건이 들어오면 어떤 함수 호출 사슬을 거쳐 PASS/REVIEW/BLOCK 결정이 응답으로 나가는지를 따라간다.

---

## ① 관점 정의

[`P2`](02_모델_학습_파이프라인.md) 가 모델을 만드는 단계라면, 본 단계는 **모델을 쓰는 단계**다. 학습은 시간 단위·배치 단위로 일어나지만 추론은 거래 한 건당 수십 ms 안에 끝나야 한다. 이 글은 (1) 특성 추출, (2) 모델 호출, (3) 정규화, (4) 가중 결합, (5) 룰 보정, (6) 정책 병합의 6단계를 **함수 호출 단위**로 본다.

---

## ② 전체 흐름도

```
HTTP POST /v1/score  { user_id, transaction: {...} }
   │
   ▼
routes_score.py: score_transaction()
   │
   ├─ scoring/features.py: extract_features(tx, profile)
   │   └ np.ndarray (1, N) 반환
   │
   ├─ scoring/model_loader.py: get_bundle()
   │   └ 메모리 캐시된 번들 반환 (시작 시 1회 로드)
   │
   ├─ XGBoost 추론
   │   └ bundle["xgboost"].predict_proba(X)[0][1] → xgb_proba
   │
   ├─ scoring/ensemble.py: ensemble_score(xgb_proba, bundle, X)
   │   ├─ IF 없으면 (xgb_proba, None) 그대로 반환
   │   └─ IF 있으면:
   │       ├─ iso.score_samples(X)[0] → raw (음수)
   │       ├─ _normalize_anomaly(raw) → [0,1]
   │       └─ 0.7·xgb_proba + 0.3·anomaly → final
   │
   ▼
HTTP POST /v1/fraud/evaluate  { user_id, score, ... }
   │
   ├─ services/rule_engine.py: evaluate_rules(tx, score)
   │   └ 결정적 룰 평가 → [{rule_id, triggered, severity}, ...]
   │
   ├─ services/behavioral_signals.py: get_signal_weight(user_id)
   │   └ 평소 패턴 대비 가중치
   │
   ├─ services/policy_merge.py: merge(score, rules, weight)
   │   └ action 결정: PASS / REVIEW / BLOCK
   │
   ▼
응답: { action, score, reasons[], stepup_required }
```

## ③ 단계별 핵심

### 단계 1: 특성 추출의 동기성

[`fraud-service/app/scoring/features.py`](../../../fraud-service/app/scoring/features.py) 가 거래·프로필을 받아 numpy 벡터를 만든다. 프로필 조회는 [`profile_store.py`](../../../fraud-service/app/services/profile_store.py) 또는 Redis 백엔드의 [`profile_store_redis.py`](../../../fraud-service/app/services/profile_store_redis.py). **Redis 캐시 히트가 추론 latency 의 가장 큰 변수**다.

### 단계 2: 번들의 메모리 보유

[`fraud-service/app/scoring/model_loader.py`](../../../fraud-service/app/scoring/model_loader.py) 가 시작 시 번들을 한 번 로드해 모듈 전역에 보관. 매 요청마다 디스크 I/O가 없다 — 다만 모델 교체 시 재시작 필요 ([`P2`](02_모델_학습_파이프라인.md) ⑤ 참조).

### 단계 3: XGBoost 추론의 결정적 부분

`predict_proba()` 가 [0,1] 확률 반환. 이는 모델이 학습 분포 내라면 안정적. 학습 분포 밖 거래(예: 새로운 MCC, 새로운 통화)는 **확률이 의미를 잃는** 회색지대다. 본 시스템은 이를 IF로 보강한다.

### 단계 4: Isolation Forest 의 정규화 트릭

[`ensemble.py:17`](../../../fraud-service/app/scoring/ensemble.py:17) 의 `_normalize_anomaly()` 가 IF의 음수 점수를 [0,1] 로 변환한다. 핵심 코드:

```python
LOW, HIGH = -0.5, -0.05
clipped = max(LOW, min(HIGH, raw_score))
normalized = (clipped - HIGH) / (LOW - HIGH)
```

`-0.5` 가 1 (이상), `-0.05` 가 0 (정상). 이 두 상수는 학습 시점 분포 가정. **분포가 바뀌면 정규화가 의미를 잃는** 잠재 버그 영역.

### 단계 5: 가중 결합의 단순성

[`ensemble.py:45`](../../../fraud-service/app/scoring/ensemble.py:45) 의 `combined = ALPHA * xgb_proba + BETA * anomaly` 가 핵심 한 줄. 단순 선형 결합이 의외로 강건한 이유는 두 모델이 **서로 다른 가정**을 사용하기 때문. 비선형 메타 학습기(스태킹)는 캡스톤 범위 외.

### 단계 6: 룰 엔진의 평가

[`rule_engine.py`](../../../fraud-service/app/services/rule_engine.py) 가 결정적 룰 목록을 순회한다 ([`#13 규칙 엔진`](../../13_규칙_엔진.md)). 각 룰이 (triggered, severity) 를 반환하고, 이게 ML 점수와 함께 다음 단계로 전달된다.

### 단계 7: 정책 병합과 응답

[`policy_merge.py`](../../../fraud-service/app/services/policy_merge.py) 가 (ML 점수, 룰 결과, 행동 가중치) → action 결정. 응답에는 `reasons[]` 배열로 어떤 룰·어떤 모델이 결정에 기여했는지가 포함되어 사용자/관리자에게 노출된다 — 이는 [`#7 XAI`](../../07_과소비_분류_XAI_XGBoost_SHAP.md) 와 결을 같이하는 **설명 가능성** 의 한 형태.

## ⑤ 통합 설계 트레이드오프

- **정규화 상수 분포 가정**: [`ensemble.py:23`](../../../fraud-service/app/scoring/ensemble.py:23) 의 `-0.5/-0.05` 가 학습 시점 분포에 핀됨. 모델 재학습 시 이 상수도 재추정해야 하지만 **자동 추정이 없다** — 운영자가 수동 갱신.
- **try/except 의 무음 폴백**: [`ensemble.py:42`](../../../fraud-service/app/scoring/ensemble.py:42) 의 `except Exception: return xgb_proba, None` 은 IF 호출이 실패해도 단독 점수로 폴백한다. 가용성은 좋지만 **무음 실패** — 로깅·모니터링이 없으면 IF가 영원히 동작하지 않는 상태로 운영될 수 있다.
- **추론 latency 측정 부재**: 각 단계의 latency 를 응답 헤더나 메트릭으로 노출하는 명시적 코드가 없다. P99 latency 추적은 [`M4`](../mlops/04_운영_관측과_향후_과제.md) 향후 과제.
- **profile_store 의 두 백엔드**: [`profile_store.py`](../../../fraud-service/app/services/profile_store.py) (인메모리)와 [`profile_store_redis.py`](../../../fraud-service/app/services/profile_store_redis.py) (Redis)가 공존. 환경별 선택 로직이 명시적으로 정리되어 있는지가 운영 안정성의 한 축.
- **두 단계 HTTP 호출**: `/v1/score` → `/v1/fraud/evaluate` 가 분리되어 있어 네트워크 왕복이 두 번. 단일 엔드포인트로의 합치기는 호출자 편의 vs 모듈 분리의 트레이드오프.

---

## ⑥ 한 줄 정리

추론은 특성 추출 → 두 모델 호출 → 정규화 → 가중 결합 → 룰 보정 → 정책 병합의 6단계가 한 거래당 30ms 안에 응축되며, **정규화 상수의 분포 가정**이 가장 자주 깨지는 부분이다.
