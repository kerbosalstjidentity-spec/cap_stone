# [P1] 데이터 수집과 특성 공학 — 거래 한 행이 모델 입력 벡터가 되기까지

> **데이터 파이프라인 시리즈 1편**. 거래 데이터가 DB에 적재되어 카테고리 분류·감정 라벨·행동 시그널·소비 비율 벡터로 변환되는 과정을 따라간다. ML 모델이 보는 것은 "거래 한 건" 이 아니라 **이 단계에서 만들어진 파생 특성들** 이다.

---

## ① 관점 정의

ML 시스템에서 가장 자주 깨지는 곳은 모델이 아니라 **그 앞단의 특성 공학**이다. 같은 거래도 어떻게 변환하느냐에 따라 군집·예측·과소비·사기 점수가 모두 달라진다. 이 글은 PayWise가 "원시 거래 → 모델 입력" 구간에서 어떤 변환을 하는지, 그리고 어디에 단일 장애점이 있는지를 본다.

---

## ② 전체 흐름도

```
거래 데이터 (Transaction 테이블)
   user_id, amount, merchant, category_raw, ts, ...
        │
        ├──── ① category_engine.py
        │     └ 키워드/가맹점 룰 → category_id
        │       (모든 후속 모듈의 공통 축)
        │
        ├──── ② spend_profile.py / spend_profile_db.py
        │     └ 사용자별 카테고리 비율 벡터 누적
        │       (KMeans 입력)
        │
        ├──── ③ emotion_engine.py
        │     └ 메모·시간대·카테고리 → 감정 라벨
        │
        ├──── ④ behavioral_signals.py
        │     └ 디바이스·시간대·IP 패턴
        │
        └──── ⑤ fraud-service/scoring/features.py
              └ 사기 모델 입력 벡터
                (금액 로그·시간대·MCC·국가·평소 차이 등)

   ▼ 산출물
- spend_profile_db: 카테고리 비율 (KMeans, 군집 ID)
- emotion_label: 라벨 (스트레스·계획·충동)
- behavioral profile: risk_score 의 한 입력
- feature vector: 사기 점수 모델 입력
```

## ③ 단계별 핵심

### 단계 1: 카테고리 엔진의 단일 진입점

[`backend/app/services/category_engine.py`](../../../backend/app/services/category_engine.py) 가 키워드/가맹점 룰로 거래의 카테고리를 부여한다 ([`#8 카테고리`](../../08_카테고리_자동_분류.md)). 이 결과가 후속 4개 모듈 모두의 입력이 된다 — 즉 **이 한 모듈의 정확도가 파이프라인 전체 정확도의 상한을 정한다**.

### 단계 2: 소비 프로필의 누적 모델

[`backend/app/services/spend_profile.py`](../../../backend/app/services/spend_profile.py) 가 사용자별로 카테고리 비율 벡터를 누적한다. [`spend_profile_db.py`](../../../backend/app/services/spend_profile_db.py) 가 영속화. 이 벡터가 KMeans 군집화의 직접 입력이다 ([`#5 KMeans`](../../05_소비_패턴_분석_KMeans_군집화.md)). **누적 vs 윈도우** 의 선택이 중요한데, 현재는 누적 — 신규 사용자의 데이터 부족 문제가 있다.

### 단계 3: 감정 라벨링의 룰 기반 변환

[`backend/app/services/emotion_engine.py`](../../../backend/app/services/emotion_engine.py) 는 ML 없이 (메모, 시간대, 카테고리) → 라벨의 룰 기반 매핑이다 ([`#9 감정`](../../09_감정_기반_소비_분석.md)). 캡스톤 단계의 합리적 선택이지만, 룰이 코드에 박혀 있어 새 패턴 추가가 재배포로 이어진다.

### 단계 4: 행동 시그널의 시간 윈도우

[`fraud-service/app/services/behavioral_signals.py`](../../../fraud-service/app/services/behavioral_signals.py) 가 사용자의 최근 N건 로그인·디바이스 변경 이벤트를 윈도우로 묶어 평소 패턴을 추정한다 ([`#14 행동 시그널`](../../14_행동_시그널_분석.md)). 이는 [`P3`](03_추론_하이브리드_스코어.md) 의 사기 점수 입력으로 들어간다.

### 단계 5: 사기 모델 특성 추출

[`fraud-service/app/scoring/features.py`](../../../fraud-service/app/scoring/features.py) 가 거래 한 건과 사용자 프로필을 받아 모델 입력 벡터를 만든다. 금액 로그 변환·시간대 원-핫·MCC 임베딩·평균 거래 대비 z-score 등 ([`#12 사기 점수`](../../12_실시간_사기_점수_IF_RF_하이브리드.md) ④ 참조). **이 변환의 정의가 학습 시점과 추론 시점에 일치해야** 모델이 의미 있게 작동.

### 단계 6: 학습/추론의 변환 일관성

[`P2`](02_모델_학습_파이프라인.md) 의 학습 단계에서 쓰는 변환이 본 단계의 추론 변환과 동일해야 한다. 현재는 같은 모듈을 양쪽에서 import 해 쓰는 구조 — 즉 **단일 함수가 학습/추론 두 컨텍스트에서 호출**된다. 코드 변경 시 양쪽이 함께 갱신되는 점이 안전 장치.

## ⑤ 통합 설계 트레이드오프

- **단일 카테고리 룰의 단일 장애점**: 한 번 잘못 분류하면 KMeans·LSTM·과소비·감정·사기 모델이 모두 흔들린다. 분류 confidence를 함께 저장해 하위 모듈이 가중치로 쓰는 방식이 더 견고.
- **누적 vs 윈도우 소비 프로필**: 현재 누적 — 평생 평균이 누적되어 최근 변화에 둔감하다. 슬라이딩 윈도우(예: 최근 90일)가 적응형 분석에 유리.
- **감정 룰의 외부화 부재**: 룰이 코드에 박혀 있어 신규 패턴 추가가 코드 변경. 룰 DSL/JSON 외부 파일로 빼는 게 다음 단계.
- **학습/추론 변환의 임플리시트 결합**: 같은 함수를 import 하는 구조가 안전하지만 **버전 핀이 없다**. 모델 번들이 학습 시점의 변환 함수 버전을 기록하지 않으면 향후 변환 변경 시 추론 결과가 조용히 깨질 수 있다.
- **시드 데이터 의존**: 신규 사용자의 분석은 [`J1`](../journey/01_가입과_온보딩.md) 의 자동 시딩 120건에 의존. 시딩 분포가 카테고리 룰 학습 분포와 다르면 모델 신뢰도 저하.

---

## ⑥ 한 줄 정리

거래 한 행은 카테고리·소비 비율·감정·행동·사기 특성의 5개 변환을 거쳐 모델 입력이 되며, **단일 카테고리 룰의 정확도가 전체 파이프라인 정확도의 상한**이다.
