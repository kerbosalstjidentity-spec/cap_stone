# [P4] 비동기 이벤트 처리 — 설계는 있되 브로커는 없는 Kafka, 그리고 알림

> **데이터 파이프라인 시리즈 4편 (마지막)**. PayWise는 Kafka producer/consumer 코드를 완비했지만 docker-compose 에 broker 가 없어 **현재는 동작하지 않는다**. 이 글은 그 설계 의도, 알림 시스템과의 차이, 그리고 활성화 시 어디가 어떻게 바뀌는지를 본다.

---

## ① 관점 정의

동기 호출만으로 만든 시스템은 한 부분이 느려지면 전체가 느려진다. 비동기 이벤트 처리는 이 결합을 끊는 표준 해법이다. PayWise는 (1) Kafka 기반 사기 평가 결과 비동기 전파를 **설계만** 했고, (2) 알림 시스템은 비동기 큐로 **실제 작동**한다. 이 두 가지의 격차를 보는 것이 본 글의 목적.

---

## ② 전체 흐름도

```
[설계됐지만 비활성] Kafka 흐름
─────────────────────────────────────────────
  fraud-service Producer
    └ scoring 결과 발행 → topic: fraud.score.events
        │
        ▼
  Consumer 들 (예정 — 미구현)
    ├─ backend (사용자 알림)
    ├─ analytics (지표 집계)
    └─ audit (감사 체인 적재)

  현재 docker-compose.yml 에 broker 없음
  → producer.send() 호출이 즉시 실패하거나
    재시도 루프에 들어가지 않도록 try/except 로 감쌈

[실제 동작] 알림 흐름
─────────────────────────────────────────────
  거래/인증/차단 결정
    │
    ▼
  backend/services/notification_service.py
    └ 큐(또는 DB 테이블)에 알림 적재
        │
        ▼
  fraud-service/services/push_service.py
    └ 디바이스 푸시 발사 (외부 푸시 서비스 mock)

  사용자 측면:
    GET /v1/notifications → 미확인 목록
    웹소켓 또는 폴링으로 실시간 갱신
```

## ③ 단계별 핵심

### 단계 1: Kafka 코드의 위치

[`fraud-service/app/kafka/producer.py`](../../../fraud-service/app/kafka/producer.py) 와 [`consumer.py`](../../../fraud-service/app/kafka/consumer.py) 가 aiokafka 기반으로 구현돼 있다 ([`#19 Kafka`](../../19_Kafka_이벤트_스트림.md)). [`kafka/config.py`](../../../fraud-service/app/kafka/config.py) 가 broker 주소·topic 이름·재시도 정책을 담고 있다.

### 단계 2: docker-compose 의 broker 부재

루트 [`docker-compose.yml`](../../../docker-compose.yml) 에 PostgreSQL·Redis 는 있지만 Kafka(또는 Redpanda) 가 없다. 즉 코드는 임포트 가능하지만 실제 연결은 실패하는 상태. 이는 [`#19 글`](../../19_Kafka_이벤트_스트림.md) 에서 명시적으로 "미연결" 로 표기됨.

### 단계 3: Producer 의 안전한 무음

producer 호출은 try/except 로 감싸져 있어 broker 없을 때도 메인 흐름이 죽지 않는다. 즉 **Kafka 가 활성화되든 안 되든 추론 응답은 정상**이다. 이는 점진적 활성화를 위한 설계.

### 단계 4: Consumer 의 부재

producer 만 호출되고 consumer 가 없으면 메시지는 broker 안에서 쌓이거나 삭제된다. 현재는 broker 자체가 없으므로 consumer 부재가 문제가 되지 않지만 **활성화 시 consumer 가 먼저 준비되어야** 메시지 손실이 없다.

### 단계 5: 알림 흐름은 별개로 작동

[`backend/app/services/notification_service.py`](../../../backend/app/services/notification_service.py) 와 [`fraud-service/app/services/push_service.py`](../../../fraud-service/app/services/push_service.py) 는 Kafka 와 무관하게 작동한다. 이들은 **DB 기반 큐 또는 in-process 큐**로 비동기성을 흉내낸다 ([`#21 알림`](../../21_알림_시스템.md)).

### 단계 6: 두 흐름의 통합 가능성

이상적으로는 fraud-service 의 평가 결과가 Kafka 토픽으로 발행되고, 알림 consumer 가 그 토픽을 구독해 푸시·in-app 알림을 발사하는 구조. 현재는 두 시스템이 결합도 없이 각자 작동하는데, **활성화 시 가장 큰 변화가 이 통합**이 될 것.

## ⑤ 통합 설계 트레이드오프

- **설계와 운영의 격차**: Kafka 코드는 완비됐지만 broker 가 없는 상태가 코드베이스에 그대로 남아 있다. **활성화 PR 한 번 + docker-compose 수정** 으로 가능하지만 캡스톤 범위 결정.
- **무음 실패의 위험**: producer try/except 가 broker 없을 때 조용히 넘어가는데, broker 가 활성화된 후 일시 장애가 발생해도 **같은 코드가 메시지를 조용히 버린다**. 활성화 시 dead-letter queue 또는 로깅 강화 필요.
- **알림과 Kafka의 미통합**: 현재 알림은 in-process 큐 / DB 폴링. broker 활성화 후 Kafka 기반으로 옮기면 다중 consumer (analytics, audit, push) 가 같은 이벤트를 분기 소비할 수 있다.
- **순서 보장의 부재**: 한 사용자에 대한 PASS/REVIEW/BLOCK 순서가 토픽 파티션 키 설계에 따라 흐트러질 수 있다. user_id 기준 파티셔닝이 자연스러운 선택이지만 명시적 코드는 미작성.
- **장기 보존 정책**: Kafka 가 활성화되면 토픽 retention 이 새로운 운영 변수가 된다. 감사 목적이라면 별도 영속 저장소(DB)로 흘려야 하는데, 이는 [`T5 감사`](../threat/05_감사와_관측.md) 의 블록체인 체인과 책임 분리가 필요.

## ⑥ 한 줄 정리

비동기 이벤트 처리는 Kafka 가 **설계만 완비된 청사진** 으로 남아 있고 알림 시스템은 별도의 단순 큐로 작동하는 분리 상태로, broker 활성화 시 두 흐름의 통합이 다음 자연스러운 단계다.
