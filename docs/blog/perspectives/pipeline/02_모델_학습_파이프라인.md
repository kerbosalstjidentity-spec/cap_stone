# [P2] 모델 학습 파이프라인 — fds-research 에서 fraud-service 까지

> **데이터 파이프라인 시리즈 2편**. PayWise는 모델을 fraud-service 안에서 학습하지 않는다. **별도 저장소 `fds-research/`** 에서 학습이 일어나고, 결과(joblib 번들)가 fraud-service 의 `models/` 디렉토리로 마운트된다. 이 분리의 의미와 운영 절차를 본다.

---

## ① 관점 정의

추론 서비스 안에서 모델을 학습하면 (1) 학습 부하가 추론을 방해하고, (2) 학습 환경이 추론 의존성과 묶이고, (3) 모델 실험 관리가 어려워진다. PayWise는 학습 저장소(fds-research)와 추론 서비스(fraud-service)를 명시적으로 분리한다. 이 글은 그 분리의 경계선 — **무엇이 어디서 일어나고 무엇이 어디로 흘러가는가** — 를 본다.

---

## ③ 단계별 핵심

### 단계 1: fds-research 저장소의 위치

루트의 [`fds-research/`](../../../fds-research/) 가 별도 git 저장소(또는 서브트리)로 학습 전용. PayWise 메인 저장소와 분리되어 있어 **학습 의존성(scikit-learn, xgboost, pandas, jupyter 등)이 추론 서비스에 들어가지 않는다**. `fds-research/scripts/` 의 두 갈래(`creditcard/`, `open/`)는 데이터셋 출처에 따른 분리.

### 단계 2: Isolation Forest 비지도 학습

`fds-research/scripts/creditcard/` 가 Kaggle 신용카드 데이터셋으로 IF를 학습한다. 라벨 없이 정상 분포를 학습한다는 점이 핵심. 결과는 `score_samples()` 가 음수 점수를 반환하는 sklearn IF 객체 그대로 [`fraud-service/app/scoring/ensemble.py:43`](../../../fraud-service/app/scoring/ensemble.py:43) 에서 호출됨.

### 단계 3: 지도 학습 (XGBoost / RF)

`fds-research/scripts/open/` 가 내부 라벨링된 데이터로 XGBoost 또는 RF를 학습. 산출물은 `predict_proba()` 가 [0,1] 확률을 반환하는 객체. 이 둘이 같은 번들 안에 묶여 `bundle.joblib` 한 파일로 저장된다.

### 단계 4: 번들 포맷의 명시적 키

[`fraud-service/app/scoring/model_loader.py`](../../../fraud-service/app/scoring/model_loader.py) 가 번들을 dict 로 받는다 — `bundle["xgboost"]`, `bundle["isolation_forest"]`. [`ensemble.py:38`](../../../fraud-service/app/scoring/ensemble.py:38) 의 `bundle.get("isolation_forest")` 가 None을 허용하는 게 핵심: **IF 키가 없으면 자동으로 XGBoost 단독 폴백**. 이는 학습 단계가 IF 학습에 실패해도 시스템이 죽지 않게 하는 안전장치.

### 단계 5: 마운트와 핫 리로드

번들 교체 시 fraud-service 컨테이너 재시작이 필요하다. 현재 동적 핫 리로드는 미구현 — 모델 교체가 곧 서비스 재시작이라는 점이 운영 비용. 단, [`#18 A/B 테스트`](../../18_AB_테스트_모델_비교.md) 는 두 번들을 동시에 메모리에 두고 트래픽을 분배하는 방식으로 이를 우회한다.

### 단계 6: 메타데이터의 흔적 추적

학습 시점의 데이터 해시·하이퍼파라미터·지표를 `metadata.json` 으로 함께 저장. 이게 [`M1 학습과 재현성`](../mlops/01_학습과_재현성.md) 의 토대가 된다. 단, 현재 metadata 가 fraud-service 측에서 자동 검증되지는 않는다 — 운영자가 수동 확인.

### 단계 7: backend 의 분석용 학습은 별개

[`backend/app/api/routes_train.py`](../../../backend/app/api/routes_train.py) 는 36줄짜리 짧은 라우터로, 소비 분석용 KMeans·LSTM 학습을 트리거한다 ([`#20 학습 파이프라인`](../../20_모델_학습_파이프라인.md) 의 backend 절). **사기 모델 학습과는 별개의 흐름**으로, 본 글의 fds-research → fraud-service 흐름과 혼동하지 말 것.

## ⑤ 통합 설계 트레이드오프

- **저장소 분리의 운영 비용**: 학습/추론 분리는 좋지만 **번들 전달이 수동**이다. CI/CD 로 fds-research 빌드 → fraud-service 디플로이가 묶여야 운영 가능.
- **번들 포맷의 비공식성**: dict 키(`"xgboost"`, `"isolation_forest"`)가 코드 양쪽에 박혀 있다. 키 변경 시 학습/추론이 한 번에 깨질 수 있다 — 스키마 정의 + 검증 단계가 필요.
- **핫 리로드 부재**: 모델 교체 = 서비스 재시작. A/B 테스트가 우회책이지만 일반화된 동적 로드는 미구현.
- **metadata 검증의 수동성**: 데이터 해시·지표 검증을 운영자가 본다. 자동 임계값 검사(예: AUC 회귀 시 거부)는 [`M3`](../mlops/03_AB_테스트와_모델_평가.md) 에서 다룰 향후 영역.
- **두 학습 흐름의 분리**: backend의 분석 학습 ([routes_train.py](../../../backend/app/api/routes_train.py)) 과 fds-research 의 사기 학습이 별개로 운영. 통합 학습 오케스트레이터가 없는 점이 시스템 복잡도의 한 축.

---

## ⑥ 한 줄 정리

PayWise 의 사기 모델 학습은 **fds-research → joblib 번들 → fraud-service 마운트** 의 명시적 분리 흐름으로, 자동 CI/CD 와 핫 리로드 부재가 운영화 1순위 보강 영역이다.
