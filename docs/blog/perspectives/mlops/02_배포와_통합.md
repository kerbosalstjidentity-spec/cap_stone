# [M2] 배포와 통합 — joblib 한 파일이 운영 트래픽을 받기까지

> **ML 모델 생명주기 시리즈 2편**. fds-research 가 학습한 번들이 fraud-service 의 메모리에 들어가 첫 거래를 평가하는 순간까지의 통합 흐름을 본다. 운영 모델 교체의 비용·위험·우회 전략까지.

---

## ① 관점 정의

학습이 끝났다고 모델이 운영에 들어간 게 아니다. 번들 전달·로딩·검증·트래픽 전환의 4단계가 있고, 각 단계마다 **모델이 잘못 로드된 상태로 운영 트래픽을 받을 위험**이 존재한다. 이 글은 그 위험과 PayWise 의 현재 완화 수준을 본다.

---

## ② 전체 흐름도

```
fds-research/outputs/bundle.joblib
        │  (수동 복사 또는 볼륨 마운트)
        ▼
fraud-service/models/bundle.joblib
        │
        ▼
서비스 시작 또는 재시작
        │
        ▼
scoring/model_loader.py: load_bundle()
        │
        ├─ joblib.load(path)
        ├─ 키 존재 확인 ("xgboost" 필수, "isolation_forest" 옵션)
        └─ 메모리 전역 변수에 보관
        │
        ▼
첫 /v1/score 요청 도착
        │
        ├─ scoring/ensemble.py 가 번들 사용
        └─ 응답 정상 → 신모델이 운영 트래픽 받기 시작

[A/B 우회 경로]
        │
scoring/ab_test.py
        │
        └ user_id 해시로 트래픽 분배
          신·구 번들을 동시에 메모리에 두고 비교
```

---

## ③ 단계별 핵심

### 단계 1: 번들 전달의 수동성

현재는 fds-research 의 산출물을 운영자가 fraud-service 의 `models/` 디렉토리에 복사한다. CI/CD 자동화는 미구현 — **사람이 빠지면 모델이 안 바뀐다**. 운영화 1순위 보강 영역.

### 단계 2: 로딩 시점의 검증

[`fraud-service/app/scoring/model_loader.py`](../../../fraud-service/app/scoring/model_loader.py) 가 시작 시 번들을 로드한다. 키 검증("xgboost" 필수)이 있어 잘못된 번들은 **시작 자체가 실패**한다. 이는 silent failure 보다 안전한 fail-fast 패턴.

### 단계 3: IF 의 옵션성

[`ensemble.py:38`](../../../fraud-service/app/scoring/ensemble.py:38) 의 `bundle.get("isolation_forest")` 가 None 을 허용. 즉 IF 가 빠진 번들도 통과 — **반쪽 모델 운영의 위험**과 **단일 모델 빠짐에도 시스템 가용성 유지**의 트레이드오프. 현재는 후자를 선택.

### 단계 4: 재시작의 비용

번들 교체가 곧 컨테이너 재시작이다. Docker Compose 또는 Kubernetes 환경에서 rolling restart 하면 **순간적으로 점수 응답이 끊긴다**. 이를 회피하려면 동적 hot reload 또는 다중 인스턴스 + 헬스체크 기반 라우팅이 필요.

### 단계 5: A/B 테스트의 다른 의미

[`fraud-service/app/scoring/ab_test.py`](../../../fraud-service/app/scoring/ab_test.py) 는 **두 번들을 동시에 메모리**에 두고 user_id 해시로 트래픽을 나눈다 ([`#18 A/B 테스트`](../../18_AB_테스트_모델_비교.md)). 이는 모델 교체의 **점진적 활성화** 메커니즘이기도 하다 — 신모델을 1%, 10%, 50% 순으로 노출하며 회귀를 모니터링.

### 단계 6: 모델 호환성의 silent breakage

번들 안의 sklearn/xgboost 버전이 추론 환경과 다르면 joblib.load 가 성공해도 predict 가 어긋날 수 있다. [`M1 학습과 재현성`](01_학습과_재현성.md) 에서 다룬 라이브러리 버전 잠금이 이 단계에서 결과로 드러난다.

### 단계 7: 롤백의 단순성

신모델에 문제가 생기면 구 번들로 되돌리고 재시작이 끝. 이는 **상태 없는 배포**의 장점 — DB 마이그레이션처럼 되돌리기 어려운 변경이 없다. 단, A/B 트래픽 분배가 동적이지 않으면 신모델 100% 노출 시점에 문제가 발견되면 롤백까지의 영향이 크다.

## ⑤ 통합 설계 트레이드오프

- **수동 배포의 사람 의존**: 학습 → 복사 → 재시작이 운영자 손에 달려 있다. 실수·누락이 silent. CI/CD 가 다음 보강 1순위. (✅ ROADMAP W6-#5 — `docker-compose.mlflow.yml` 로컬 MLflow 트래킹(SQLite backend + serve-artifacts) + `.github/workflows/ml-train.yml` Docker 빌드·`train_paysim.py --help` 헬스체크 + bundle 스키마/AUC/persistence/training_progress/TABLESAMPLE pytest 잡 3개)
- **로딩 시 키 검증의 좁음**: "xgboost" 키 존재만 본다. 실제 모델이 `predict_proba` 를 갖는지, 입력 차원이 features.py 와 일치하는지는 확인하지 않는다. 추론 첫 요청에서 발견되는 게 현재 수준.
- **IF 빠짐의 무음 폴백**: [`P3`](../pipeline/03_추론_하이브리드_스코어.md) 에서 본 try/except 와 같은 맥락. 가용성 vs 성능 보장의 트레이드오프.
- **재시작 다운타임**: 단일 인스턴스 환경에서는 모델 교체 시 점수 응답이 끊긴다. 다중 인스턴스 + 헬스체크 기반 무중단 배포는 운영화 단계 결정.
- **A/B 의 점진성 부재**: 현재 [`ab_test.py`](../../../fraud-service/app/scoring/ab_test.py) 는 단순 해시 기반 분배 — 트래픽 비율 동적 조정은 미구현. 1%→10%→50% 같은 점진 롤아웃은 다음 보강 영역.

---

## ⑥ 한 줄 정리

배포는 번들 복사 → 로딩 검증 → 트래픽 인입의 3단계로 단순하지만, **수동 절차와 silent breakage 가능성**이 신뢰성의 가장 큰 빚이다.
