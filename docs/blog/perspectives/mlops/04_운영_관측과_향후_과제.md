# [M4] 운영 관측과 향후 과제 — 모델이 살아 있는지 어떻게 아는가

> **ML 모델 생명주기 시리즈 4편 (마지막)**. 모델이 운영 중이라는 사실과 모델이 **여전히 잘 작동하고 있다는 사실**은 다르다. PayWise 의 현재 관측 수준과, 운영화로 가기 위해 채워야 할 6가지 빈칸을 정리한다.

---

## ① 관점 정의

ML 시스템은 운영 시작 시점이 가장 정확하고 시간이 갈수록 성능이 저하된다 (data drift, concept drift). 이를 발견하지 못하면 **모델이 조용히 망가진다**. 본 글은 PayWise 의 현재 관측 수준을 점검하고, 가장 자주 나오는 6가지 빈칸을 캡스톤 다음 단계의 로드맵으로 정리한다.

---

## ③ 단계별 핵심

### 단계 1: 보안 대시보드의 1차 신호

[`#4 보안 대시보드`](../../04_보안_대시보드.md) 의 시간대별 분포가 가장 빠른 신호. 갑자기 BLOCK 비율이 평소 대비 3배 이상이면 (a) 진짜 사기 급증, (b) 모델 오작동, (c) 입력 데이터 변화 셋 중 하나. 즉 **분포 변화가 알람의 시작점**.

### 단계 2: routes_evaluation 의 사후 검증

[`#22 모델 평가`](../../22_모델_평가.md) 가 라벨 도달 후 정밀도·재현율을 갱신. 이는 **신뢰할 수 있는 사후 지표**지만 라벨 lag (며칠~몇 주) 동안은 비어 있다.

### 단계 3: Feature drift — 가장 큰 빈칸

운영 데이터가 학습 분포와 얼마나 다른지를 측정하는 코드는 **현재 미구현**. 학습 시점의 feature 통계(mean, std, quantile) 와 운영 시점의 같은 통계 비교가 표준 방법. 이게 있으면 [`P3`](../pipeline/03_추론_하이브리드_스코어.md) 의 "정규화 상수 분포 가정" 깨짐을 자동 탐지할 수 있다.

### 단계 4: Latency P99 — 응답 시간의 분포

추론 latency 를 P50/P95/P99 로 분리해서 보는 게 표준이지만 현재 명시적 미들웨어가 없다. [`fraud-service/app/middleware/`](../../../fraud-service/app/middleware/) 에 추가할 자연스러운 위치.

### 단계 5: 모델 응답 분포

매일 평균 점수, 점수 분포의 분위수가 안정적인지를 추적해야 한다. 평균 점수가 갑자기 떨어졌다면 (a) 모델이 너무 관대해졌거나 (b) 입력이 정상 쪽으로 치우쳤거나. 자동 알람이 있어야 인지된다.

### 단계 6: 학습 메타데이터 자동 검증

[`M1 학습과 재현성`](01_학습과_재현성.md) 에서 짚은 metadata.json 검증이 fraud-service 시작 시 자동 적용되어야 한다. 예: AUC 임계값 미달 모델은 시작 거부. 현재는 사람이 본다.

### 단계 7: 알람·롤백의 자동화

분포 변화 → 슬랙/이메일 알람 → 운영자 판단 → 수동 롤백 의 흐름이 표준이지만, 현재는 알람부터가 미구현. 알람 → 자동 롤백(이전 번들로 즉시 재시작)은 다음 단계의 보강 영역.

## ⑤ 통합 설계 트레이드오프 (= 향후 과제 6가지)

1. **Feature drift 자동 탐지**: 학습 시점 통계 vs 운영 시점 통계 비교. KS 검정 또는 단순 분위수 차이 임계값 기반.
2. **Latency P99 추적**: 미들웨어로 측정하고 [`#4 글`](../../04_보안_대시보드.md) 의 보안 점수와 함께 노출.
3. **점수 분포 모니터링**: 일별 평균·분위수 시계열을 routes_evaluation 에 추가.
4. **메타데이터 자동 검증**: 모델 로드 시 metadata 의 AUC가 임계값 이상인지 강제. (✅ ROADMAP W6-#4 — `model_loader.validate_metadata_auc()` MODEL_BUNDLE_MIN_AUC env 임계값 미달 시 None+warning 또는 strict 모드 raise, holdout/top-level/holdout_auc/roc_auc 다중 키 추출)
5. **임계값 알람**: 분포·latency·점수 분포 셋 중 하나가 정상 범위를 벗어나면 외부 채널로 알람.
6. **자동 롤백**: 알람 발생 시 이전 번들로 자동 재시작. 또는 A/B 트래픽을 100% → 0% 로 dynamic 하게 차단.

(✅ ROADMAP W7.5-#6 — `/admin/api/slo` 시나리오별 검출률·latency p50/p99·FN/FP·분 단위 시계열 노출)
(✅ ROADMAP W7-#3 — `/admin/api/score-distribution?days=N` 일자별 점수 분포 mean/p50/p95/p99/min/max + block_rate)
(✅ ROADMAP W7-#1 — `drift_detector.py` 양측 KS 통계량 + p-value 근사 + `/admin/api/drift?threshold=0.2` 피처별 드리프트 보고)
(✅ ROADMAP W7-#4 — `alarm_manager.py` 분포 알람 + 자동 롤백 (drift/score p99 임계 초과 시 ensemble 가중치 0,0 강제 + audit log) + `/admin/api/alarm` GET·check·restore)

이 6가지가 운영화의 다음 마일스톤. 현재 PayWise 는 1차 신호(보안 대시보드)와 사후 검증(routes_evaluation)을 갖춘 수준 — **시연·심사용으로는 충분하지만 실서비스화 전에는 6가지 보강이 필수**.

(✅ ROADMAP W7-#2 — LatencyMiddleware: `X-Process-Time-Ms / X-P50-Ms / X-P99-Ms` 응답 헤더 + GET `/admin/api/latency` 경로별 통계)
(✅ ROADMAP W7-#9 — `feedback_store.precision_recall_by_variant` + `StatEntry.ab_variant` + GET `/admin/api/ab-precision-recall` variant 별 TP/FN/FP/TN/F1)
(✅ ROADMAP W6-#3 — `model_loader.validate_bundle()` domain별 필수 키 + predict_proba/score_samples 콜러블 검증, MODEL_BUNDLE_STRICT env)
(✅ ROADMAP W8-#4 — `services/audit_retention.py` 5년 보존 cutoff_datetime / classify_age active/warning/expired / purge_db 배치 삭제 + AUDIT_RETENTION_* env)
(✅ ROADMAP W8-#3 — `services/policy_loader.py` PolicyFile mtime 폴링 hot reload + register/reload_all 레지스트리)

## ⑥ 한 줄 정리

운영 관측은 보안 대시보드의 1차 신호와 routes_evaluation 의 사후 검증으로 시작 라인을 갖췄으나, drift·latency·분포·메타데이터·알람·롤백의 6가지 자동화가 운영화로 가는 다음 마일스톤이다. **W7/W8 완료 시점에 6가지 모두 어드민 API 로 노출 완료** — 시연/심사를 넘어 실서비스 직전 단계 도달.
