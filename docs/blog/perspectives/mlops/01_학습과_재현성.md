# [M1] 학습과 재현성 — 같은 결과를 다시 만들 수 있어야 모델이다

> **ML 모델 생명주기 시리즈 1편**. ML 모델이 운영에 들어가는 순간, "어떻게 학습됐는지" 가 곧 시스템의 일부가 된다. 데이터 해시·하이퍼파라미터·시드·번들링이 어떻게 묶여야 6개월 뒤에도 같은 모델을 다시 만들 수 있는지를 본다.

---

## ① 관점 정의

ML 시스템의 가장 큰 빚(debt) 중 하나는 **재현 불가능한 학습**이다. 산출물(joblib 번들)만 있고 그걸 어떻게 만들었는지가 사라지면, 모델 디버깅·규제 대응·재학습이 모두 막힌다. 본 글은 PayWise 가 이 빚을 어떻게 관리하는지, 그리고 어디에 구멍이 남았는지를 본다.

---

## ② 전체 흐름도

```
재현성을 위해 묶여야 할 정보
─────────────────────────────────────
  ① 학습 데이터의 해시 (예: SHA-256 of CSV)
  ② 학습 코드 버전 (git commit hash)
  ③ 하이퍼파라미터 (n_estimators, max_depth, ...)
  ④ 랜덤 시드
  ⑤ 라이브러리 버전 (sklearn, xgboost, ...)
  ⑥ 평가 지표 (AUC, precision@K, ...)
  ⑦ 학습 환경 (Python 버전, 하드웨어)

  ▼ PayWise 의 현재 상태

  fds-research/scripts/<dataset>/train.py
    │
    ├─ 학습 → model 객체
    ├─ 평가 → metrics dict
    │
    ▼
  outputs/
    bundle.joblib         ← 모델 본체
    metadata.json         ← ①·③·④·⑥ 일부
    requirements_lock.txt ← ⑤ (있다면)

  ▼ fraud-service 측

  models/bundle.joblib 만 마운트
  → metadata 는 운영자가 별도 확인
```

## ③ 단계별 핵심

### 단계 1: 데이터 해시의 의미

데이터셋 자체를 매번 보관하기 어려우니 **해시로 동일성 증명**한다. fds-research 의 학습 스크립트는 입력 CSV의 SHA-256 을 metadata.json 에 기록한다 ([`#20 학습 파이프라인`](../../20_모델_학습_파이프라인.md) 참조). 같은 해시 = 같은 데이터 = 결정적 학습 가능성.

### 단계 2: 시드 고정의 비결정적 부분

`random_state=42` 는 sklearn 의 결정성을 보장하지만, **GPU 연산·멀티스레드 BLAS** 는 시드만으로 결정적이지 않을 수 있다. PayWise 의 IF·XGBoost 는 CPU 기반이라 비교적 안전하지만, 향후 LSTM 같은 deep model 을 학습한다면 [`torch.use_deterministic_algorithms()`](https://pytorch.org/docs/stable/notes/randomness.html) 같은 설정이 필요.

### 단계 3: 하이퍼파라미터의 코드 vs JSON

현재 fds-research 학습 스크립트의 하이퍼파라미터가 **코드에 박혀 있다**. metadata.json 에 함께 적히지만, "코드와 JSON 이 동기화돼 있다" 는 보장은 수동. 이상적으로는 단일 JSON 을 코드와 metadata 양쪽에서 읽는 것.

### 단계 4: 라이브러리 버전의 잠금

`fds-research/requirements.txt` 가 학습 환경을, `fraud-service/requirements.txt` 가 추론 환경을 정의. 두 파일의 sklearn/xgboost 버전이 일치해야 joblib 번들이 호환된다 — **버전 불일치는 silent breakage 의 가장 흔한 원인**.

### 단계 5: 평가 지표의 함께 기록

학습 시점에 측정한 AUC·precision@K·confusion matrix 가 metadata.json 에 함께 저장된다. 이 지표가 [`M3`](03_AB_테스트와_모델_평가.md) 에서 신·구 모델 비교의 출발점이 된다.

### 단계 6: 환경 격리의 부재

학습이 컨테이너 내부가 아니라 개발자 로컬에서 일어날 수도 있다. Dockerfile 기반 학습 환경(예: GitHub Actions + Docker) 이 있으면 환경 변수·OS 영향이 사라지지만, 캡스톤 단계에서는 명시적이지 않다.

### 단계 7: backend 분석 모델의 별도 흐름

[`backend/app/api/routes_train.py`](../../../backend/app/api/routes_train.py) 가 KMeans·LSTM 학습을 트리거한다. 이는 **운영 중 즉시 학습** 하는 구조로, 본 글의 fds-research 흐름과 다르다. 즉시 학습은 사용자 데이터 변화에 반응하는 장점이 있지만 **재현성은 약하다** — 학습 시점의 데이터 스냅샷이 보관되지 않음.

## ⑤ 통합 설계 트레이드오프

- **metadata 의 비강제성**: metadata.json 이 있으면 좋지만 없어도 fraud-service 는 작동. 즉 **재현성 보장이 필수가 아니다** — 운영자가 잊으면 빚이 쌓인다. 모델 로드 시 metadata 검증을 강제하는 게 다음 단계.
- **하이퍼파라미터 출처의 단일화**: 현재 코드와 metadata 가 따로. 단일 JSON/YAML 을 양쪽에서 읽는 구조가 안전.
- **학습 환경 컨테이너화 부재**: 로컬 학습 의존성이 운영 환경과 어긋날 수 있다. Dockerfile 기반 학습 + CI 자동화 가 다음 보강 영역. (✅ ROADMAP W6-#6 — `fds-research/Dockerfile` python:3.11-slim + requirements 캐시 레이어 + train_paysim CMD, .dockerignore 로 data/outputs 제외)
- **backend 즉시 학습의 재현성 공백**: KMeans·LSTM 의 학습 데이터가 학습 직후 변할 수 있어 "그때 그 모델" 을 다시 만들 수 없다. 학습 입력 스냅샷 저장이 필요.
- **시드 외 비결정성 원인**: 멀티스레드 BLAS·CUDA·dataloader shuffle 등이 캡스톤 단계에선 무관하지만 향후 deep model 도입 시 명시적 설정 필요.

## ⑥ 한 줄 정리

재현성은 데이터 해시·하이퍼파라미터·시드·라이브러리 버전·환경·지표의 7가지 정보가 **번들과 함께 묶여야** 비로소 보장되며, PayWise 는 metadata.json 으로 일부를 묶지만 검증의 강제성이 다음 보강 영역이다.
