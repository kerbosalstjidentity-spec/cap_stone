# [M3] A/B 테스트와 모델 평가 — 신모델이 정말 더 나은가를 묻는 방법

> **ML 모델 생명주기 시리즈 3편**. 학습 시점의 평가 지표만으로는 운영에서의 우월성이 증명되지 않는다. PayWise 는 (1) A/B 트래픽 분배, (2) 운영 시점 평가 지표, (3) XAI 검증의 3가지로 모델 비교를 한다.

---

## ① 관점 정의

학습 시점 AUC 0.95 가 운영에서 0.85 가 되는 일은 흔하다. 데이터 분포 차이·라벨 지연·시간 변화 때문이다. 그래서 **운영 트래픽 위에서의 비교**가 필요하다. 이 글은 A/B 테스트·평가 라우터·XAI 검증의 3축을 본다.

---

## ② 전체 흐름도

```
학습 시점:
  fds-research/scripts/<dataset>/eval.py
    └ AUC, precision@K, confusion matrix 산출
       (정적 지표, 학습 데이터 분포 기준)

배포 후:
  fraud-service/scoring/ab_test.py
    │
    ├─ user_id hash → 0~99
    ├─ < SPLIT_RATIO → 모델 A
    ├─ ≥ SPLIT_RATIO → 모델 B
    │
    ├─ 두 번들 모두 메모리 보유
    └─ 결과를 로그/DB에 적재 (variant 라벨 포함)

운영 평가:
  backend/api/routes_evaluation.py (#22)
    │
    ├─ 시간 윈도우별 PASS/REVIEW/BLOCK 분포
    ├─ variant 별 비교
    └─ 라벨이 도달하면 confusion matrix 갱신

XAI 검증:
  backend/services/xai_engine.py (#7)
    └ SHAP 상위 특성이 도메인 직관과 일치하는지
      "왜 이 거래가 사기로 분류됐는가" 가 설명 가능한지
```

## ③ 단계별 핵심

### 단계 1: 학습 시점 평가의 한계

fds-research 의 eval 스크립트가 산출하는 AUC·precision@K 는 **학습 데이터 분포 기준**의 정적 지표다. 운영 데이터가 분포 이동(drift)을 겪으면 이 숫자는 미래 성능을 보장하지 않는다.

### 단계 2: A/B 트래픽 분배

[`fraud-service/app/scoring/ab_test.py`](../../../fraud-service/app/scoring/ab_test.py) 가 user_id 해시로 트래픽을 나눈다 ([`#18 A/B 테스트`](../../18_AB_테스트_모델_비교.md)). 같은 사용자는 항상 같은 variant 에 할당되는 점이 중요 — **사용자 경험 일관성**.

### 단계 3: variant 라벨의 추적

A/B 결과는 (timestamp, user_id, variant, score, action) 로 적재되어야 한다. 향후 라벨(실제 사기 여부)이 도달하면 variant 별 confusion matrix 가 갱신된다. 이는 [`#22 모델 평가`](../../22_모델_평가.md) 의 직접 입력.

### 단계 4: 운영 평가 지표

[`backend/app/api/routes_evaluation.py`](../../../backend/app/api/routes_evaluation.py) 가 (1) 시간 윈도우별 분포, (2) variant 별 비교, (3) 라벨 도달 시 정밀도/재현율 갱신을 제공한다 ([`#22 모델 평가`](../../22_모델_평가.md)). **학습 시점의 한 숫자(AUC)** 가 아닌 **운영 시점의 시계열 지표**가 핵심.

### 단계 5: 라벨 지연 문제

사기 거래의 진짜 라벨(차지백·고객 신고)이 거래 후 며칠~몇 주 뒤에야 도달한다. 즉 **신모델이 진짜로 우월한지 확인까지의 lag** 가 있다. 이 lag 동안 A/B 비교는 PASS/BLOCK 분포 같은 **간접 지표**에 의존.

### 단계 6: XAI 의 도메인 정합성 체크

[`backend/app/services/xai_engine.py`](../../../backend/app/services/xai_engine.py) 의 SHAP 값이 **도메인 직관과 일치하는가** 가 모델 신뢰의 한 형태다 ([`#7 XAI`](../../07_과소비_분류_XAI_XGBoost_SHAP.md)). 예: 사기 점수에 "거래 시간대" 보다 "user_id 의 첫 글자" 가 더 기여하면 데이터 누수 의심. XAI 가 모델 디버깅 도구로 작동하는 시점.

### 단계 7: 비교의 통계적 유의성

A/B 결과 차이가 우연인지 진짜인지 판별하려면 **샘플 수와 효과 크기**가 필요. 현재 코드에 통계적 유의성 검정(예: 카이제곱)은 명시되지 않음 — 운영자가 외부 도구로 검증하는 단계.

## ⑤ 통합 설계 트레이드오프

- **트래픽 비율 동적 조정 부재**: 현재 A/B 분배는 정적. 1%→10%→50%→100% 점진 롤아웃은 미구현. 신모델 회귀 시 영향 크기를 제어하기 어렵다. (✅ ROADMAP W7-#5 — `GET·PATCH /admin/api/ab-traffic` 0~100 동적 조정)
- **라벨 지연의 비대칭성**: PASS 거래의 정상성은 즉시 알 수 없고, BLOCK 거래의 false-positive 도 사용자 신고가 와야 안다. 이 비대칭이 평가 lag 의 본질.
- **통계 검정 자동화 부재**: 카이제곱·t-test 같은 기본 검정이 routes_evaluation 에 통합되어 있지 않다. 운영자 의존. (✅ ROADMAP W7-#7 — `app/scoring/ab_stats.py` 두 비율 z-test + 3분할 카이제곱(df=2 closed-form) + `GET /admin/api/ab-significance` 자동 검정)
- **XAI 검증의 수동성**: SHAP 값을 사람이 보고 판단해야 한다. 자동 anomaly detection (예: "user_id 가 상위 기여 특성") 은 미구현.
- **성공 지표의 비즈니스 정렬**: AUC 가 올라도 false-positive 비용이 오르면 비즈니스 손실이 커질 수 있다. **비즈니스 KPI 와 ML 지표의 매핑**이 명시적이지 않다.

## ⑥ 한 줄 정리

A/B 테스트와 모델 평가는 트래픽 분배·variant 추적·라벨 지연 처리·XAI 검증의 4중 메커니즘으로 짜이지만, **점진 롤아웃과 통계 검정 자동화**가 다음 운영화 영역이다.
